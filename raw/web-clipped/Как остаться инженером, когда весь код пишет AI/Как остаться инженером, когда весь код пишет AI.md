And most importantly, we don't burn the most important resource—the engineers ' attention, which is currently in very short supply. So, after all this rigorous CI passes, we can say that the code quality seems to be okay.

**27:59** · Why do I say "seems"? Because these are all metrics, but there is also architecture . And it might look good, but be architecturally incorrect. So, we also check this code with a separate agent that scans it for architectural violations. How can we actually do this ? Quite simply. Any codebase we build corresponds to some kind of architecture. There are different approaches and different architectures: stricter ones, looser ones.

**28:24** · But the main thing is that the code follows some architecture, rather than just being dumped there by our models based on how they were trained and what they think is best. Because that is most likely when we get that terrible code we might see, if the model just goes into a loop, throws something together, writes it up, and you look at it and think, "What kind of junk did it make?"

**28:46** · So, in order for us to be able to check the architecture of our code, we have a separate judge, a separate agent, that checks the code for its architecture.

**28:55** · But how do we go about forming this agent? We could give it a prompt: " Check the code for architecture to see if it's good." But then it would check it solely based on what is inside the model. And this means that to properly check code for architecture, we need to maintain a knowledge base that spells out all our architectural principles, all our approaches, everything that we and our team consider correct and high-quality, and how we want our production to look.

**29:20** · So, for this agent to be effective, you definitely need to work on this knowledge base, describe it, update it, and constantly improve it. And in this case, this agent complements our CI, which had rigorous code checks, by now checking whether the code conforms to our architecture.

**29:39** · And if it finds any problems, we won't open a PR or give it to other engineers for review. If we have passed this agent's check, then from this code we can create a PR, merge it into the main branches, review it further, and it goes to production. And it would seem that everything is fine, but there is one nuance. Let's assume that the code and these agent checks are already far along in our pipeline, at the very end.

**30:01** · And if at the moment of verification we realize that this code does not align with our knowledge base or our architecture, and errors were made earlier in the pipeline. And this means that in our workflow, where the code was somewhere at the end and a global architectural error was made, what should we do now? Do we just change this code, or do we go back earlier in our workflow, perhaps to the design phase? Accordingly, we rework that design phase and start everything all over again.

**30:32** · And this is a question that is better left for an engineer to answer, not a model. If our agent-based verification fails and we return this information to our coding phase agent, it might start making decisions about changing the design at a point where it could cause new problems. It is better to stop at this point, put a human in the loop, and decide what we are going to do. Are we reworking our entire pipeline, or are we making changes to our code to move forward?

**31:03** · So, where is the human in all those pipelines I was talking about? Definitely, the human is in the enrichment phase, when we need to take the engineering knowledge in our heads, put it into our pipeline and task, and pass it to the agent. Then, when we have drawn up the design and architecture of what we are going to do , there aren't that many documents, just architectural matters. and review them independently as a team.

**31:28** · This is quite fascinating, because while working on architecture and design previously seemed like something only architects or senior team members could do, no, now we are all seniors, and everyone works on design and architecture. Because writing code with agents is very fast, but integrating that code correctly into our gigantic codebases is quite difficult.

**31:50** · Therefore , we place a human, or even better, a team, in the design phase, because then the knowledge of how our system works will spread among the engineers. All other phases will not proceed in a " human in the loop" format, but in a " human on the loop" format. That is, the human is observing. And we can observe what is happening here so that at some point we can stop it if we see that things are going wrong. But at the same time, our main verification is deterministic.

**32:21** · Plus, we can add agents to any transition phase where we feel we need extra attention, where errors are highly probable, and could lead to code base degradation or the burning of a huge number of limits and tokens.

### Core, supporting, generic: кто ревьюит PR

**32:38** · Next, and the following big point is when we can hand off PR reviews to agents and when to humans. And here, our good old friend DDD comes to the rescue. This means that all features, everything we create, can be broken down into three types. And these will be our domain types. This is CORE, the most important functionality that gives us an advantage from a business perspective, from the perspective of the product we are developing. The next is Supporting.

**33:07** · This is the part of the domain that supports our core competitive advantages but is not something exceptional for the business or the value that our product creates.

**33:20** · And the last is Generic. This is standard functionality that is necessary for our business but doesn't create any unique value because everyone has it. So, in terms of PRs, we have a rule: first, if it’s Core, then all PRs must be 100%reviewed by a human. And accordingly, this Core PR is reviewed by one or more engineers. They check it thoroughly because it affects our key value, something without which our domain wouldn't exist.

**33:48** · When we talk about Supporting, the number of engineers who review it decreases. It can be reviewed by the person who wrote it. And the engineers themselves know that Supporting can be reviewed a bit more loosely than Core. We don't need to read everything thoroughly, download it, run it, and verify it. It’s a bit simpler here.

**34:07** · If it’s Generic, we simplify the review process even further and allow the developer to just quickly scan through it, understand that yes, something was changed or not, because we already reviewed the design earlier, we ran a large number of tests , and it will likely be safe to release . More or less, as I told you, if we have the human resources to review our code, it is better to have that code reviewed by our own resources.

**34:37** · Therefore, it’s best to base your decisions on what capabilities you have , how fast you need to move, how quickly you need to deliver features, whether you can slow down, and whether you can implement very strict pipelines . Because if your pipelines are strict and you measure your production, you have metrics in place, and you know what CFR, MTTR, and MTTF are. You measure all of this and realize that in terms of how things reach production, the number of incidents, and how you handle them, everything is fine, then you can relax PR review standards for certain subject areas.

**35:07** · If your production metrics are dropping significantly, you should by no means grant these concessions; instead, you must tighten your CI, tighten reviews across the board, and only then consider any easing of standards. That is precisely why delivering functionality to production quickly won't work, because it's either we cross ourselves, send it off, and say: "Well, Godspeed, let's go.""I hope it doesn't crash and somehow just works."

**35:33** · Or we act like engineers, implement engineering practices, measure everything with metrics, and see where our weak points are and where they aren't. In the event that we realize our CFR is dropping somewhere and our change failure rate is quite high, and we keep failing in terms of code because something went wrong, we then go back to our entire pipeline, to all our phases, look for errors, and add either deterministic checks, additional agents, or put a human back in the loop . That is why implementing agent-based development is a fairly complex process .

**36:02** · And you can't just come to the team and say: "Hey-hey, everyone, let's go, let's all write code with agents." I heard there's this cool thing. Spec Driven Development. Grab some specs for yourselves. There are some cool skills out there somewhere. Everyone downloads as many skills as they want and works with them. And that's it, now we will deliver a million features to production and deliver everything like gods. Most likely, no. This will lead to the decay of our codebase. It will become even harder to maintain because if it's hard for you to maintain, then it will be just as hard for an agent to maintain this codebase.

**36:30** · It will burn through more limits, it will introduce defects faster, your functionality will degrade, and users will leave you very quickly. Therefore, in any development, it is better to start from quality and the users for whom we are delivering all this. And by no means should you ship any crap to production that we don't even know how it works, just because we kept hitting Enter.

**36:51** · So, I don't advise you to turn into these meat-based proxies who just hit Enter, send code to someone for review, and don't even know what's going on in there. Because if you're worried about AI replacing you, I think being a meat-based proxy is what will get you replaced by AI pretty quickly. That's why we're coming to the realization that code is no longer the bottleneck.
