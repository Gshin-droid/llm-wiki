# Базовая защита сервера (VPS): SSH, отсев перебора, повторяемая настройка

## Определение

Минимум, который делается на арендованном сервере (VPS) до того, как на нём появится что-то ценное: вход только по ключу и не под root, отсев перебора паролей, настройка, которую можно повторить одной командой на новом сервере, копии данных вне сервера. Собрано 2026-10-30 по документации OpenSSH, Ubuntu, fail2ban, CrowdSec и Ansible; поводом была наводка из чата — [[vps-bazovaya-zashchita-ssh-crowdsec-ansible]].

Главная мысль страницы — не список настроек (он везде одинаковый), а **ловушки, при которых настройка написана, а не действует**. Это тот же класс поломки, что «тихий успех» в [[invariant-vidno-znachit-zapisano]]: отчёт есть, действия нет.

## 1. Не потерять доступ

- Перед правкой SSH держать открытой **вторую сессию** и проверять новый вход из третьего окна, не закрывая вторую. Ошибка в настройке тогда исправляется из живой сессии.
- Наводка пугает, что после запрета входа по паролю «консоль провайдера и поддержка перестанут помогать». По документации это не так: `sshd_config` управляет только службой SSH, а веб-консоль провайдера — это вход прямо в терминал машины, мимо SSH. Консоль перестанет помогать, если у пользователя вовсе нет пароля (создан с `--disabled-password`) и вход под root закрыт. *Вывод из устройства, на практике не проверен.* Значит: пользователю с `sudo` пароль оставить, SSH по паролю — закрыть.

## 2. Вход по ключу, не под root

Ключевые параметры `sshd_config` и их значения **по умолчанию** (man-страница OpenSSH):

| Параметр | По умолчанию | Что ставить |
|---|---|---|
| `PubkeyAuthentication` | `yes` | оставить |
| `PasswordAuthentication` | `yes` | `no` |
| `KbdInteractiveAuthentication` | `yes` | `no` — второй путь ввести пароль; старое имя `ChallengeResponseAuthentication` |
| `PermitRootLogin` | `prohibit-password` (root только по ключу) | `no` |
| `AllowUsers` | не задан — входят все | имя своего пользователя |
| `MaxAuthTries` | 6 | можно меньше |

Закрыть только `PasswordAuthentication` мало: `KbdInteractiveAuthentication` по умолчанию тоже `yes`.

## 3. Ловушка: действует первое значение, а не последнее

У `sshd_config` правило обратное привычному: «для каждого ключевого слова используется **первое** полученное значение». В Ubuntu строка `Include /etc/ssh/sshd_config.d/*.conf` стоит в начале файла, поэтому файлы из этой папки **перебивают** основной `sshd_config`.

Там же cloud-init (с версии 22.3) пишет `50-cloud-init.conf`, и на Ubuntu 24.04, поставленной с образа, в нём лежит `PasswordAuthentication yes` (Launchpad, ошибка #2088207). Итог: в `sshd_config` написано `no`, а вход по паролю открыт.

- Свои настройки — в файл, который читается **первым**: `/etc/ssh/sshd_config.d/00-hardening.conf`. Совет «назвать 60-…, чтобы читался позже» из обсуждений — неверный, позже прочитанное как раз проигрывает.
- Либо `ssh_pwauth: false` в настройке cloud-init, либо поправить сам `50-cloud-init.conf`.

## 4. Проверять действующее, а не написанное

- `sshd -t` — проверить файл до перезапуска: синтаксис и ключи хоста. Сломанный файл с перезапуском закрывает дверь.
- `sshd -T` — напечатать **действующую** настройку после сборки всех файлов: `sshd -T | grep -Ei 'passwordauth|kbdinteractive|permitroot'`. Именно это, а не содержимое файла, и есть доказательство.
- Последняя проверка — попытка входа по паролю с другой машины должна получить отказ.

## 5. Порт SSH на новых Ubuntu

С Ubuntu 22.10 SSH по умолчанию запускается через сокет systemd (`ssh.socket`): порт держит systemd, а не `sshd`. Строка `Port` в `sshd_config` там может не сработать. Источники про 24.04 расходятся: одни говорят, что генератор `sshd-socket-generator` читает `Port` сам после `systemctl daemon-reload`, другие — что строка игнорируется. Надёжно — переопределение сокета (`systemctl edit ssh.socket`: пустая `ListenStream=`, затем `ListenStream=<порт>`), и проверка `ss -tlnp | grep ssh`. Брандмауэр открыть **до** смены порта, старый порт закрывать после проверки входа через новый. Смена порта — снижение шума в журналах, а не защита.

## 6. Отсев перебора: fail2ban или CrowdSec

**fail2ban** — читает журналы и банит адрес после `maxretry` неудач (по умолчанию 5 за 10 минут, бан на 10 минут). `ignoreip` по умолчанию **закомментирован**, свой адрес никто не защищает — отсюда «забанил сам себя при плохой связи» из наводки. Правки — в `jail.local` или `jail.d/*.local`, не в `jail.conf`: его перезапишет обновление.

**CrowdSec** — два разных куска, и это главное непонимание:
- *движок* (Security Engine) разбирает журналы и **принимает решения**;
- *исполнитель* (Remediation Component, «баунсер») **блокирует** — в брандмауэре, веб-сервере, прокси. Без установленного исполнителя ничего не блокируется.
- Общий чёрный список (community blocklist) приходит в обмен на отправку своих сигналов об атакующих адресах — это данные, которые уходят наружу.
- Свой адрес — в разрешённый список: `cscli allowlists create <имя> -d '…'`, `cscli allowlists add <имя> <адрес>` (с версии 1.6.8, действует без перезапуска).

## 7. Повторяемая настройка: Ansible

Сценарий (playbook) описывает, каким сервер должен быть, и при повторном прогоне ничего не меняет, если всё уже так. У модуля `lineinfile` есть `validate` — команда проверки временного файла **до** замены настоящего; для SSH это `validate: sshd -t -f %s`.

Ловушка из пункта 3 ловит и Ansible: в описанном случае (DEV Community, 2026) сценарий ставил `PasswordAuthentication no` в `sshd_config` на всех серверах, отчитался успехом, а `sshd -T` показывал `yes` — перебивал файл cloud-init. Лечение то же: писать в `00-hardening.conf`, убирать параметр из других файлов папки, в конце сценария проверять `sshd -T`. Зелёный прогон сценария — не доказательство, доказательство — действующее значение.

## 8. Копии вне сервера

Копия на том же сервере погибает вместе с ним. Проверка копии — восстановление в чистую базу хотя бы раз (тот же пункт есть в чек-листе перед первым платежом).

## Не проверено

- VPN-туннель вместо открытого порта SSH (WireGuard, Tailscale) — совет из наводки, первоисточник не читан; пункт в [[gaps-backlog]].
- Совместная работа fail2ban и CrowdSec на одном сервере — не проверялась.
