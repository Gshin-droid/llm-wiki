# Оптимизация стоимости вызовов Claude API

## Определение
Официальная методология Anthropic (см. [[claude-cookbook-cost-optimization]]) для снижения стоимости агента на Claude API — не сменой провайдера/модели-исполнителя, а последовательным применением семи техник **внутри одного вызова** к одной и той же модели/семейству моделей. Отличается от [[delegirovanie-deshevym-modelyam]], которая экономит **маршрутизацией** между разными моделями и провайдерами (лестница исполнителей, каскад) — рычаги дополняют друг друга, а не конкурируют.

## Порядок применения (чеклист)
Шаги идут по убыванию отдачи на усилие — начинать сверху, не изобретать своё до baseline-замера:

1. **Baseline** — заработавшее решение на capable-модели + eval + измеренная стоимость/задача. Без этого шага непонятно, что вообще улучшилось.
2. **Prompt caching** — переиспользование токенов между ходами вместо повторной обработки (`cache_control: {"type": "ephemeral"}`). Ключевое условие эффекта — **byte-stable префикс**: статический контент (system prompt, инструменты) должен быть побайтово идентичен между вызовами, а переменный (метки времени и т.п.) — вынесен в user-сообщение, ниже точки кэш-брейка.
3. **Input token management** — модель находит контекст через инструменты (retrieval), а не получает всё заранее в system prompt. Крупный справочник вызывается по необходимости, не вставляется статично.
4. **Agent-loop efficiency** — контекст многоходового диалога не должен разрастаться бесконтрольно между вызовами инструментов.
5. **Output token management** — более жёсткие ограничения на генерацию там, где это не портит качество.
6. **Batch API** — неинтерактивная нагрузка уходит в асинхронную очередь (официальная скидка платформы — 50% на стоимость токенов).
7. **Model selection** — самая дешёвая модель, которая всё ещё проходит порог качества eval — в последнюю очередь, а не в первую: смена модели без остального чеклиста экономит меньше и рискует качеством больше.

## Измеренный порядок величины эффекта
Из notebook-примера (агент адъюдикации страховых случаев, baseline $0.29/задача, 10/10 точности):

| Техника | Экономия |
|---|---|
| Prompt caching (автокэш, 2 хода) | −32% |
| Byte-stable префикс | −44% относительно нестабильного |
| Явные cache breakpoints (стабильное перед переменным) | −54% |

Цифры конкретного примера, не универсальная гарантия — но полезный ориентир порядка величины (десятки процентов от одного только кэширования, если префикс дисциплинированно стабилен).

## Дополнение (2026-08-25): TTL кэша как отдельный параметр

Claude Code 2.1.243 ([[claude-code-changelog-snapshot-2026-08-25]]) добавил `promptCacheTtl`/`subagentPromptCacheTtl` — раздельный срок жизни промпт-кэша: час на основном диалоге, пять минут (дефолт) на субагентах. Это не новый шаг чеклиста, а прежде неявный параметр шага 2 (Prompt caching), впервые вынесенный в настройку CLI отдельно от byte-stable префикса. Практический вывод: длинный автономный ход (Routines, `/loop`), растягивающийся дольше пяти минут между обращениями к модели, терял кэш на дефолтном TTL до этой версии — если он не укладывался в старое окно автокэша.

## Дополнение (2026-08-28): TTL кэша на уровне одного агента, и чеклист как встроенная команда

Claude Code 2.1.248 ([[claude-code-changelog-snapshot-2026-08-28]]) добавил `experimental.cacheTtl` (`"5m"`/`"1h"`) в frontmatter конкретного агента — гранулярность на ступень ниже дополнения 08-25: там TTL задавался классу («основной диалог» / «субагенты»), здесь — одному конкретному агенту, в обход дефолта его класса. Полезно агенту, который системно ждёт дольше пяти минут между вызовами модели, но не заслуживает часового TTL для всех субагентов сразу. Статус `experimental` — единственная пометка нестабильности среди TTL-настроек на этой странице.

Той же версии (2.1.247) — **`/claude-api cost-optimize`**, встроенная subcommand: *"profile an existing project's Claude API spend and work through cost levers (caching, token hygiene, batch, effort, model choice) one measured change at a time"*. Порядок и состав рычагов совпадает с чеклистом этой страницы (prompt caching → input token management → agent-loop efficiency → output token management → batch API → model selection) почти дословно — методология, собранная из notebook'а [[claude-cookbook-cost-optimization]] и применявшаяся вручную, теперь формализована вендором в инструмент, профилирующий конкретный проект вместо общего текста.

## Дополнение (2026-08-31): видимость спенд-лимита и промпт-кэша

Claude Code 2.1.251 ([[claude-code-changelog-snapshot-2026-08-31]]) добавил Spend limit bar в `/usage` (для шлюзов организации со спенд-лимитом) и per-session строку в `/cost` с hit ratio, misses и разбивкой warm/cold попаданий промпт-кэша. Не новая механика, а видимость уже существующей — прежде TTL-настройки (дополнения 08-25 и 08-28 выше) применялись «в теории»: не было штатного способа проверить, что заданный `promptCacheTtl`/`experimental.cacheTtl` действительно снижает промахи кэша, а не просто выставлен. Теперь `/cost` даёт цифру для этой проверки на конкретной сессии.

Той же версии — резюмирующие `SessionStart`-хуки получают возраст сессии и оценку стоимости пере-кэширования до того, как сессия продолжится с холодным кэшем: хук может теперь принять решение (продолжать / предупредить / отказаться) на основе цены заранее, а не постфактум по счёту.

## Связь с делегированием дешёвым моделям
[[delegirovanie-deshevym-modelyam]] решает «какая модель вообще должна выполнить задачу» (лестница исполнителей: скрипт → локальная модель → бесплатный API → субагент → основной агент). Этот концепт решает другой вопрос — «как дешевле дозвониться до уже выбранной модели», применим на любой ступени этой лестницы, где ступень — вызов Claude API. Практический пример пересечения: субагент на ступени 3 лестницы делегирования — сам является Claude-агентом и может применить этот чеклист (кэш, batch) внутри себя.
