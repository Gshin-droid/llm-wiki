# Obsidian-вики для документации кодового проекта (альтернативный паттерн)

## Определение
Из [[bashkardinov-obsidian-claude-guide]]: другое применение связки Obsidian + Claude, чем персональная база знаний ([[persistent-wiki-pattern]]) — вики как живая документация конкретного кодового проекта, для команды разработчиков.

## Структура (отличается от Jarvis-паттерна)
- `daily-changes/` — лог изменений агентом и разработчиком по дням
- `context/` — техзадание, термины, записи встреч, требования
- `structure/` — техническая документация, повторяющая структуру кодовой базы (client/server/database/endpoints); это основной раздел, с которым работает агент, должен полностью отражать текущее состояние кода
- `README.md` — корневой файл со ссылками на все разделы + инструкции для агентов

## Подключение через MCP (альтернатива прямому доступу к файлам)
В отличие от нашего подхода (Claude Code запускается прямо в папке vault, читает файлы напрямую), здесь используется протокол MCP через плагин Obsidian **Local REST API** + сервер (`obsidian-semantic-mcp`, на момент статьи (05-2026) deprecated → `obsidian-mcp-plugin` в бета). Даёт агенту доступ к vault даже когда Obsidian закрыт, но требует больше настройки (`.mcp.json`, API-ключи, сертификаты).

**Устарело: схема из источника (05-2026) описывает мост из двух частей — плагин Local REST API внутри Obsidian + отдельный внешний Node-процесс `obsidian-semantic-mcp`, поднимаемый через `npx`.** Допроверка 2026-09-12 по официальному репозиторию `github.com/aaronsb/obsidian-mcp-plugin` (клонирован напрямую, не пересказ) показала архитектурный сдвиг: тот же проект, что источник называл бетой-преемником, вырос в самостоятельный плагин **«Semantic Notes Vault MCP»**, официально опубликован в Obsidian Community Plugin directory (`community.obsidian.md/plugins/semantic-vault-mcp`) — уже не бета. Ключевая перемена в самом README: «No external Node process to launch, no separate REST-API plugin to bridge through: the server *is* the plugin» — MCP-сервер теперь встроен в сам плагин и работает внутри Obsidian, мост из двух отдельных частей (REST API + внешний npm-пакет) для этого пути подключения больше не нужен. Установка — перетащить файл `.mcpb` на Claude Desktop и вставить ключ.

Подтверждено по первичным файлам репозитория (`manifest.json`, `package.json`, `git log`): актуальная версия **0.12.8** (коммит от 2026-09-02), активно развивается (десятки релизов с версии 0.9.3). Восемь тулов вместо изначальных: `vault` (13 операций — list/read/create/search/move/split/combine и др.), `edit`, `view`, `graph`, `workflow`, `dataview`, `bases`, `system`; поддерживает не только Claude Desktop/Code, но и Cline, Continue.dev — любой MCP-совместимый клиент. Заявлен режим только для чтения и allow/block-списки путей.

**Проверка «уверенности прозы», а не доверие ей на слово:** в `CHANGELOG.md` под заголовком `[Unreleased]` до сих пор висят строки «🔴 CRITICAL: no API key validation» и «🔴 CRITICAL: path traversal vulnerability» — на первый взгляд похоже на актуальные открытые дыры. Проверка `git log -p` показала, что эти строки не менялись с самых ранних коммитов истории репозитория (шаблонный текст первичной настройки issue-трекера, issues #9–#12), а текущий код (`src/main.ts`) требует API-ключ на каждый запрос («Authentication enabled. API key required for access.») — то есть заявление устарело внутри самого файла-источника и не отражает текущее состояние кода. Урок общий, не только про этот плагин: у файла-источника внутри проекта тоже может быть просроченная секция, и её нельзя принимать по одной уверенно звучащей строке без сверки с кодом.

## Практические советы источника
- Файл `CLAUDE.md` в корне проекта, можно ссылаться на него явно, если агент "не слушается"
- Загружать контекст небольшими порциями с проверкой на каждом шаге, не доверять модели описать весь проект за один проход
- Следить за размером файлов — просить агента дробить, если раздел разросся
- Подход даёт максимум пользы на крупных/средних проектах; для простого лендинга хватает обычного контекстного окна

## Применимость к рабочим проектам пользователя
Это отдельный, но совместимый с [[vibecoding-full-workflow|вайбкодинг-воркфлоу]] паттерн — можно применять к конкретному `wiki/projects/`-проекту как способ вести живую документацию кода, отдельно от общей персональной вики.
