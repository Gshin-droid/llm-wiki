# Практические правила создания Skills вместо промтов

## Определение
Свод практических правил перехода от одноразовых промтов к [[claude-skills|скиллам]] — переносимым, накапливаемым "умениям" Claude. Синтезировано из официальной методологии Anthropic ([[anthropic-official-skills-docs]]), доклада создателей Skills ([[anthropic-code-summit-build-skills-talk]]) и практики сообщества ([[habr-claude-skills-practical-guide]]).

## Когда переходить от промта к скиллу
Эвристика из официальной документации Claude Code: **создавай скилл, когда ловишь себя на вставке одной и той же инструкции/чеклиста/процедуры в чат повторно**, или когда раздел CLAUDE.md разросся в процедуру, а не остался фактом. Ключевое отличие от CLAUDE.md: тело скилла грузится в контекст только при использовании — длинный референсный материал почти ничего не стоит, пока не понадобился, в отличие от CLAUDE.md, который читается целиком каждую сессию.

## Архитектура: progressive disclosure
Три уровня загрузки контекста (не более того, что нужно прямо сейчас):
1. **Система** — только `name`+`description` всех скиллов в system prompt
2. **Активация** — Claude решает, что скилл релевантен → грузит весь `SKILL.md`
3. **Навигация** — доп. файлы (`references/*.md`) грузятся по требованию через Bash, а не сразу

Это делает объём контекста, который можно "упаковать" в скилл, практически неограниченным — файловая система и code execution заменяют удержание всего в промте разом.

## Три слоя SKILL.md
| Слой | Вопрос | Содержание |
|---|---|---|
| **Description** | Когда брать скилл? | Триггер в frontmatter — единственный механизм, по которому Claude решает подключать скилл |
| **Instructions** | Как выполнить задачу? | Плейбук, пошаговая процедура |
| **Tools** | Чем выполнить? | Скрипты/API-обёртки — детерминированный код вместо AI-вычислений: дешевле, быстрее, повторяемо |

Большинство ограничиваются первыми двумя слоями и считают, что готово — реальная сила в третьем (`scripts/`), но именно туда доходят не все.

## Правило: Description — это всё
Description — единственное, что видит Claude при выборе скилла из списка; тело файла на решение не влияет.
- Объём: ~100 слов в метаданных
- Явное "when to use", а не просто резюме содержимого — это условие срабатывания, а не аннотация
- "Pushy" тон: явно перечислить кейсы, а не быть обтекаемым (расплывчатое описание не подцепится)
- Разные формулировки одного и того же намерения пользователя
- Плохо: `"Build dashboards"` → Хорошо: `"How to build a simple fast dashboard... use whenever user mentions dashboards, data visualization, internal metrics — even if they don't explicitly ask for a 'dashboard'"`
- Метод проверки: 20 eval-запросов (should-trigger / should-not-trigger), с упором на **near-misses** — запросы, которые звучат похоже, но требуют другого скилла

**Лимит длины различается по платформам** (уточнено 2026-07-29 при проверке [[bohomolov-skill-architecture]] по [официальной документации](https://claude.com/docs/skills/how-to)): спецификация [Agent Skills](https://agentskills.io/specification) допускает **1024 символа**, но claude.ai режет description до **200 символов**. Скилл, написанный по спецификации, при загрузке в claude.ai придётся ужимать — а ужимать приходится ровно то, что отвечает за срабатывание. Практический вывод: если скилл предназначен и для claude.ai, писать description сразу под 200 символов, вкладывая в них «when to use», а не пересказ содержимого.

## Структура файлов
```
skill-name/
├── SKILL.md          # frontmatter (name, description) + тело < 500 строк
├── scripts/           # детерминированный код, повторяющаяся логика
├── references/        # документация >300 строк или domain-specific, грузится по требованию
└── assets/            # шаблоны, иконки, статичные файлы
```
- **Правило 500 строк**: тело SKILL.md, приближающееся к пределу — сигнал выносить контент в `references/` с явными указателями (`See references/config-guide.md`)
- **Разделяй взаимоисключающие контексты** по разным файлам (напр. `aws.md`/`gcp.md`/`azure.md`) — экономит токены, Claude грузит только релевантный
- **Сигнал для scripts/**: если в нескольких test-кейсах Claude заново пишет один и тот же код (`build_chart.py`, `create_pdf.py`) — вынести в bundled script один раз
- **`dependencies` во frontmatter** (уточнено 2026-07-29): скрипт, которому нужны внешние пакеты, объявляет их там — `dependencies: python>=3.8, pandas>=1.5.0, matplotlib`. Claude ставит пакеты из PyPI/npm при загрузке скилла. Без объявления скрипт работает только на машине автора и падает у всех, кому скилл передан
- **Правило против «схлопывания» архитектуры** (из [[bohomolov-skill-architecture]]): вынося правила в отдельный файл, надо явно запретить дублировать их обратно в SKILL.md. Без этой фразы модель копирует вынесенное «на всякий случай» — файлы появляются, но главный файл не худеет, и смысл выноса теряется
- **Упаковка для claude.ai** — ZIP, содержащий **папку** скилла (`my-skill.zip → my-skill/SKILL.md`), а не файлы в корне архива; имя папки должно совпадать с полем `name`

## Гранулярность стоит ходов агента (проверено замером 2026-07-29)

Progressive disclosure описывают как безусловное благо: «грузится только нужное». Замер на реальном скилле ([[humanizer-ru-skill-refactor]]) показал, чего в этой формулировке не хватает: **каждый файл, который агент открывает отдельно, стоит хода, а каждый ход заново прогоняет накопленный контекст через модель.** Биллинг идёт не за размер файла, а за раунд-трип.

Что из этого следует:

- **Много мелких файлов дороже, чем несколько крупных.** Первая, наивная разбивка монолита (499 строк → 6 файлов с таблицей навигации) оказалась на 4–12% **дороже** исходного монолита: 12–13 ходов вместо 3–5. Экономия «не грузить лишнее» полностью съелась переспрашиванием контекста.
- **Правило «читай только нужный файл» надо писать явно и с запретом.** Таблица навигации без запрета читать остальное не работает: агент честно открывает всё, что перечислено. Формулировка «файлы не открывай, кроме случаев X и Y» вернула около половины перерасхода.
- **Лучший ход — вообще не заставлять модель открывать файлы.** Если у скилла есть скрипт, пусть он и доставляет нужный кусок правил: находка + правило переписывания одним выводом. В замере это дало 6 ходов вместо 12–13 и увело новую версию на 4,2–7,8% **ниже** монолита. Файлы при этом остаются раздельными — для правки руками, не для чтения моделью.
- **Файл, нужный почти в каждом прогоне, держи в SKILL.md.** Вынос такого файла — это гарантированный лишний ход без экономии.

Экономический смысл разбивки при этом сохраняется, но он другой, чем принято думать: пол монолита (~8 400 токенов при каждой активации) растёт с каждым новым правилом, пол многофайлового скилла (~1 800) не зависит от размера базы правил. Это вложение в стоимость будущего, а не сегодняшнего прогона.

## Скилл должен знать свои границы

Отдельный класс правил, который не приходит в голову при написании и вылезает только на прогоне ([[humanizer-ru-skill-refactor]]): что скиллу делать **нельзя**. Скилл-редактор в тесте дописал в текст ссылку на исследования учёного, которого во входных данных не было, и раздул объём вдвое — формально выполнив инструкцию «сделай текст живым».

Что стоит проговаривать явно, если скилл преобразует чужой материал:

- не добавлять фактов, имён, цифр и дат, которых нет во входе;
- держаться исходного объёма (±20%), если задача — переписать, а не дописать;
- не менять смысл заголовков и других «обещаний» исходника.

## Дополнение (2026-07-30): что подтвердила и что поправила официальная статья Anthropic

Из [[anthropic-context-engineering-claude-5]] (полностью — [[context-engineering-claude-5]]) три вещи ложатся прямо сюда:

- **Скилл — «лёгкий путеводитель», а не свод ограничений.** Формулировка Anthropic: скиллы кодируют мнения и практики команды, жёсткие рамки оставляют критичным областям. То есть раздел «Границы работы» (что скиллу делать нельзя) остаётся оправданным — но как исключение под конкретный риск, а не как стиль написания всего скилла.
- **Примеры теперь скорее вредят, чем помогают.** Модель цепляется за показанный способ и перестаёт искать за его пределами. Для скилла со скриптами это означает: вкладывать усилие во внятное описание инструмента и выразительные параметры, а не в галерею примеров вызова. Согласуется с уже записанной здесь ошибкой «хардкод примеров вместо паттернов», но даёт другую причину: дело не только в необобщаемости, а в сужении поиска.
- **Progressive disclosure подтверждён как правильная архитектура** — и это не отменяет замера из [[humanizer-ru-skill-refactor]], где наивная разбивка вышла дороже монолита. Оси разные: Anthropic говорит про объём и конфликтность контекста, замер — про биллинг за раунд-трипы. Практический вывод остаётся прежним: разбивать, но не заставлять модель открывать файлы по одному.

Ещё один пункт статьи касается не скиллов, а их соседа: **то, что раньше писали в `CLAUDE.md` длинными процедурами, должно уезжать в скиллы** — `CLAUDE.md` остаётся лёгким, с gotchas репозитория. Это ровно эвристика «раздел CLAUDE.md разросся в процедуру» из начала страницы, теперь подтверждённая первоисточником.

## Композиционность, а не монолит
Один гигантский скилл "делает всё" становится неуправляемым: баг непонятно где, улучшение одного кейса ломает другие. Решение — 3-5 фокус-скиллов, каждый отвечает за одну задачу, Claude координирует их сам (оркестрация). Баг находится мгновенно, улучшения не ломают соседние функции, не нужно строить заново.

## Чужой набор скиллов берут не целиком (сформулировано 2026-08-18)

Скиллы пишут под свои задачи, а задачи у всех разные. Поэтому в чужом наборе неизбежно и лишнее, и недостающее — брать его целиком значит платить контекстом за первое и не замечать второго. Правило: чужое берут поштучно и переделывают под себя.

Что проверять до отбора — по разбору набора [[mattpocock-skills]]:

- **Что реально загружается.** Файлы в папке плагина ≠ включённые скиллы: манифест бывает курирован. Источник истины — список `skills` в `.claude-plugin/plugin.json`. На этом наборе счёт по файлам завышал стоимость вчетверо (41 файл против 22 включённых, 486 токенов против насчитанных 1810).
- **Что стоит контекста.** Скилл с `disable-model-invocation: true` не попадает в листинг вовсе — платят только те, кого модель может взять сама. Половина набора может оказаться бесплатной.
- **Что не работает без настройки.** Скилл, пишущий во внешнюю систему (трекер задач, база), мёртв, пока эту систему не назвали. Четыре скилла из двадцати двух в разобранном наборе именно такие.
- **Что тянет за собой соседа.** Зависимости между скиллами выражаются прозой — «запусти скилл `/grilling`». Выдернешь один — получишь ссылку в пустоту.
- **Каким путём копировать.** У набора может быть несколько способов установки с разной цепочкой поставок. Путь «скопировать файлы себе» иногда проходит через чужой установщик — и возвращает звено, от которого отказались при первом выборе (см. правило 12б в [[claude-code-practices]]).
- **На каком языке говорит скилл.** Для пользователя, читающего по-английски плохо, англоязычный скилл проигрывает посредственному русскому независимо от качества содержимого. Это не придирка: скилл, вопросы которого приходится переводить, не будет вызван.

Родственное правило органического роста — ниже, «Итеративное накопление»: своё растёт из песочницы, чужое приживается только после переделки.

## Итеративное накопление ("эффект 30 дней")
Цель Anthropic: «Claude на 30-й день работы должен быть заметно лучше, чем в первый». Механизм — не Claude "учится" сам, а пользователь/Claude вместе фиксируют находки в файл:
- После сессии — один вопрос: «разовая правка или в скилл навсегда?»
- Просить Claude самого предложить правки в `SKILL.md`/`tools/` на основе только что решённой задачи
- **Раздел "Gotchas" (типичные ошибки)** — самый ценный контент скилла на практике; не придумывается заранее, а дополняется по мере реальных факапов
- Органический рост: сначала личная sandbox-версия скилла, публикация в общий marketplace — только когда доказал полезность

## Правка существующего скилла (уточнено 2026-07-29)

В claude.ai скилл правится на месте: выделить текст → **Edit with Claude** → сформулировать правку. Для многофайлового скилла правки по разным файлам отправляются вместе и применяются за один проход; новые файлы добавляются в директорию скилла. Удалять и пересобирать скилл целиком ради изменения одного файла не нужно.

Зафиксировано отдельно потому, что обратное — «дописать файл в существующий скилл из чата нельзя, только полная пересборка» — было верно ещё в июне 2026 и стоило автору [[bohomolov-skill-architecture]] часа работы. Проверено по [справке Anthropic](https://support.claude.com/en/articles/12512198-how-to-create-custom-skills) 2026-07-29; момент перехода установить не удалось, справка не датирована.

## Тестирование и итерация
1. Начинать с оценки: гонять на representative задачах, искать конкретные пробелы
2. 2-3 реалистичных тест-промпта → `evals.json`
3. Сравнение with/without skill (baseline обязателен, иначе нельзя оценить, помогает ли скилл вообще)
4. Мониторинг реального использования, self-reflection при ошибках
5. Не переобучаться на 2-3 тест-кейса — обобщать, объяснять "почему", а не только "что делать"

## Частые ошибки
| Ошибка | Последствие |
|---|---|
| Обобщённый description | Скилл не триггерится (undertriggering) |
| SKILL.md > 500 строк без иерархии | Перегрузка контекста при каждой активации |
| Хардкод примеров вместо паттернов | Скилл не обобщается на новые случаи |
| MUST/NEVER без объяснения "почему" | LLM игнорирует правило без понимания причины |
| Нет bundled script для повторяющейся работы | Каждый вызов заново "изобретает колесо" токенами |
| Нет baseline-сравнения при тестировании | Невозможно оценить, действительно ли скилл помогает |

## Где хранятся и как приоритизируются (Claude Code)
Enterprise > Personal (`~/.claude/skills/`) > Project (`.claude/skills/`) > Plugin (namespace `plugin:skill`) — при совпадении имён старший уровень перекрывает младший. Custom commands слиты со skills: `.claude/commands/deploy.md` эквивалентен `.claude/skills/deploy/SKILL.md`. В монорепо скиллы из `packages/frontend/.claude/skills/` подхватываются при работе с файлами в этой директории.

## Токен-эффективность (замер из [[hook-4-pravila-claude-skills]])
Одна и та же задача (ответ на письмо в стиле пользователя): промт — 2700 токенов / 70 сек / стиль "плавает"; скилл `/draft-email` — 900 токенов / 25 сек / 100% попадание в стиль с первого раза. ×3 меньше токенов, ×2.8 быстрее.

## Универсальность принципа
Работает везде, где есть кастомная "обёртка" над моделью, не только в Claude Code: ChatGPT (Custom GPT + uploaded files как tools), Gemini (Gems), Cursor/Windsurf (`.cursorrules` + agents + скрипты в проекте), n8n/Make (workflow-шаблоны = композиция узлов), Vercel AI SDK (tool calling + system prompts в коде). Общий принцип: не начинать каждую сессию с нуля.

## Маршрутная таблица вместо «прочитай всё» (2026-09-01, [[geekneural-sepia-de-ai-skill]])

Живой пример progressive disclosure на чужом скилле. `SKILL.md` у [[sepia]] — не свод правил, а **диспетчер**: таблица «тип текста → какие файлы грузить и в каком порядке», плюс таблица «операция → её контракт». Одиннадцать файлов правил лежат рядом, но за один вызов открываются два-три. Пол активации ~7 КБ вместо суммарных ~70 КБ базы правил.

Два решения оттуда, применимых к своим скиллам:

- **Обёртки-точки входа.** Кроме основного скилла, четыре скилла-однострочника по ~1 КБ (`sepia-write`, `sepia-review`, `sepia-refactor`, `sepia-recreate`). Операция выбирается именем вызова, а не разбором формулировки пользователя — то есть неоднозначность снимается до того, как модель начала гадать.
- **Раздел про границу доверия внутри `SKILL.md`.** Для скилла, работающего с чужим контентом, — см. [[ai-security-by-design]].

Ограничение, которое здесь уже измерено: маршрутизация окупается не сама по себе. Замер 2026-07-29 ([[humanizer-ru-skill-refactor]]) показал, что наивный вынос правил по файлам вышел на 12% дороже монолита из-за лишних ходов агента, и выигрыш появился только когда файлы перестали открываться вовсе. У Sepia ходов на маршрут два-три — но замера этого никто не делал, звёзды репозитория о стоимости не говорят.
