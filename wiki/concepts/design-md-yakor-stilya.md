# DESIGN.md: якорь стиля для агента

## Определение

**DESIGN.md** — описание визуального языка одного продукта обычным markdown-файлом в корне проекта: цвета, шрифты, отступы, скругления, тени, компоненты и раздел «делай / не делай». Агент читает его как задание к внешнему виду. Формат придуман Google Stitch; по README `VoltAgent/awesome-design-md` это пара к `AGENTS.md`: тот говорит, **как собрать** проект, этот — **как он должен выглядеть**.

Повод записать — [[vibe-coding-frontend-references]]: подборка советует брать готовый DESIGN.md реального сайта и просить модель от него не отходить.

## Зачем: позитивный якорь к негативному списку

Без указаний модель рисует в нескольких стилях по умолчанию. У нас против этого уже стоит список запретных примет ([[claude-code-practices]] п. 15): он говорит, **чего не делать**, но не говорит, что делать вместо. Модель уходит от запрещённого в соседний шаблон, и список приходится дописывать после каждого результата.

DESIGN.md закрывает вторую половину: задаёт конкретную палитру, шрифтовую пару и сетку. Вместе получается пара «якорь + запреты», и у каждой части своя работа.

Совет из поста, который стоит держать: **один файл, не смесь**. Два-три стиля в контексте дают усреднение — ту самую безликость, от которой уходим.

## Как применять у нас

- **Варианты на выбор = разные DESIGN.md.** Приём «два-три готовых варианта на выбор» из п. 15 получает материал: каждый вариант — один файл из подборки (74 штуки на 28.09.2026) или своего сбора. Выбор сохраняется в проекте файлом, а не в памяти сессии.
- **Приоритет у своего.** Если в проекте уже есть дизайн-система или компоненты, внешний DESIGN.md используется только там, где решение ещё не принято (правило из того же поста — берём).
- **Файл — это референс, а не приёмка.** Совпадение с DESIGN.md кодом не проверить (фильтр [[verification-three-levels]]: это вкус), приёмка остаётся на человеке, как и в п. 15.

## Как подключать: не через @-импорт

Пост советует подключить файл строкой `@DESIGN.md` в `CLAUDE.md` проекта. **Так делать не стоит.** По документации Claude Code ([[claude-code-practices]] п. 16) импортированный файл грузится в каждую сессию целиком. Файл Airtable из подборки — 35 КБ, порядка 9 тыс. токенов (оценка ~4 знака на токен для английского текста), и это в каждой сессии, включая правку бэкенда и тестов.

Два способа дешевле:

1. **Правило «по месту»**: `.claude/rules/design.md` с полем `paths:` на файлы интерфейса (`**/*.tsx`, `**/*.css`…) и одной строкой «перед правкой интерфейса прочитай DESIGN.md». Грузится только когда агент открыл файл интерфейса. Ограничение из п. 16: срабатывает только на файлы внутри папки проекта сессии.
2. **Упоминание без импорта**: в `CLAUDE.md` строка «стиль — в DESIGN.md, читать при работе с интерфейсом». Агент читает файл по требованию.

## Границы

- **Цвета в готовых файлах — приближение.** В файле Airtable авторы сами пометили, что часть палитры снята «пипеткой со скриншотов» и может меняться по сезону.
- **Чужой бренд.** Копировать визуальный язык Airbnb или Stripe для учебного и внутреннего проекта нормально; для продукта, который выходит наружу, это подражание чужому бренду — брать как основу, а не как копию.
- **Файл — чужой текст в контексте.** DESIGN.md читается агентом каждый раз, когда нужен, и может нести не только стиль. Проверенный файл (Airtable) — чистый; каждый новый читать перед подключением (урок ContextCrush — [[ai-security-by-design]]). Подборка коммерческая: в README реклама и платные «заказы DESIGN.md».
- **Словарь и стек.** Как и у [[maket-kak-tz-dlya-agenta]], описание компонентов может предполагать стек, которого в проекте нет; палитра, шрифты и отступы переносимы в любой стек, имена компонентов — нет.
