# RAG (Retrieval Augmented Generation)

## Определение

Способ дать языковой модели знание, которого нет в её весах и нет в вебе (внутренние документы, приватная база), не дообучая модель: система находит релевантные фрагменты по смысловой близости и подкладывает их в контекст запроса перед генерацией ответа. Решает конкретную проблему — модель не хранилище фактов, а генератор текста по паттернам, и без внешних данных на вопрос вне обучающей выборки либо выдумывает, либо честно отвечает «не знаю». Источник: [[berezhnitsky-rag-explained]].

Отличать от [[persistent-wiki-pattern|персональной вики]] (этой самой): там знания синтезируются один раз и накапливаются как связанные страницы; здесь — извлекаются заново при каждом запросе из неизменного сырья, без накопления между обращениями. Оба подхода закрывают один и тот же разрыв («модель не знает моих данных») разными средствами — RAG дешевле завести, вики дороже поддерживать, но не теряет связность и синтез между источниками.

## Базовый конвейер

1. **Chunking** — документы (PDF, страницы, база знаний) режутся на небольшие куски: модель эмбеддинга и языковая модель ограничены по объёму входа за раз.
2. **Embedding** — каждый чанк превращается в вектор («отпечаток смысла»): семантически близкие тексты оказываются близко друг к другу в векторном пространстве независимо от точных слов.
3. **Векторная база данных** — хранит эти векторы и умеет быстро находить ближайшие по смыслу без полного перебора (в отличие от обычной БД, которая ищет по точному совпадению).
4. **Retrieval** — вопрос пользователя тоже превращается в эмбеддинг, векторная база находит ближайшие по смыслу чанки.
5. **Augmentation** — найденные чанки добавляются в контекст запроса вместе с исходным вопросом.
6. **Generation** — модель отвечает на основе вопроса и подложенного контекста, а не только по паттернам из обучения.

## Почему не хватает встроенного веб-поиска моделей

У современных ассистентов (ChatGPT, Claude, Gemini) уже есть доступ в интернет, но это не заменяет RAG для приватных/внутренних данных: встроенный поиск работает только с публичным вебом, не видит корпоративные документы и внутренние базы; каждый вызов поиска стоит отдельно и не кэшируется под задачу; нет контроля над тем, какие источники используются. RAG даёт то же самое для собственных данных — с кэшированием и настройкой под конкретный бизнес-процесс.

## Пять продвинутых техник (сверх базового конвейера)

Простой конвейер выше «хорош для демо», в реальных системах не хватает точности. Комбинация техник ниже используется по ситуации — единого правильного набора нет: для новостного сайта достаточно быстрого BM25, для медицинской системы оправдан более медленный и точный реранкинг.

- **Гибридный поиск** — семантический (векторный) поиск пропускает точные совпадения (модели/номера/термины); BM25 (keyword-поиск, считает частоту точных слов) их ловит. Оба запускаются параллельно, результаты объединяются.
- **Parent document retrieval** — поиск идёт по мелким чанкам (точнее совпадают с вопросом), но модели отдаётся весь родительский документ (даёт полноту контекста, которой не хватает мелкому куску).
- **Multi-query** — вопрос пользователя автоматически переформулируется в несколько версий перед поиском, компенсируя неточную формулировку.
- **Реранкинг** — первичный поиск находит широкий пул кандидатов (например, 20), отдельная модель оценивает и оставляет top-3–5 самых релевантных перед тем, как отдать их в LLM. Стоит дополнительных секунд задержки за счёт точности.
- **Семантическое разбиение** — границы чанка проводятся по смысловым, а не по символьным границам, чтобы не разрывать связанную мысль посередине.

## Оценка качества: Ragas

Качество RAG-системы нельзя мерить на глаз («ну как, норм отвечает?») — открытый фреймворк Ragas автоматизирует это: строит knowledge graph по загруженным документам, генерирует тысячи синтетических тестовых вопросов трёх типов (простые из одного источника, требующие синтеза нескольких источников, комбинирующие конкретные факты из разных документов) вместе с эталонными ответами, прогоняет систему и считает четыре метрики:

- **Faithfulness (честность)** — насколько ответ основан на реально найденных данных, а не додуман.
- **Полнота контекста** — нашла ли система все релевантные документы.
- **Релевантность ответа** — отвечает ли система именно на заданный вопрос.
- **Точность контекста** — насколько точно выбранные документы соответствуют вопросу.

## Production-слой

- **Три уровня кэширования**: кэш уже посчитанных эмбеддингов (не пересчитывать чанк повторно); exact-match кэш готовых ответов на дословно повторяющийся вопрос; semantic cache — кэш по смысловой близости вопросов через тот же векторный поиск («как приготовить борщ» и «рецепт свекольного супа» — один кэш-хит). Риск — устаревание кэша при обновлении исходных документов, баланс между экономией и актуальностью решается вручную.
- **Мониторинг** — задержка, стоимость отдельных запросов, качество ответов на реальных данных в реальном времени; без него система «тормозит и дорожает» незаметно.
- **Приватность** — эмбеддинг практически необратим в исходный текст («отпечаток пальца, а не фотография»), но это не отменяет контроль доступа (кто ищет и в каких документах), audit log и политику хранения (сколько хранить эмбеддинги после удаления документа). Для данных под NDA — приватные модели; по мнению автора источника публичные API-провайдеры не гарантируют полной конфиденциальности даже на enterprise-подписке — это его оценка, не проверено по документации конкретных вендоров.
