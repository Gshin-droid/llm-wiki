# Работа из Windows с Linux-сервером и файлами: шесть ловушек

Живой документ. Актуально на 2026-11-09.

Собраны за один день развёртывания на удалённом Linux-сервере из Windows (Git Bash, Python, системный OpenSSH).
Ловушки 1–4 собраны там, 5–6 — 09.11 при пробе песочницы WSL. Все многоразовые: бьют в любом проекте, где агент работает из Windows. Общее с
[[ustanovka-instrumentov-na-windows]]: **команда отчитывается об успехе, а результат не тот.** Поэтому
лечится каждая проверкой результата, а не внимательностью.

## 1. `&` в конце удалённой команды уводит в фон всю цепочку — и отнимает у неё вход

Случай: файл заливался на сервер и тут же запускался в фоне одной командой:

```bash
ssh хост "cat > скрипт.sh && chmod +x скрипт.sh && nohup ./скрипт.sh > журнал 2>&1 &" < скрипт.sh
```

Команда отработала без ошибок, а `скрипт.sh` на сервере оказался **пустым** (0 байт), и запускать было нечего.

Причина — две особенности bash, а не ssh и не Windows:

- `&&` связывает сильнее, чем `&`. Значок `&` в конце уводит в фон **всю** цепочку `A && B && C`, а не только `C`.
- Фоновой команде в неинтерактивной оболочке bash подменяет стандартный вход на пустой (`/dev/null`), если управление
  заданиями выключено — так написано в руководстве bash (раздел о списках команд). `cat` читает пустоту и честно
  записывает ноль байт.

Проверено опытом: та же заливка через `< файл` без `&` передаёт файл целиком; с `cat > f && true &` — 0 байт.

**Как не наступать:** заливку и запуск — **двумя отдельными вызовами** ssh. Заливку — со сверкой размера на обеих
сторонах (`wc -c` здесь и там), несовпадение — ошибка. Удобнее всего держать маленький скрипт заливки, который сверяет
сам: тогда пустой файл не пройдёт тихо ни в одной сессии.

**Урок про разбор.** Первая версия причины была «Windows-ssh не передаёт вход через `<`» — правдоподобно и неверно.
Её опроверг один опыт в две строки до записи сюда. Причину сбоя, которая идёт в общее знание, проверять запуском, а не
выводить из того, что «после правки заработало»: правка могла убрать причину случайно.

## 2. Python на Windows пишет файлы с концами строк Windows

`Path.write_text()` и `open(..., "w")` в текстовом режиме переводят `\n` в разделитель системы — на Windows это
`\r\n` (документация Python, параметр `newline`). Файл, прочитанный с концами строк Linux, после записи «тем же
текстом» молча становится файлом с концами строк Windows. Git предупредит (`CRLF will be replaced by LF`), но
сервер, куда уедет такой файл, — нет: shell-скрипт с `\r` в конце строк падает с невнятной ошибкой.

**Как не наступать:** для файлов, которые уедут на Linux (скрипты, YAML, конфиги), писать `newline="\n"` или
`write_bytes(...)`. Проверять сам файл, а не `git diff`: при включённой настройке `core.autocrlf=true` git сам
переводит концы строк и такую разницу не показывает, так что проверка будет зелёной, а файл на диске останется с `\r\n`.
Годятся `file файл` (пишет `with CRLF line terminators`) или, для файла под git, `git ls-files --eol файл`
(столбец `w/crlf` — на диске концы строк Windows). Оба проверены опытом. `grep -c $'\r'` в Git Bash в нашем запуске
дал неверный счёт — посчитал все строки файла без единого `\r`; причину не выясняли, для проверки его не брать.

## 3. Русский текст из Python в консоли Windows превращается в «кракозябры»

`print("вставлено")` из Python, запущенного в Git Bash на Windows, выводит знаки вопроса и мусор: кодировка вывода
по умолчанию — не UTF-8. Данные при этом верные, сломан только вывод — но по нему делают выводы.

**Как не наступать:** `PYTHONIOENCODING=utf-8` перед запуском или `sys.stdout.reconfigure(encoding="utf-8")` в начале
скрипта. Для машинной проверки выводить числа и латиницу, а не русский текст.

## 4. `docker compose exec` съедает остаток скрипта, переданного через `ssh хост "bash -s" < скрипт`

Случай: скрипт замера из двух циклов — первый по одной модели, второй по другой — отдан на сервер через стандартный
вход (`bash -s` читает команды оттуда). Первый цикл отработал, второй **не выполнился вовсе**, даже его `echo`.
Ошибки нет, выход нулевой.

Причина: `bash -s` читает скрипт с того же входа, с которого `docker compose exec -T` (как и `ssh`, `docker run -i`)
читает данные для команды в контейнере. Первый же `exec` забирает остаток скрипта себе, bash дальше читать нечего.
Первый цикл уцелел, потому что bash прочитал его целиком до запуска.

Проверено опытом: такой скрипт, отданный через `ssh хост "bash -s"`, слово `ВТОРОЙ` не печатает:

```bash
docker compose exec -T сервис true
echo ВТОРОЙ
```

С `< /dev/null` в конце строки с `exec` — печатает.

**Как не наступать:** у каждой команды внутри такого скрипта, которая может читать вход, — `< /dev/null`. Либо
залить скрипт файлом (ловушка 1, со сверкой размера) и запускать файл, а не вход.

## 5. `wsl -- bash -lc '…'` раскрывает переменные раньше времени (2026-11-09)

Та же беда, что у `ssh`, только с локальной WSL. `wsl.exe` склеивает аргументы и пропускает их через оболочку
Ubuntu, и только потом её результат уходит в `bash -lc`. Одинарные кавычки Git Bash до этого второго прохода не
доживают: `$C`, `$f`, `$HOME` раскрываются в пустоту. Ошибки не будет. Вместо неё — `timeout: failed to execute
process` (пустая команда) и строки вида `ЕСТЬ ` с пустым именем файла: проверка «файл есть» отчиталась про
пустую строку.

**Как не наступать:** скрипт для WSL — файлом (в Windows-папке, её видно из WSL как `/mnt/c/…`), запуск
`wsl -d <дистрибутив> -u <пользователь> -e bash -l /mnt/c/…/скрипт.sh`. Ключ `-e` выполняет команду без
промежуточной оболочки.

## 6. Git Bash переписывает путь `/mnt/c/…` в виндовый (2026-11-09)

Аргумент, похожий на путь Unix, Git Bash (MSYS) перед запуском программы Windows сам переводит в путь Windows.
`/mnt/c/…` превращается в `<папка Git>/mnt/c/…`, и WSL отвечает «No such file or
directory».

**Как не наступать:** `MSYS_NO_PATHCONV=1` перед командой —
`MSYS_NO_PATHCONV=1 wsl -d Ubuntu -u agent -e bash -l /mnt/c/…/скрипт.sh`. Касается любой программы Windows,
которой из Git Bash передают путь Linux (`wsl`, `docker`, `scp` с удалённым путём).
