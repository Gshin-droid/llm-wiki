# Поиск уязвимостей: инструменты и что каждый из них не видит

Действующий свод: чем проверять свой код на дыры, в каком порядке и как читать отчёты. Собран
19.08.2026 после первого настоящего прогона сканеров по личному проекту (REST API на FastAPI +
React + Expo) — цифры ниже не из статьи, а из этого прогона.

Соседние страницы: [[vibecoding-app-security]] — *какие* бывают дыры и как проверить их руками;
[[ai-security-by-design]] — безопасность самого агента; эта — *чем* искать машинно.

## Пять классов инструментов

Каждый класс видит свой слой. Они не заменяют друг друга и почти не пересекаются.

| Класс | Что проверяет | Чем | Установка |
|---|---|---|---|
| **SCA** (состав ПО) | чужие библиотеки: нет ли в этой версии известной дыры | `npm audit`; для Python — база **OSV** (`api.osv.dev`) или `pip-audit` | npm audit встроен; OSV — HTTP-запрос, ключ не нужен |
| **SAST** (статический анализ) | свой код: опасные шаблоны, не запуская программу | `ruff --select S` (перенесённый в ruff **bandit**), глубже — `semgrep` | `uvx`, в систему не ставится |
| **Поиск секретов** | ключи и пароли в коде и в истории коммитов | `detect-secrets`, `gitleaks`; плюс `git log --all --name-only -- "*.env" "*.key"` | `uvx` / git |
| **DAST и фаззинг** | работающее приложение: что будет от кривого запроса | `schemathesis` (генерирует запросы по схеме OpenAPI), OWASP ZAP | `uvx` |
| **Сканер образов** | системные пакеты внутри контейнера и ошибки Dockerfile | `trivy` | через docker |

**Запускать через `uvx` (из состава `uv`), а не ставить.** `uvx имя-инструмента` разворачивает
инструмент во временном окружении и выбрасывает после работы. Ни одна проверка из прогона 19.08 не
потребовала установки в систему. Это снимает главное возражение против сканеров — «не хочу
захламлять машину ради одного запуска».

**Схема OpenAPI — бесплатный вход в фаззинг.** FastAPI (и любой фреймворк, отдающий OpenAPI)
публикует описание всех своих эндпоинтов. `schemathesis run http://localhost:8000/openapi.json` берёт
это описание и сам генерирует пограничные запросы к каждому. Ручного описания тестов не требуется
вообще — редкий случай, когда полезный инструмент включается одной строкой.

## Правило первое: метка severity ничего не говорит о твоём проекте

Метка (CRITICAL, HIGH) описывает **худший мыслимый способ использовать библиотеку**, а не твой.
Решает один вопрос: *дотягивается ли чужой человек до уязвимого кода по реальному пути*.

Из прогона 19.08, оба случая в одном проекте:

- Пакет с меткой **CRITICAL** оказался безопасен: дыра срабатывает при работе с асимметричными
  ключами, а приложение использует симметричный секрет и явный список разрешённых алгоритмов.
  Вектора нет по построению.
- Пакет с меткой **HIGH** оказался настоящей дырой: отказ в обслуживании через кривой
  `multipart/form-data`, эксплуатируется без авторизации, на эндпоинте загрузки файлов.

Проверять надо не метку, а три вещи: **(1)** вызывается ли уязвимая функция в нашем коде вообще;
**(2)** попадает ли в неё то, что прислал чужой человек; **(3)** нужен ли для этого аккаунт.

## Правило второе: шум — норма, разбирать его надо один раз

Прогон 19.08: **52 находки, реальна 1.** Соотношение примерно 50:1 — это не признак кривой
настройки, а обычная работа сканера.

Типовые источники шума, все встретились в одном прогоне:

- **Зависимости для сборки** (`postcss`, `nanoid` и подобное) — исполняются на машине разработчика,
  в браузер пользователя не попадают. Дыра в них угрожает сборочной машине, а не посетителю.
- **Транзитивные цепочки под другую платформу.** 16 находок из 25 в мобильной части вели к пакету,
  который исполняется только при сборке iOS-приложения на macOS. Починка требовала ломающего
  обновления фреймворка ради кода, который не выполняется никогда.
- **Дыра в функции, которую не вызываешь.** Библиотека чтения переменных окружения имела дефект в
  функции *записи*. Проект только читает.
- **SAST не понимает смысла.** Запрос, где f-строкой собираются только куски условий
  (`"date >= %s"`), а значения идут отдельным списком параметров, — это правильный
  параметризованный запрос. Линтер видит f-строку рядом со словом SELECT и срабатывает.
- **Намеренные заглушки.** `dev-secret-key-change-in-production` рядом с проверкой «в production
  такой ключ — отказ старта» распознаётся как захардкоженный пароль.

**Отсюда правило:** разобранный шум записывается в документ проекта поимённо, с объяснением по
каждому пункту. Следующий прогон читается **как разница с этим списком**, а не целиком. Кто читает
отчёт целиком каждый раз — через месяц перестаёт читать вообще, и это худший исход, чем не
запускать сканер вовсе: остаётся ощущение защищённости без защищённости.

## Правило третье: три класса дыр не ловит ни один инструмент

1. **Логика прав доступа (IDOR / BOLA).** Запрос без одного условия `AND user_id = ...` выглядит
   как совершенно обычный код. Сканер не отличит его от корректного никогда — у него нет понятия
   «чей это объект». Это **первое место** в обоих каталогах OWASP одновременно. Ловится ручным
   аудитом и тестами межпользовательской изоляции.
2. **Конфигурация, противоречащая сама себе.** Найдено 19.08 глазами, мимо всех пяти проверок:
   Dockerfile запускал сервер в режиме разработки с автоперезагрузкой, а compose рядом объявлял
   `ENV=production`. Каждый файл по отдельности корректен — проблема в их сочетании.
3. **Бизнес-логика.** Дорогая операция без ограничения частоты; последовательность действий,
   безобидная поодиночке и разрушительная в цикле.

Первый и третий классы — ровно то, что находит вдумчивое чтение кода человеком или моделью.
Отсюда порядок: **сканеры первыми** (дёшево, механически, за минуты), **ручной аудит вторым** (дорого,
но только он видит логику). Не наоборот и не вместо.

## Каталоги, по которым сверяться

Только первоисточники: списки пересматриваются, вторичные пересказы устаревают молча.

- **[OWASP API Security Top 10](https://owasp.org/API-Security/editions/2023/en/0x11-t10/)** —
  актуальная редакция **2023**, новой на август 2026 не выпущено. Для проекта, который отдаёт REST
  API, это главный список, а не общий Top 10. **Пять пунктов из первых шести — про права доступа:**
  `API1` (доступ к чужому объекту), `API2` (аутентификация), `API3` (доступ к чужим полям объекта),
  `API5` (доступ к чужим функциям). Отдельно `API4` — неограниченное потребление ресурсов, и `API6`
  — злоупотребление бизнес-сценарием.
- **[OWASP Top 10:2025](https://owasp.org/Top10/2025/)** — общий веб-список, вышел в 2025-м взамен
  редакции 2021 года. Что изменилось: `A01 Broken Access Control` удержал первое место и вобрал в
  себя SSRF; `A02 Security Misconfiguration` поднялась с пятого места на второе; `A03` из «уязвимых
  компонентов» превратилась в **Software Supply Chain Failures** — теперь это про всю цепочку,
  включая систему сборки и доставку; добавлена новая категория `A10 Mishandling of Exceptional
  Conditions` (необработанные ошибки, «падение в открытое состояние»); `A09` переименована в
  Security Logging **& Alerting** Failures — оповещение выделено намеренно.
- **[OWASP ASVS 5.0](https://owasp.org/www-project-application-security-verification-standard/)** —
  версия 5.0.0 от 30.05.2025. Не список рисков, а перечень конкретных требований с
  идентификаторами вида `1.2.5`. Нужен, когда вопрос звучит «что вообще должно быть проверено».
  По нему сверяются точечно, а не читают подряд.
- **[CWE Top 25 (2025)](https://cwe.mitre.org/top25/archive/2025/2025_cwe_top25.html)** — рейтинг
  MITRE по *типам дефектов*, а не по рискам. Работает как словарь: идентификаторы `CWE-…` стоят в
  отчёте почти любого сканера, по ним смотрят, что именно нашли.

Разделение простое: **OWASP Top 10 — риски** («что чаще всего ломают»), **CWE — дефекты** («как
именно это называется»), **ASVS — требования** («что должно быть сделано»).

## Что из этого стало правилом

- Перед разговором о безопасности проекта — сначала прогон сканеров, потом теория. Один прогон
  даёт список своих дыр; обзор без прогона даёт ощущение осведомлённости.
- Разобранный шум — часть документации проекта, а не черновик. Без него следующий прогон стоит
  столько же, сколько первый.
- Метка severity не приоритет. Приоритет — достижимость чужим человеком.
- Сканеры не отменяют чтения кода: класс дыр номер один в мире (права доступа) машинно не
  обнаруживается вовсе. Связано: [[claude-code-practices]], правило про cross-user isolation-тест
  на каждый ресурсный роутер.
