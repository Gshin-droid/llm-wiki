# Установка инструментов на Windows: четыре грабли

Живой документ. Актуально на 2026-09-11.

Первые три собраны из одной установки — PHP и Composer под новый проект 26.08.2026, —
четвёртый добавлен 11.09.2026. Все случаи многоразовые и бьют по любому инструменту,
а не только по тому, на котором их нашли. Общее у них одно:
**инструмент отчитывается об успехе, а работает не он или не там, где смотрят.**

## 1. Пакетный менеджер ссылается на чужой файл и ломается молча

`winget install php` не ставится **ни в одной версии** — 404 на каждой.

Причина не в сети и не в правах. Манифест winget хранит прямую ссылку на конкретную
сборку у поставщика. `php.net` держит на основном зеркале только текущие версии, а
старые переносит в архив (`downloads.php.net`) — ссылка в манифесте после этого мертва.
Свежая версия ещё не в манифесте, старая уже не по ссылке; рабочего пересечения нет.

**Класс задачи, а не единичный случай.** Так устроен любой менеджер, чей манифест —
ссылка на upstream без собственного зеркала: chocolatey, scoop, часть формул Homebrew.
Пока поставщик не трогает архив, всё работает; в день уборки ломается сразу вся история
версий, и виновата не ваша машина.

**Что делать:**

- проверить, есть ли у менеджера собственное зеркало файлов; нет — не рассчитывать на
  него в инструкции, которую кто-то повторит через полгода;
- ставить распаковкой архива из архивного каталога поставщика — это скучно, зато не
  зависит от чужой уборки;
- **не подбирать версию перебором.** Когда 404 приходит на вторую и третью версию
  подряд — дело не в версии. Перебор здесь стоит времени и ничего не выясняет.

## 2. PATH обновляется только для новых процессов

Установили, прописали в PATH, проверили в новом окне — работает. В открытом окне
соседней сессии та же команда отвечает «не найдено».

Windows выдаёт окружение процессу при запуске и потом не догоняет. Уже запущенные
терминалы, редакторы и сессии агента держат старую копию PATH до перезапуска.

**Симптом обманчив:** выглядит как «установка не удалась» или «пропало после
перезагрузки», хотя на диске всё на месте. Проверено 27.08: обходчик машины показывал
`php нет`, пока запись в PATH пользователя была на месте, а `php.exe` лежал по своему
пути и отвечал на прямой вызов.

**Правило:** прежде чем переустанавливать — перезапустить окно и вызвать по полному
пути. Если по полному пути работает, а по имени нет, вопрос не к установке, а к PATH.

## 3. Git Bash не видит `.bat`-обёрток

Установщик, который кладёт в PATH `tool.bat`, работает в PowerShell и в cmd, но не в
Git Bash: тот исполняемым файлом `.bat` не считает. Так вышло с Composer — в PowerShell
есть, в Git Bash «команда не найдена», хотя PATH один и тот же.

**Лечение:** положить рядом обёртку **без расширения** — обычный sh-скрипт, который
вызывает настоящий файл. Оба мира тогда видят команду под одним именем, и рецепты в
`justfile` не приходится писать в двух вариантах.

Заодно объясняет странность вида «в одном терминале команда есть, в другом нет» — до
того как начать искать в PATH различия, которых там нет.

## 4. Сессия агента в VS Code получает окружение Python соседнего проекта

**Симптом.** В окне VS Code, открытом на папке над всеми проектами, `python` в сессии
Claude Code запускает интерпретатор из `.venv` одного из проектов, и `VIRTUAL_ENV`
указывает туда же. В PATH пользователя и системы этого пути нет, профиля оболочки нет.

**Механизм — две штатные функции, каждая по отдельности разумна:**

1. Расширение Claude Code для VS Code настройкой `claudeCode.usePythonEnvironment`
   (по умолчанию включена) активирует для сессии окружение Python рабочей области.
   Описание в манифесте расширения (версия 2.1.267): *«Automatically activate the
   workspace's Python environment when running Claude»* — «при запуске Claude
   автоматически активировать окружение Python рабочей области».
2. Расширение Python Environments ищет окружения рабочей области по шаблонам `.venv` и
   `*/.venv` (настройка `python-envs.workspaceSearchPaths`). Если рабочая область —
   папка над проектами, под `*/.venv` попадает окружение первого подходящего проекта.

Вместе: в «окне над всеми» агент тихо работает в окружении одного проекта. Скрипт на
стандартной библиотеке запустится и так — опасен `pip install`, который уедет в чужое
окружение. Дефектом в трекере Claude Code это не значится, поведение штатное; соседняя
задача #92887 — о другом (настройка молча не срабатывает при `claudeCode.useTerminal`).

**Лечение** — выключить автоактивацию только для этой папки, в её `.vscode/settings.json`:
`"claudeCode.usePythonEnvironment": false`. Глобально выключать не нужно: в окне
отдельного проекта та же функция подключает окружение самого проекта, и это полезно.
Действует со следующего запуска сессии — окружение выдаётся процессу при старте (п. 2).

**Диагностика одной командой:** `$env:VIRTUAL_ENV` в сессии агента. Не пусто, а окно не
проектное — это оно.

## Что из этого правило

- **Установщик, который «не работает», сначала проверяется по полному пути.** Отвечает
  по пути, но не по имени — это PATH или оболочка, а не установка.
- **Повторяющийся 404 на разных версиях — признак мёртвой ссылки в манифесте**, а не
  неудачного выбора версии. Перебор прекращать после второго раза.
- **Путь есть в PATH процесса, но нет в PATH пользователя и системы — его подставил
  родитель:** редактор или его расширение. Искать в настройках родителя, а не в Windows.
- **Способ установки записывается рядом с проектом.** Не «поставили PHP», а «ставили
  распаковкой архива оттуда-то, потому что менеджер даёт 404» — иначе через полгода
  повторяется весь перебор.
