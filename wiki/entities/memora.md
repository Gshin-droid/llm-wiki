# Memora

MCP-сервер, дающий агенту постоянную память между сессиями. Попал в вики не как кандидат на установку, а как **чужая реализация той же рамки**, что разобрана в [[agent-memory-five-questions]] — и как разбор поучительной аварии.

**Тип:** инструмент (MCP-сервер памяти, открытый исходный код)
**Актуально на:** 2026-11-04

Хранение — SQLite локально, либо Cloudflare D1, либо S3/R2, либо HTTP-сервис в контейнере. **Допроверка 11-04 нашла архитектурный сдвиг (ветка 0.5.x, с 24.09):** SQLite может быть не просто альтернативой D1, а **первичным хранилищем с непрерывной репликацией в D1** («local SQLite primary with D1 replication») — отдельный репликатор, write-gate с журналом намерений, транзакционный `absorb`, операторские скрипты экспорта/отката/сверки; старый режим «D1 как единственный бэкенд» продолжает работать без изменений, переход на локальный primary — явный шаг оператора, не дефолт. **44 инструмента** в полном профиле (было 43 на 09-14 — рост от одного нового админ-тула `memory_import_sweep`, выпущенного в v0.4.5, не от общего пересчёта).

**Противоречие с записью 08-10 (допроверка 09-14): default эмбеддингов — не TF-IDF, а OpenAI.** README дословно: `` `openai` (default) | Included | High quality | API latency ``, и переменная `MEMORA_EMBEDDING_MODEL` тоже описана как «`openai` (default)». Страница с 08-10 утверждала обратное — «по умолчанию локальные (TF-IDF, без зависимостей)». Не установлено, был ли дефолт другим на 08-10 и сменился, или страница ошиблась изначально: raw-файл разбора 08-10 недоступен для перепроверки построчно. Практическое следствие меняется на обратное: **дефолтная установка Memora по умолчанию шлёт текст записей в OpenAI**, а не считает эмбеддинги локально. **Подтверждено повторно 11-04** — дефолт не отыграли назад: README по-прежнему называет `openai`/`text-embedding-3-small` дефолтной моделью эмбеддинга.

## Чем интересен

- **Цепочки замещения.** Запись не удаляется: новая версия связывается со старой через `supersedes`, история обходится запросом (`follow="full_history"`). Закрывает то, чего не хватало [[mem0]] после перехода на append-only.
- **`memory_absorb`** — запись через автоматическую дедупликацию, замещение и слияние фактов синтезом модели. Тот самый механизм, от которого Mem0 отказался как ненадёжного; страховка Memora в том, что замещённое не теряется.
- **Принципы из `SOUL.md`:** «предпочитать детерминированную агрегацию скрытой генерации повествования» и «сохранять идентификаторы исходных записей, чтобы вызывающий мог проверить сводки» — второе дословно совпадает с правилом «якорь к источнику» в `CLAUDE.md` этой вики.
- **Одна система памяти, а не две.** Весь `CLAUDE.md` проекта — 248 байт: Memora единственная память, встроенную auto-memory Claude Code не использовать.

## Чего стоит опасаться

- **Не библиотека, а расширение агента:** несёт скилл, плагин Claude Code с `marketplace.json` и `install.sh`. Категория с известной статистикой рисков — см. [[ai-security-by-design]]. Установочный скрипт исполняется до того, как его прочитали.
- **README вписывает `CLOUDFLARE_API_TOKEN` прямо в `.mcp.json`** — файл обычно лежит в репозитории проекта. Секрет уедет в git первым же коммитом. **Уточнение 11-04:** README сам же описывает отдельный, безопасный путь — Container Deployment, где credentials «never enter the image, the instance file, or the workspace's HTTP config» и читаются из отдельного файла — но примеры конфигурации D1 и Cloud Graph в том же README продолжают пользоваться опасным путём, и документация не сводит два подхода воедино явно.
- **Установка из `main` без фиксации версии** (`pip install git+...`). Тег «Latest» на странице релизов GitHub (`v0.5.5`) сам устарел — фактический верх по `CHANGELOG.md` на 11-04 — `v0.5.7.6`; ставить с проверкой `CHANGELOG.md`, не доверяя одному тегу.
- **Найдено 09-14: дефолт отправляет текст записей в OpenAI.** Если не менять `MEMORA_EMBEDDING_MODEL` явно, каждая запись памяти уходит на эмбеддинг во внешний API — риск того же рода, что и `CLOUDFLARE_API_TOKEN` в README, но не про секрет, а про сам контент памяти.
- **Один фактический промах уже найден:** причина собственной аварии в релизных заметках названа неверно либо устарела — см. «Противоречия» в [[memora-agent-memory-mcp]] и [[openrouter]].

## Допроверка 2026-09-14 (ежедневный процесс закрытия пробелов)

Первая содержательная сверка с момента разбора (08-10 → сейчас, 35 дней) — пункт числился в очереди просроченных «Актуально на» с приоритетом (09-13, воскресный проход: `memora` и `openrouter` ни разу не проверялись по первоисточнику). `memora.ai` не проверялся — `github.com/agentic-box/memora` (README + теги + страница репозитория) прочитан напрямую, без блокировки.

Кроме противоречия по дефолту эмбеддингов (вынесено выше) и роста версии/звёзд — новые фичи, которых на странице не было вовсе: **tool profiles** (`full`/`leader`/`agent` — 43/19/12 инструментов, снижение токена схемы тула для агентов, которым не нужен полный набор), **Live Graph Server** (SSE, интерактивная визуализация графа памяти), **Cloud Graph** (тот же граф, хостится на Cloudflare Pages), **Memory Insights** (обнаружение устаревших записей, предложения консолидации), интеграция с Neovim через Telescope. Ни changelog, ни migration guide в README нет — что именно из этого появилось после 08-10, а что уже было и не попало на страницу тогда, не установлено.

## Допроверка 2026-11-04 (ежедневный процесс закрытия пробелов)

Повторное истечение порога «Актуально на» (09-14 → сейчас, 51 день), первая содержательная сверка с прошлой допроверки. `memora.ai` не проверялся — README репозитория (`raw.githubusercontent.com`), страница репозитория, страница релизов GitHub и — новое по сравнению с 09-14 — `CHANGELOG.md` прочитаны напрямую.

**Исправление собственного вывода 09-14: changelog теперь есть, и он расходится со страницей релизов GitHub.** `CHANGELOG.md` существует и ведётся дисциплинированно (построчно, newest-first, версии вплоть до патчей четвёртого уровня — `0.5.7.6`). Страница GitHub Releases при этом показывает «Latest» **v0.5.5** (24.09) — она не содержит минорных релизов 0.5.6–0.5.7.6 (17–21.10), то есть сама метка «Latest» на странице релизов устарела и вводит в заблуждение, если проверять только её. Тот же урок, что уже был на [[opencode]] (разъехавшиеся линии тегов) — у проекта может быть две поверхности версионирования, несинхронные между собой; доверять надо той, что детальнее (`CHANGELOG.md`), а не короче (`Releases`).

**Главная содержательная находка — архитектурный сдвиг веткой 0.5.x (с 24.09, «multi-database» сменилась на «local SQLite primary with D1 replication»):** SQLite из простой альтернативы Cloudflare D1 стала возможным **первичным хранилищем**, которое непрерывно реплицируется в D1 как зеркало — не наоборот. Механизм: репликатор шлёт изменения через outbox-таблицу как allow-listed upsert/delete с учётом foreign keys, строки помечаются отправленными только после подтверждения D1; журнал намерений логирует каждую запись в D1 до отправки; `absorb` на локальном хранилище — одна транзакция (БД), вызовы LLM/эмбеддинга/изображений — вне блокировки записи; есть операторские скрипты экспорта/сева/откатов/сверки и отдельный раннер cutover с полной сверкой перед переключением хранилища. D1-зависимые деплои продолжают работать без изменений — переход на локальный primary явный шаг оператора, не дефолт и не breaking change. Отдельно, тем же релизом: identity эмбеддинга больше не включает хост эндпоинта — перенос сервера эмбеддингов больше не вызывает полный ребилд (чинит ровно тот класс проблем, что уже раз привёл к аварии 0.3.0, см. источник).

**Вторая находка — v0.4.5–0.4.6 убрала эвристику автоопределения проекта по ключевым словам.** Раньше память могла быть молча приписана проекту по совпадению слов в тексте; теперь проект определяется только явно — аргументом `project`, `metadata.project` или единственным сконфигурированным тегом через новую переменную `MEMORA_PROJECTS`. Без неё проект не выводится из тегов вовсе. Это ровно то же направление, что и принцип `SOUL.md` «детерминированная агрегация вместо скрытой генерации» (раздел «Чем интересен» выше), применённое к ещё одному месту программы, где раньше угадывали. Этим же релизом тул-каунт вырос до **44** — не общий пересчёт, а один новый админ-тул `memory_import_sweep`, убирающий недописанные строки после прерванного импорта.

**Третья находка — Phase 0 JSON API, отдельный от MCP.** Релиз v0.4.6 добавил плоский JSON API (`/api/v1/<store>/...`: health/search/absorb) как первую фазу отдельного демона `clmux`; контракт зафиксирован как `memora-api/v1 1.0.0`. `search` — только чтение; `absorb` через API пока возвращает 501 (ни одно хранилище не поддерживает транзакционную запись через этот путь). API выключен, если не задана `MEMORA_API_TOKENS_FILE` — у `memora-all` она не задана, то есть эти роуты по умолчанию недоступны (404). Второй, не MCP-шный способ говорить с Memora — пока только для чтения.

Детали и источники — выше по тексту страницы (таблица «Факты», «Чего стоит опасаться»); правки внесены без удаления записи 09-14. Деталь на уровне источника/ошибки аварии 0.3.0 не затронута этой допроверкой.

## Решение по этой вики (2026-08-10)

**Не ставим.** Вика сама и есть слой памяти — в markdown, в git, читаемая человеком. Memora решает задачу для агентов, чья память непрозрачна: разложить её и дать спрашивать. У нас задача обратная — не дать прозрачным страницам разойтись с сырьём, и на неё Memora не отвечает. Плюс постоянный контекстный налог 22 описаний инструментов на каждую сессию.

Решение отложенное, а не закрытое: порог тот же, что у всей темы памяти, — появление второго писателя-человека или второй машины. (Токенный налог полного профиля вырос до 44 инструментов — 11-04; профиль `agent`, 12 инструментов, снял бы часть налога, но решение не поставлено вообще, вопрос не проверялся отдельно.)
