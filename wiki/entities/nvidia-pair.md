# NVIDIA PAIR (Personal AI Router)

Бесплатная открытая программа NVIDIA, раздающая запросы к локальным моделям между машинами одной сети. Попала в вики как первый инструмент, делающий локальный вывод **сетевым ресурсом**, а не свойством одной машины.

**Тип:** инструмент (маршрутизатор локального инференса)
**Актуально на:** 2026-09-24
**Версия:** публичная бета, **0.1.5** по CHANGELOG.md репозитория (допроверка 09-24; на 09-22 знали только v0.1.1 по вторичной выдаче), анонс 03.09.2026 на IFA
**Репозиторий:** `github.com/NVIDIA/Personal-AI-Router` (ветка `develop`) · **Лицензия:** Apache 2.0 — подтверждена дословно допроверкой 09-24

## Маршрутизатор, а не кластер

Каждый запрос исполняется **целиком на одном узле**. PAIR не делит запрос между видеокартами и не объединяет их видеопамять — формулировка технического блога NVIDIA дословна: *«PAIR does not split requests across multiple GPUs or merge VRAM»*. Потолок размера модели задаёт самая мощная одиночная карта в сети, и второй машиной он не поднимается. Выигрыш — параллельность задач: пока один агент занял одну машину, следующий уходит на свободную.

Сам вывод PAIR не делает: модели исполняют **Ollama** или **LM Studio**, PAIR обнаруживает узлы, следит за готовностью, ставит задачи и возвращает ответы.

## Как выбирает узел

Готовность узла → наличие на нём движка вывода → **наличие запрошенной модели именно на этом узле** → текущая загрузка GPU. Одинаковый набор моделей на всех машинах не нужен, но запрос уйдёт только туда, где модель уже скачана.

**Допроверка 09-24 (`docs/architecture.mdx`): выбор устроен как упорядоченный список failover, не как одна попытка.** Порядок кандидатов: узел, закреплённый вручную через терминальный интерфейс → приоритет планировщика (нагрузка GPU переводится в «давление» 0–3 по порогам 40/70/85%, сортировка «очередь → давление → ID узла») → остальные по стабильному ID. Отказ различается по типу: `404` от узла — повторяемая ошибка, запрос уходит следующему по списку; `400`/`422` — не повторяются, потому что упадут везде одинаково; протухший из инвентаря узел отвечает локальным `502` без обращения к движку. Своего резерва каждый прокси добавляет к оценке нагрузки **ещё до отправки** запроса — поэтому всплеск запросов расходится по узлам сам. Начатый запрос при этом никуда не переносится: *«one request goes to one node and the proxy never splits it»*.

## Подключение

Выдаёт **Ollama-совместимую и LM Studio-совместимую** точку входа: в приложении меняется только базовый URL, нового API нет. Допроверка 09-24 нашла третий режим, о котором страница не знала: README называет ещё и точку входа, **совместимую с Anthropic Messages API** — предметно не проверялась (заголовки, ограничения), практического значения пока нет, поскольку сам вывод всё равно идёт через локальные Ollama/LM Studio, а не через Claude.

Узлы — Windows с GeForce RTX (серия 20+), DGX Spark/GB10, Mac M4+, Linux с RTX. От 8 ГБ ОЗУ, 20+ ГБ на диске. Интернет нужен только для скачивания моделей. Конфигурация узлов — не файл, а интерфейс: спаривание через приложение (`Settings → Cluster`) шестизначным PIN, параметры отдельного узла — через `Engine settings`.

Безопасность: обнаружение по mDNS, спаривание подтверждается человеком, трафик между узлами шифруется mTLS и не покидает локальную сеть.

## Границы применимости

- **Только одна локальная сеть** — обнаружение идёт по mDNS, машины в разных сетях PAIR не объединит.
- Строго последовательные задачи и один длинный запрос выигрыша почти не дают — признано авторами.
- Не увеличивает доступную видеопамять.
- Бета «специфична к конфигурации»: набор проверенных сочетаний железа и ОС ограничен.
