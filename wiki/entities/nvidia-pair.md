# NVIDIA PAIR (Personal AI Router)

Бесплатная открытая программа NVIDIA, раздающая запросы к локальным моделям между машинами одной сети. Попала в вики как первый инструмент, делающий локальный вывод **сетевым ресурсом**, а не свойством одной машины.

**Тип:** инструмент (маршрутизатор локального инференса)
**Актуально на:** 2026-11-16
**Версия:** вышла из публичной беты — релиз **1.0.0**, сейчас **1.0.23** по CHANGELOG.md репозитория (допроверка 11-16; на 09-24 знали только 0.1.5), анонс беты 03.09.2026 на IFA
**Репозиторий:** `github.com/NVIDIA/Personal-AI-Router` (ветка `develop`) · **Лицензия:** Apache 2.0 — подтверждена повторно допроверкой 11-16 · звёзды 1,8к, форки 305, открытых issues 39 (допроверка 11-16, раньше не отслеживались)

## Маршрутизатор, а не кластер

Каждый запрос исполняется **целиком на одном узле**. PAIR не делит запрос между видеокартами и не объединяет их видеопамять — формулировка технического блога NVIDIA дословна: *«PAIR does not split requests across multiple GPUs or merge VRAM»*. Потолок размера модели задаёт самая мощная одиночная карта в сети, и второй машиной он не поднимается. Выигрыш — параллельность задач: пока один агент занял одну машину, следующий уходит на свободную.

Сам вывод PAIR не делает: модели исполняют движки-исполнители, PAIR обнаруживает узлы, следит за готовностью, ставит задачи и возвращает ответы. На допроверку 09-24 исполнителей было два (Ollama, LM Studio); допроверка 11-16 нашла два новых, добавленных релизами между ними — **llama.cpp** (0.1.11) и **vLLM** (1.0.15, только Linux с видеокартой NVIDIA или Apple Silicon macOS, на Windows не предлагается).

## Как выбирает узел

Готовность узла → наличие на нём движка вывода → **наличие запрошенной модели именно на этом узле** → текущая загрузка GPU. Одинаковый набор моделей на всех машинах не нужен, но запрос уйдёт только туда, где модель уже скачана.

**Допроверка 09-24 (`docs/architecture.mdx`): выбор устроен как упорядоченный список failover, не как одна попытка.** Порядок кандидатов: узел, закреплённый вручную через терминальный интерфейс → приоритет планировщика (нагрузка GPU переводится в «давление» 0–3 по порогам 40/70/85%, сортировка «очередь → давление → ID узла») → остальные по стабильному ID. Отказ различается по типу: `404` от узла — повторяемая ошибка, запрос уходит следующему по списку; `400`/`422` — не повторяются, потому что упадут везде одинаково; протухший из инвентаря узел отвечает локальным `502` без обращения к движку. Своего резерва каждый прокси добавляет к оценке нагрузки **ещё до отправки** запроса — поэтому всплеск запросов расходится по узлам сам. Начатый запрос при этом никуда не переносится: *«one request goes to one node and the proxy never splits it»*.

**Допроверка 11-16: планировщик видит нагрузку, а не возможности узла — официально признанный предел, не находка расхождения.** `docs/known-issues.mdx` дословно: единственная политика планирования ранжирует узлы по уже стоящей в очереди работе и грубой загрузке GPU, не учитывая модель видеокарты, свободную память, измеренную задержку, загружена ли модель уже в память, или «дороговизну» запроса; телеметрия старше 10 секунд считается средней загрузкой, а не простоем. На кластере из похожих машин это работает разумно, на смешанном — одинаковый процент загрузки означает разное на маленькой и большой карте, и работа может уйти на более медленную машину. Отдельно (релиз 1.0.17) — кандидат, не ответивший первым байтом в дедлайн, на один дедлайн задвигается в конец списка, не исключается навсегда.

## Подключение

Выдаёт точки входа, совместимые с **Ollama**, **OpenAI** и **Anthropic Messages API**: в приложении меняется только базовый URL, нового API нет. Допроверка 09-24 нашла режим Anthropic Messages, но не смогла проверить его предметно; **допроверка 11-16 закрывает этот вопрос прямой цитатой CHANGELOG.md (релиз 0.1.3)** — запросы на `/v1/messages` маршрутизируются к владельцу запрошенной модели точно так же, как любой другой метод инференса, отдельного ограничения или урезанной функциональности у этого пути нет.

**Допроверка 11-16: требования к узлам пересобраны — общая платформа PAIR отделена от требований движка.** Прежняя формулировка («Windows с GeForce RTX серии 20+, DGX Spark/GB10, Mac M4+, Linux с RTX») смешивала два разных уровня; официальная таблица README их развела. Сам **PAIR** идёт на любой из трёх ОС (Windows 11, Linux, macOS), архитектуры x64 и arm64 (Windows on ARM — экспериментально), узлы разных ОС свободно собираются в один кластер. А вот какой **движок** потянет машина — решается отдельно для каждого движка и каждой модели: «PAIR running on a machine does not mean an engine will» — у Ollama/LM Studio/llama.cpp/vLLM свои требования к ОС, GPU и драйверам, и проверять их нужно по документации самого движка, не по общей таблице PAIR. Прежние цифры (8 ГБ ОЗУ, 20+ ГБ на диске) README одной строкой не повторяет — по всей видимости, относились к конкретному движку, не к PAIR как таковому; не переоткрывается отдельным пунктом, стоит того же класса неопределённости, что и раньше. Интернет нужен только для скачивания моделей — без изменений. Конфигурация узлов — не файл, а интерфейс: спаривание через приложение (`Settings → Cluster`) шестизначным PIN, параметры отдельного узла — через `Engine settings`.

Безопасность: обнаружение по mDNS, спаривание подтверждается человеком, трафик между узлами шифруется mTLS и не покидает локальную сеть. **Допроверка 11-16:** релиз 1.0.23 (последняя запись CHANGELOG.md на дату сверки) ужесточил эту модель — PAIR теперь проверяет (authenticate) обнаруженный по mDNS список узлов до того, как использует их заявленные идентичность, эндпоинты, модели или замеры железа для решений о маршрутизации; устаревшее состояние узла после смены доверия отзывается, а не просто помечается свежим кэшем. Дословной формулировки, что именно проверялось до этого релиза (то есть какой конкретно риск закрыт), CHANGELOG не даёт — заголовок релиза говорит только о направлении изменения, не о прежней дыре; как факт в вики идёт то, что подтверждено текстом, не домысленный сценарий атаки.

## Границы применимости

- **Только одна локальная сеть** — обнаружение идёт по mDNS, машины в разных сетях PAIR не объединит; интеграция с Tailscale стоит в roadmap невыполненным пунктом (допроверка 11-16).
- Строго последовательные задачи и один длинный запрос выигрыша почти не дают — признано авторами.
- Не увеличивает доступную видеопамять.
- ~~Бета «специфична к конфигурации»~~ — снято допроверкой 11-16: проект вышел из беты релизом 1.0.0, сейчас 1.0.23, пункт больше не актуален.
- **Допроверка 11-16, официально признанные пределы (`docs/known-issues.mdx`):** на системах с unified memory (кроме Grace Blackwell/DGX Spark, где обработано намеренно) показания видеопамяти в интерфейсе врут или пропадают — влияет только на отображение, не на маршрутизацию (планировщик вообще не смотрит на VRAM, только на очередь и загрузку); PAIR не обнаруживает «зависшую», но живую на вид службу — лечится перезапуском; на macOS без кластера узел может перестать отвечать на LAN-подключения после долгого простоя.

## Дополнение (2026-11-02): рядом в ландшафте — [[strata]], другой паттерн

PAIR делит задачи **между машинами** одной сети, не деля видеопамять одной модели. [[strata]] решает обратную задачу — **одну** большую MoE-модель (Qwen3.8-Flash-Next) засунуть в **одну** видеокарту потребительского класса через offloading в RAM/SSD, без сети между машинами вовсе. У обоих — OpenAI-совместимая точка входа и Anthropic Messages-совместимый эндпоинт: у PAIR он подтверждён предметно допроверкой 11-16 (см. раздел «Подключение» выше), у Strata — через `ANTHROPIC_BASE_URL`.
