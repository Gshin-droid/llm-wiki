# Zep / Graphiti

**Тип:** инструмент (temporal knowledge graph)
**Актуально на:** 2026-09-21

## Что это
Zep построен поверх open-source движка Graphiti — граф, где каждый факт-ребро имеет `valid_from`/`valid_until`/`recorded_at`. Позволяет отвечать на временные вопросы ("где жил пользователь полгода назад") через graph traversal — то, чего Mem0 структурно не умеет.

## Цена архитектурной мощи
Тяжёлый multi-pass extraction (десятки тысяч токенов на разговор), retrieval сразу после ingest может не находить только что добавленный факт (фоновая обработка графа), заметная latency на мульти-хоп запросах.

## Когда уместен
Длинные разговоры с меняющимися во времени фактами: финансовые ассистенты, юридические агенты, домены с сильной temporal-семантикой.

## Наблюдение
Публичная "бенчмарк-война" с Mem0 (LOCOMO benchmark, взаимные пересчёты цифр в issue-трекерах, а не peer-review) — показатель того, что индустрия memory-фреймворков ещё очень молода и маркетинговым цифрам стоит не доверять без проверки.

## Дополнение (2026-08-07, [[berezhnitsky-agent-memory-lies]]): закрытие записи датой и ещё один собственный бенчмарк

**Механика устаревания названа явно.** Graphiti старую запись не удаляет, а закрывает с нужной даты — история остаётся на месте, и можно спросить, какие правила действовали в марте прошлого года. Это ответ на дыру, оставшуюся у [[mem0]] после перехода на append-only: добавление сохраняет обе версии факта, но не говорит, какая верна сейчас; закрытие датой говорит.

**Ещё одна цифра — и ровно тот случай, о котором предупреждает «Наблюдение» выше.** На собственном бенчмарке Zep подход «старое сжимается в пересказ, а пересказ в пересказ» отвечал верно примерно на треть вопросов, память с фактами при источниках и без повторного пережатия — около 95%. Замер и продукт-победитель принадлежат одному владельцу; автор источника это оговаривает и утверждает, что направление совпадает с независимыми работами, но ссылок не даёт. Брать как порядок величины и иллюстрацию механизма (петля пересказа портит факты), а не как измеренное преимущество продукта. Механизм разобран в [[agent-memory-five-questions]], вопрос 4.

## Допроверка 2026-08-09 (ежедневный процесс закрытия пробелов): частично устарело — у Mem0 теперь тоже есть temporal-слой

Строки выше («то, чего Mem0 структурно не умеет», «дыра, оставшаяся у [[mem0]] после перехода на append-only: … не говорит, какая версия верна сейчас») были верны на момент записи, но официальный README `mem0ai/mem0` объявляет с апреля 2026 **Temporal Reasoning** — time-aware retrieval, которая при запросе ранжирует нужную по времени версию факта. Механизм не graph traversal с явными `valid_from`/`valid_until`, как у Graphiti (это подтверждению не поддавалось — README раскрывает Mem0-часть, не внутреннюю механику), поэтому не противоречие "кто лучше", а сужение зазора: раньше это была задача, которую решал только Zep/Graphiti, теперь Mem0 тоже отвечает на неё, пусть и другим механизмом. Подробности и оговорка про managed-платформу — [[mem0]], раздел "Допроверка 2026-08-09".

## Допроверка 2026-09-21 (ежедневный процесс закрытия пробелов)

Повторное истечение 30-дневного порога (08-09 → сейчас, 43 дня) — первая содержательная сверка раздела «Что это» с моментом ingest, не только переустановка даты. `getzep.com`/`docs.getzep.com` не проверялись отдельно (не первоисточник этой страницы и раньше). Официальный `github.com/getzep/graphiti` — README и код прочитаны напрямую через `raw.githubusercontent.com` (`WebFetch`; прямой `curl`/`git clone` отклонён разрешениями окружения).

**Механизм подтверждён, конкретные имена полей — нет.** README описывает то же самое ("each fact... has a validity window: when it became true, and when... it was superseded") без указания имён атрибутов. Проверено по коду напрямую (`graphiti_core/edges.py`, класс `EntityEdge`): реальные temporal-поля — `created_at`, `valid_at`, `invalid_at`, `expired_at`, `reference_time`.

**Противоречие с записью раздела «Что это»: имена полей не `valid_from`/`valid_until`/`recorded_at`.** Страница с момента создания утверждает именно эти три имени — в актуальном коде репозитория таких атрибутов нет вообще (ни `valid_from`, ни `valid_until`, ни `recorded_at`); ближайшие по смыслу — `valid_at`/`invalid_at`/`created_at`. Не установлено, изменились ли имена полей с момента, когда собирался исходный источник ([[shubin-llm-memory-landscape]]), или страница изначально записала их неточно (raw-файл для этой части не даёт построчной проверки). Сам механизм (открытый интервал действия факта, старое не удаляется) — верен, расхождение только в именах атрибутов.

Не подтверждено и не опровергнуто этим источником: «Тяжёлый multi-pass extraction» из раздела «Цена архитектурной мощи» — README не детализирует внутренний пайплайн LLM-вызовов, вопрос остаётся открытым отдельно от этой допроверки.

Новое, чего страница не знала: звёзды репозитория **31.0k**. Версия/тег последнего релиза фетчером не отдана в текстовом виде — не установлено.

## Допроверка 2026-09-22 (ежедневный процесс закрытия пробелов): происхождение неверных имён полей установлено

Продолжение вчерашней сверки — куда взялись `valid_from`/`valid_until`/`recorded_at`. Три независимые проверки:

1. **Raw-файл источника содержит эти имена дословно.** `raw/web-clipped/.../У ChatGPT и Claude уже есть память.md` (источник [[shubin-llm-memory-landscape]]) прямым текстом: «каждый факт — ребро с обязательными полями `valid_from`, `valid_until`, `recorded_at`». Страница вики не придумала имена и не исказила их при ингесте — она дословно унаследовала их от собственного источника. Прошлая запись (09-21) ошибочно решила, что «raw-файл не даёт построчной проверки» — файл был, его не перечитали.
2. **`recorded_at` не существовало в репозитории Graphiti никогда.** Поиск по истории коммитов (`github.com/search?type=commits`) по строке `recorded_at` в `getzep/graphiti` — **0 результатов** за всю историю репозитория.
3. **`valid_from`/`valid_to` существовали, но были в процессе удаления уже в августе 2024** — за 21 месяц до публикации источника (04.05.2026). Коммит `fix: Address graph disconnect (#7)`, 19.08.2024, убирает выставление `valid_to`/`valid_from` на шаге извлечения рёбер в пользу отдельной фазы инвалидации. Прямая проверка тега `v0.3.0` (ранний релиз) через `raw.githubusercontent.com/getzep/graphiti/v0.3.0/graphiti_core/edges.py` показывает уже тот же набор полей, что и сейчас — `created_at`/`valid_at`/`invalid_at`/`expired_at` (плюс `reference_time` появился позже) — без `valid_from`/`valid_until`/`recorded_at` вообще.

**Вывод: не расхождение "документация обогнала вики", а собственная неточность источника [[shubin-llm-memory-landscape]].** Habr-статья описала внутренности Graphiti терминами, которые либо были упразднены за полтора года до публикации поста (`valid_from`/`valid_to`), либо не существовали в коде никогда (`recorded_at`) — похоже на иллюстративное пересказывание механики своими словами, выданное за конкретные имена атрибутов. Сам механизм (открытый интервал действия факта, ничего не удаляется) у источника верен — это подтвердила ещё вчерашняя сверка. Страница не переписывается: раздел «Что это» остаётся с исходной (неточной) терминологией по правилу «не удалять без причины», расхождение зафиксировано здесь и в допроверке 09-21.
