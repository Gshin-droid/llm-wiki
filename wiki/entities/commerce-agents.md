# Commerce Agents

Официальный открытый эталонный блюпринт Anthropic для торговых агентов: пара агентов (шоппинг для покупателя, мерчант для персонала), один раз определённая и запускаемая на трёх рантаймах.

**Тип:** инструмент (открытый reference blueprint, Apache License 2.0, не поддерживается автором для контрибьюций)
**Актуально на:** 2026-09-08

## Что это

`github.com/anthropics/commerce-agents` — не cookbook и не документация продукта, а полноценный референсный проект с двумя ролями:
- **Shopping agent** — поиск и сравнение товаров, планирование покупки, корзина, чекаут, память о клиенте (Messages API-путь), ответы на вопросы о заказе/политике.
- **Merchant agent** — объяснение метрик, ведение листингов, реакция на алерты по остаткам/заказам, ценообразование и промо, черновики кампаний. Каждая запись — staged change, требующая одобрения человека.

Каждая роль определена один раз (промпт, скиллы, контракты тулов, гейты в `commerce-common/` + role-specific `core/`) и исполняется на трёх независимых рантаймах через тонкие адаптеры: Messages API (эталонная реализация turn loop), [[claude-agent-sdk|Claude Agent SDK]] (консольный интерфейс, SDK сам ведёт цикл хода) и [[claude-managed-agents|Managed Agents]] (хостед-агент, обращающийся к своему MCP-серверу). Четыре готовые вертикали (retail/ACME, travel/ACME Travel, telecom/ACME Mobile, entertainment/ACME Tickets) показывают одну и ту же пару агентов на разных доменах через расширяемый `PresentationExtension`, не форк кода.

## Safety-паттерн: гейты в исполнителе тула, а не в промпте

Ключевое архитектурное решение, зафиксированное `docs/safety.md`: правило, встроенное в вызов тула (`commerce_common/execution.py` + role-specific `executor.py`), держится одинаково на всех трёх рантаймах — потому что все три исполняют тулы через один и тот же исполнитель. Правило, живущее в рантайме (grounding, лимиты анализа, извлечение памяти), таким гарантиям не подчиняется и требует отдельной проверки на каждом пути.

Четыре гейта в коде: **fencing** (сторонний текст санитизируется и оборачивается фиксированной меткой до того, как модель его увидит), **cart/staging provenance** (запись принимает только id, которые сама сессия вернула инструментом ранее — модель не может сослаться на несуществующий товар/листинг), **host approval gate** (запись мерчанта проходит только по явной пометке approved от человека через портал/SDK-консоль — ни превью-карточка, ни «одобряю» в чате разрешения не дают). Подробности и точные цитаты — [[claude-commerce-agents-blueprint]].

## Место среди уже разобранных паттернов

Прямая параллель, но с обратным знаком, [[claude-cookbook-scheduled-repository-reviewer]] (09-07): там read-only агент лишён канала эксфильтрации в принципе («nowhere to go but the reply itself»); здесь у агента канал записи есть (мерчант меняет цены), но исполнить запись без прохождения origination-проверки и человеческого одобрения он не может — тот же принцип «канал есть, заперт независимой проверкой», примененный к write-стороне.

Также параллель к [[claude-managed-agents]]: та страница описывает типичный путь «прототип на Agent SDK → продакшн на Managed Agents» как последовательную миграцию с одного рантайма на другой; здесь показана альтернатива — держать оба рантайма (плюс Messages API) одновременно на общем ядре, не мигрируя.
