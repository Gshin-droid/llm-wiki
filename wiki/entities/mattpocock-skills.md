## Что это

Набор скиллов «прямо из моей `.agents`-директории», как формулирует сам автор. Не фреймворк с рантаймом, а именно набор коротких markdown-инструкций, вокруг которого сложился пайплайн разработки. ## Пайплайн из четырёх шагов

Основная ценность — не отдельные скиллы, а порядок:

1. **`grilling` / `grill-me`** — агент допрашивает пользователя по каждой ветке дерева решений, пока не достигнуто взаимопонимание. Явная оговорка внутри скилла: если факт можно установить, изучив окружение, — искать самому, а не спрашивать. Закрывает главный источник брака — модель не поняла, что от неё хотят.
2. **`to-spec`** — превращает транскрипт опроса в спецификацию. Ничего не спрашивает, только оформляет уже известное.
3. **`to-tickets`** — нарезает спецификацию на тикеты методом **tracer bullet**: каждый тикет — узкий, но полный вертикальный срез через все слои (схема, API, UI, тесты), демонстрируемый сам по себе и размером ровно в одно контекстное окно. Каждый тикет объявляет свои blocking edges — какие тикеты должны завершиться раньше.
4. **`implement`** — запускает разработку по тикету, внутри ссылается на `tdd` и `code-review`.

**`wayfinder`** (свежее дополнение) — для работы, которая не помещается в одну сессию: пишет не все тикеты сразу, а карту решений; тикет здесь разрешает *решение*, а не исполняет срез сборки.

## Что есть в исходнике, но не попало во вторичный пересказ

**Исключение для широких рефакторов.** `to-tickets/SKILL.md` прямо оговаривает: механическая правка с большим blast radius (переименовать колонку, сменить тип общего символа) в вертикальный срез не лезет — ни один срез не встанет «зелёным». Для таких случаев предписана схема **expand–contract**: добавить новую форму рядом со старой → мигрировать вызовы пачками (каждая пачка — свой тикет, блокируемый expand) → удалить старую форму тикетом, блокируемым всеми пачками. Если даже пачки не держат зелёный поодиночке — общая интеграционная ветка и финальный тикет integrate-and-verify.

Это существенно, потому что именно на широких рефакторах правило «каждый тикет — готовая фича» ломается, и автор это предусмотрел. В пересказе [[nickvels-mattpocock-pipeline]] оговорки нет.

**Ручной запуск — заявленный дизайн, а не недоработка.** У `to-tickets` и `wayfinder` во frontmatter стоит `disable-model-invocation: true` — скиллы принципиально не подключаются автоматически. «Слабое место», о котором говорит вторичный источник, — осознанная позиция автора: пак сделан инженером для инженеров, каждый тикет предполагается прочитать глазами.

## Содержательный тезис: убирать рамки, а не ставить

Скиллы намеренно короткие. Логика (из пересказа, подтверждается объёмом файлов): огромные промпты и толстые фреймворки писались под слабые модели, которые надо было загонять в рамки. Современным моделям рамки, наоборот, мешают — работает порядок операций, а не объём инструкций. Прямое противопоставление тяжёлым фреймворкам полного SDLC — см. [[agentic-sdlc-frameworks]].

## Установка (как сделано у пользователя)

**Установлен 2026-07-27**, user scope, через **нативный плагин-механизм Claude Code**, а не через `npx skills add mattpocock/skills`:

```
claude plugin marketplace add mattpocock/skills
claude plugin install mattpocock-skills@mattpocock
```

Причина выбора (правило 12б в [[claude-code-practices]]): npm-пакет `skills` принадлежит **не Пококу**, а `vercel-labs` (мейнтейнер `rauchg` — Guillermo Rauch, CEO Vercel). Источник сам по себе приличный, но это лишнее звено в цепочке поставок, о котором вторичный источник не упоминает. Плагин-путь короче на одну сторону и показывает манифест целиком.

**Проверка после установки:** `claude plugin details` — 22 скилла, **0 агентов, 0 хуков, 0 MCP-серверов**, то есть исполняемой поверхности нет вообще. Стоимость: ~~~1 419 токенов always-on~~ — **цифра устарела, см. «Уточнение стоимости» ниже: пересчёт 2026-08-18 даёт 486 токенов**. On-invoke от ~20 токенов (`grill-me`) до ~3.9k (`wayfinder`).

Манифест плагина курирован: 22 скилла из репозитория, категории `in-progress` и `deprecated` в него не входят.

### Четыре скилла мертвы без настройки

`to-spec`, `to-tickets`, `triage` и `implement` пишут в трекер задач, которого им не назвали: команда `setup-matt-pocock-skills` ни разу не запускалась. Это четверть инженерной части набора и одна из причин, почему за три недели набор не использовали ни разу.

### Пересечения с [[superpowers]]

| Задача | superpowers | этот набор |
|---|---|---|
| Прощупать идею до работы | `brainstorming` | `grilling`, `grill-me` |
| Отладка | `systematic-debugging` | `diagnosing-bugs` |
| Разработка через тесты | `test-driven-development` | `tdd` |
| Ревью кода | `requesting-code-review`, `receiving-code-review` | `code-review` |
| Планирование крупной работы | `writing-plans`, `executing-plans` | `wayfinder`, `to-spec`, `to-tickets` |
| Написание скиллов | `writing-skills` | `writing-great-skills` |

Только у superpowers: параллельные агенты, git-worktrees, проверка перед объявлением «готово». Только здесь: исследование по первоисточникам, обучение пользователя, передача работы другому агенту. **Выключить один целиком в пользу другого нельзя — потеряется уникальное.**

## Первая проба на живом проекте (2026-08-26)

Вопрос «каким набором вести разработку» задавался с 27.07 и ни разу не решался в пользу
этого пака — проба откладывалась месяц. Состоялась на новом веб-проекте (сайт салона
красоты, стек Laravel), причём набор взяли **не целиком, а частями**: хребтом процесса
остался [[superpowers]], а отсюда взяли `domain-modeling` и `grilling` на этап допроса
замысла. Полный переход отвергнут по конкретной причине — в паке нет аналога
`writing-plans`.

Критерии задавались заранее, чтобы проба не свелась к «понравилось / не понравилось».

**1. Вскрыл ли дыру в замысле, которую не заметил бы обычный разбор — да.** Допрос
отменил три опорных решения, принятых на брифе:

- необязательная «онлайн-запись потом» оказалась сердцем проекта, из-за чего отпал весь
  задуманный порядок работ «витрина на файле → база → админка»: расписание без базы не живёт;
- **у площадки нет владельца** — это помещение, где независимые мастера арендуют места,
  каждый сам себе прайс и график;
- сайт по сути задумывался макетом для других таких же площадок, а значит имя, логотип,
  цвета и тексты обязаны жить в базе, а не в коде.

Ценнее всего второе. Замысел «сделать сайт и продать владельцу» опирался на персонажа,
которого не существует. Обычный разбор архитектуры такого не ловит: он проверяет, как
построить заказанное, а не существует ли заказчик.

**2. Задал ли вопрос, до которого не додумался бы ассистент сам — да.**
`domain-modeling` оставляет после себя файл-словарь предметной области, где у каждого
термина есть поле «_Избегать_»: у «площадки» — салон, филиал, точка; у «администратора» —
владелец, хозяин, управляющий. Это не документация ради документации: словарь ловит
расползание терминов до того, как оно попадёт в имена таблиц и в интерфейс. Ни
`brainstorming`, ни обычный разбор словаря не заводят.

**3. Пришлось ли переводить с английского — нет.** Скиллы англоязычные, но работа шла
по-русски: в ответах ассистента 8% латиницы, и та — имена скиллов и техтермины. Критерий
считался решающим заранее: скилл, вопросы которого надо переводить, просто не будет
вызван, каким бы хорошим он ни был.

**Вывод: пак остаётся.** Рабочая форма — не «выбрать один набор из двух», а брать
отдельные скиллы под конкретный этап. Проверено на одном проекте; прежде чем считать
правилом, повторить на втором.
