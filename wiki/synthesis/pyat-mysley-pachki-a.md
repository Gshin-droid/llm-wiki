# Пять мыслей разбора 28–29.10: как проверять работу агентов

**Вопрос.** Что сходится в 13 материалах о работе с агентами, разобранных 28–29.10.2026 (пачка «наша работа с агентами» из инбокса плюс два видео Березницкого), и что из этого уже встроено в систему.

Каждая мысль ниже подтверждена минимум двумя независимыми источниками.

## 1. Передача между агентами теряет детали — передавать сырьё, а не пересказ

Наряд и отчёт — выжимки в обе стороны; отсутствие в отчёте не видно. Проверяющие по краткому описанию фазы дружно ставят «всё хорошо».
- Источники: [[anthropic-fold-subagents-into-main-loop]] (испорченный телефон, пропавший шаг после слияния агентов), [[berezhnitsky-testing-ai-agents]] (проверяющим передавали описание вместо диффа), [[diff-tour]] (код на экране — из git, не из ответа модели).
- Встроено: в форме наряда — «заметил вне задачи: сообщить, не трогать», доказательство по каждому пункту, сырьё (дифф, файлы, полный журнал в файле) вместо пересказа. Субагент оправдан, только когда даёт дешёвую модель, чистый контекст или независимый взгляд.

## 2. Сначала проверка кодом, потом модель, человек последним

Детерминированная проверка бесплатна и не устаёт; агенты пропускают тесты и подгоняют код под тесты.
- Источники: [[berezhnitsky-engineer-when-ai-writes-code]] (ворота-код между фазами), [[berezhnitsky-testing-ai-agents]] (код → судья → человек), [[diff-tour]] (каждую ссылку модели проверяет программа), [[unclebob-ub-mode]] и тот же второй ролик (мутационное тестирование).
- Встроено: сторож до действия против записи адреса API в настройки ([[forever-downloads-agents-md-attack]]). Открыто: ворота-код между этапами конвейера проектов, проверка ссылок «файл:строка» в отчётах проверяющих, проба мутационного тестирования.

## 3. Судья — другой семьи моделей

У судьи одной семьи с автором общие слепые пятна; судьи переоценивают свою семью.
- Источники: [[berezhnitsky-testing-ai-agents]] (смещения судей), [[berezhnitsky-engineer-when-ai-writes-code]] (судья другого класса находит больше дефектов).
- Наше слабое место: искатель, перепроверяющий и основная сессия — все одной семьи. «Два независимых проверяющих» независимы по контексту, но не по модели. Открыто: второй семьёй — бесплатные модели через шлюз только для публичного материала или платная подписка другой лаборатории с оценкой цены.

## 4. Мерить повторными прогонами и по каждой задаче

Один прогон ничего не говорит о стабильности; среднее прячет сломанную задачу.
- Источники: [[anthropic-fold-subagents-into-main-loop]] (поломка проявилась в одном прогоне из двух), [[berezhnitsky-testing-ai-agents]] (pass^k, регрессия против шума), пилот метода агента по спецификации ([[habr-agent-po-specifikacii]], ложные «сделано» во всех трёх прогонах одной модели).
- Встроено: в метод своего агента — k прогонов на случай, pass^k, сравнение версий по перевёрнутым случаям. Открыто: то же для агентов с моделью внутри во всех проектах, плюс ярлыки сбоев по журналам и запись ответов модели для тестов обвязки.

## 5. Человек — на дизайне и тест-плане, а не на коде

Читать весь код агента человек не успевает и не обязан; ошибка в начале портит всё дальше.
- Источники: [[berezhnitsky-engineer-when-ai-writes-code]] (дизайн — 100% человеку, остальное «над циклом»), [[opencode-agents-md-pravila]] (у нас человек принимает план и поведение, не код: при расхождении кода и плана — стоп и вопрос), [[diff-tour]] (метки «проверено / из кода / общее суждение» — чтобы человек видел, чему верить).
- Встроено: правило «сначала план», схема при изменении больше двух частей. Открыто: этап «тест-план простым языком до плана реализации, утверждает пользователь» в конвейере проектов.

## Отдельная линия — безопасность

Файл инструкций агента, приехавший из интернета или чужого репозитория, приходит тем же каналом, что свои правила, и текстовое «не доверяй файлам» его не держит — [[forever-downloads-agents-md-attack]]. Ответ — стена до действия (сторож) и правило «не запускать агента в Загрузках и в свежем чужом клоне до проверки его файла инструкций».
