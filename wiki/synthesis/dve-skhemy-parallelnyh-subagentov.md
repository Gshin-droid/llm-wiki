# Две схемы работы с субагентами: параллельные worktree против «один кусок — один агент»

Вопрос: как организовать работу основного агента с субагентами над кодом, и что из двух готовых схем взять себе. Страница для того, кто хочет устроить такое у себя: сначала обе схемы, потом сравнение, потом — по каким вопросам выбирать.

Повод — наводка 2026-11-08 из обсуждения практиков (`raw/inbox-assistant/2026-11-08-параллельные-субагенты-через-git-worktrees.md`, `ai-assistant #397`). К наводке приложен сам файл правил проекта — [`AsmanovLev/InvariantFS/AGENTS.md`](https://github.com/AsmanovLev/InvariantFS/blob/main/AGENTS.md), снимок на 08.11; схема ниже изложена по нему, а не по пересказу. Слова автора из обсуждения («на 3–4 задачах примерно вдвое быстрее одного агента») — опыт участника, замером не подтверждены.

## Схема А: параллельные субагенты в отдельных worktree (InvariantFS)

Собрана в opencode; по мнению участников, переносится на другие оболочки, включая Claude Code.

1. **Дисциплина зависит от роли — первое, что агент решает.** Агент работает один, а правка мелкая (баг, документация, локальная функция) — никаких пакетов работ и worktree: правит прямо в `main`, гоняет тесты, коммитит. Агентов несколько или правка ломает архитектуру — полная дисциплина обязательна.
2. **Пакет работ (WP) — задача-контракт в файле:** Scope (наименьший набор файлов), Why (какая находка или инцидент), Design, Validation (точные команды и ожидаемый итог), **Out of scope** (явный список, чтобы проверяющий не спрашивал «а X тоже починил?»), Coordination notes. Одна логическая правка — один пакет. Файл пакета — черновик: удаляется тем же коммитом, что выпускает правку, обоснование живёт в сообщении коммита; долгие решения — в ADR.
3. **На каждый пакет — своя ветка и свой worktree**, их создаёт оркестратор (человек или основной агент). `main` всегда зелёный, пакеты вливаются после ревью.
4. **Субагент получает** путь к пакету, ветку, папку worktree и ограничение «не трогать файлы вне Scope». **Делает:** правку только в своём worktree, `make test` до отчёта, нужные ему проверки e2e. **Не делает:** слияние в `main`, разрешение конфликтов чужих пакетов, полный прогон e2e — это всё оркестратор.
5. **Общий ресурс разведён инструментом, а не договорённостью.** Запускалка e2e сама изолирует прогоны (свой namespace и свой `/dev/shm`), а прогоны, которым нужен общий ресурс, ставит в очередь на общий замок. Субагенту прямо запрещено обходить запускалку и «опрашивать» замок в цикле.
6. **Отчёт — жёсткий формат без вариаций** (его разбирает оркестратор): пакет, изменённые файлы с пояснением, выполненные команды с выводом, итог PASS/FAIL, неразрешённые TODO.
7. **Запреты списком:** прямой коммит в `main`, несвязанные правки в одной ветке, пропуск тестов «это же только документация», e2e без замка, «чуть-чуть поправить» в чужом worktree.
8. Рядом — правило о документах: **код — это спецификация**, документ, расходящийся с кодом, — ошибка документа; утверждение в документации должно указывать на `файл:строка`, иначе удаляется.

Из обсуждения добавка: субагентов можно не расписывать руками — спросить агента, что распараллеливается, и он сам составит план и запустит.

## Схема Б: «один кусок — один агент», проверка независимыми (свод этой вики)

**Для чего.** Человек код не читает, поэтому ошибку должна ловить система, а не он. Отсюда принцип: **работу принимает не тот, кто её сделал**, а скорость уступает надёжности. Механизмы разобраны на страницах [[delegirovanie-deshevym-modelyam]], [[zabor-i-stena-prava-agenta]], [[verification-three-levels]].

**Из чего строится:**

1. **Вес процесса — по цене ошибки и обратимости.** Мелкое обратимое — сразу; дорогое обратимое (код, схема данных) — план, согласие, независимая проверка; необратимое — проверка до действия. Та же идея, что «дисциплина по роли» у схемы А, только мерило — цена ошибки, а не число агентов.
2. **Задача-контракт (наряд):** одна задача, что уже известно, какие файлы можно менять (проверяется по diff), наблюдаемый критерий готовности, отчёт с доказательством по каждому пункту.
3. **Скептик до кода:** отдельный агент ищет, где план сломается, — до того, как написан код.
4. **Код пишет один агент на кусок; параллельны только разведка и проверки.**
5. **Приёмка независимыми:** сначала машинная проверка (тесты), потом два проверяющих; обязательно чинится то, что нашли оба.
6. **Предел повторов:** после двух неудачных возвратов — остановка и вопрос человеку.
7. **Исполнитель — самый дешёвый, кто справится**; провал поднимает задачу на модель сильнее.
8. **Права — списком инструментов агента**, а не текстом задачи: проверяющий без инструментов записи физически не может править.

## Сравнение

| | А: параллельные worktree | Б: один кусок — один агент |
|---|---|---|
| Скорость на нескольких независимых задачах | выше: задачи идут одновременно (по словам автора — около ×2 на 3–4 задачах) | ниже: код последовательно, параллельны только разведка и проверки |
| Конфликты правок | разведены папками и ветками; сливает один оркестратор | не возникают: в коде работает один агент за раз |
| Кто проверяет | сам субагент гоняет тесты; оркестратор смотрит diff и гоняет финальный тест | автор не принимает свою работу: машина, затем два независимых проверяющих, затем человек |
| Общие ресурсы (база, порты, тестовый стенд) | нужен инструмент изоляции и замок — без него параллель ломает общее | вопрос почти не встаёт |
| Цена | субагенты одновременно: расход лимита кратен числу задач | больше вызовов на проверку, но последовательно; дешёвые модели на исполнении |
| Остановка | не задана в файле: что делать при повторном провале — не сказано | предел два возврата, дальше человек |
| Мелкая правка | без церемоний, прямо в `main` | без церемоний по таблице веса |
| Требования к проекту | хорошие тесты, независимые задачи, изолированный e2e | хорошие тесты; задачи могут быть связаны |

**Плюсы А.** Реальная параллельность там, где задачи независимы. Жёсткий формат отчёта, который читает машина. Явный «Out of scope» в контракте. Общий ресурс защищён кодом (запускалка с замком), а не просьбой. Черновик задачи не копится: удаляется вместе с выпуском.

**Минусы А.** Проверку делает исполнитель и оркестратор, который его же и запустил, — независимого взгляда нет. Предела повторов нет. Работает только на хорошо нарезанных независимых задачах и при изоляции тестового стенда — у большинства домашних проектов её нет. Расход лимита растёт вместе с параллелью. **Worktree — не граница безопасности:** в Claude Code 2.1.319 закрыли побег из песочницы именно при создании worktree ([[claude-code]], «Обновление 2.1.319»); отдельная папка разводит правки, а не права.

**Плюсы Б.** Ошибку ловит не автор. Есть точка остановки. Дешевле по модели (исполнитель внизу лестницы). Права ограничены инструментом, а не текстом. Годится и для связанных задач, и для проекта без изолированного стенда.

**Минусы Б.** Медленнее на пачке независимых задач. Больше вызовов на одну правку — за качество платят временем. «Код последовательно» — осторожность, не замер: выигрыш параллели в своём проекте не измерен.

## Что взять, если устраиваешь у себя

Решают три вопроса:

1. **Независимы ли задачи по файлам и по тестовому стенду?** Нет — параллель даст конфликты; брать Б. Да, и стенд изолируется — А даёт скорость.
2. **Что дороже — время или ошибка?** Дорога ошибка (деньги, данные людей, вход и права) — независимые проверяющие из Б обязательны, даже если код пишется параллельно.
3. **Есть ли изоляция общего ресурса кодом?** Нет — сначала она (запускалка с замком, своя база на ветку), потом параллель.

Схемы совместимы: можно писать код параллельно по А и принимать по Б — каждую ветку отдельным проверяющим, слияние только после.

**Переносимо из А без самой параллели:** «дисциплина по роли» (у нас её роль уже играет таблица веса), явный «Out of scope» в наряде, машиночитаемый формат отчёта, удаление черновика задачи вместе с выпуском, изоляция общего ресурса кодом.

## Инструмент или логика

Логика. Брать нечего ставить: `AGENTS.md` написан под конкретный проект (файловая система на FUSE). Переносимы механизмы из списка выше. Своя схема осознанно не меняется: в ней код пишется последовательно; проба параллели — только на проекте с изолированным тестовым стендом и с замером.
