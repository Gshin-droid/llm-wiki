## Саммари

Скилл — сокращённая переделка чужого набора правил (poteto-mode / pstack), к которой добавлены три детерминированные программы-проверки автора. Около 60 коротких правил в три этапа: «сначала заставь работать» (самое маленькое изменение, форма данных до логики, падающий тест до кода — и падающий по ожидаемой причине, недопустимые состояния невозможны структурой, внешние данные разбираются один раз на входе, идемпотентность), «потом сделай правильно» (воспроизвести → чинить причину; «заглушка, прячущая падение, — не исправление»; тест вызывает код как пользователь; «тест, проходящий при пустых функциях, — выбросить»), «рабочие привычки» (журнал каждого действия с причиной, главная ветка разговора маленькая, мелкие упорядоченные коммиты).

Программы-проверки: `crapper` — метрика CRAP (запутанность × непокрытость тестами) на функцию, порог < 10; `dryer` — структурные повторы кода, порог сходства 0,8; `mutator` — мутационное тестирование: покрыть непокрытое, «убить выживших» (порчи, при которых тесты остаются зелёными), удалить мёртвый код. Если программы не установлены, шаги с ними скилл пропускает.

## Что взято в вики

- **Мутационное тестирование как машинная проверка тестов** → [[verification-three-levels]] (дополнение): то же «сломай свою проверку нарочно», только программой и на каждой функции.
- **«Тест, проходящий при пустых функциях, — выбросить»** — короткая форма того же принципа; требование к скиллу наряда исполнителя-кодера (дело о нарядах по ролям, вместе с [[opencode-agents-md-pravila]] и [[agentskills-best-practices]]).

## Берём инструмент или логику

**Скилл не ставим.** Почти все правила уже стоят: режим ponytail (маленькое изменение, причина вместо заглушки, проверка на границе доверия) и [[superpowers]] (тест сначала, пошаговая отладка). Второй набор тех же мыслей другими словами спорит с первым за контекст — по правилу [[skill-authoring-practical-rules]] чужие наборы берутся поштучно, а здесь брать нечего. Программы автора не пробовались; на каком языке они работают — не проверено.

**Логику берём:** мутационное тестирование — кандидат в общий инструментарий. Для Python известен готовый `mutmut`; в нашем наборе инструментов мутационного тестирования нет. Решение пользователя 28.10: проба общим делом, проект для пробы выберет сам. Дорого по времени (полный прогон тестов на каждую порчу) — запуск по событию, не на каждый коммит. Тот же расход уже виден в замере [[bughunt-bench-sonnet-5-5]]: Sonnet на max втрое дороже из-за мутационных проверок.

## Что не взято / лиды

- Метрика CRAP и поиск повторов — у нас их роль отчасти играют линтеры devkit; отдельно не берём, пока мутационная проба не покажет, что тесты — слабое место.
- Скепсис участников чата к автору — не довод ни за, ни против; правила оценены по содержанию.

## Оценка источника

Первоисточник — скилл в репозитории автора. Обоснований и замеров нет: это свод правил опытного практика, не исследование. Ценность для нас — не новые правила, а ссылка на класс инструментов (мутационное тестирование), которого в нашей системе нет.
