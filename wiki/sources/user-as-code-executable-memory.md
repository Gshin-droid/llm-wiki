# User as Code: Executable Memory for Personalized Agents

**Дата загрузки:** 2026-11-20 (ежедневный процесс закрытия пробелов, `wiki/gaps-backlog.md`)
**Автор:** Bojie Li (Pine AI)
**Опубликовано:** июнь 2026 (arXiv)
**Тип:** научная статья (препринт) + официальный open-source репозиторий автора с кодом/прототипом
**Ссылка:** https://arxiv.org/abs/2606.16707 (сама статья — недоступна из этого окружения, см. «Оценка источника»), https://github.com/19PINE-AI/user-as-code (официальный репозиторий автора, README прочитан напрямую через `raw.githubusercontent.com`)
**Raw:** отдельным файлом не сохранён — материал получен прямым чтением README репозитория; `README.md` ветки `main` прочитан напрямую.

## Саммари

Закрывает часть пробела «Первоисточники исследований из [[berezhnitsky-agent-memory-lies]]»: источник называл работу на слух, как «user as a code», без ссылки. Первоисточник (`arXiv:2606.16707`) был найден раньше (запись от 2026-10-05 и ранее), но сам `arxiv.org` заблокирован сетевым прокси этого окружения на уровне DNS — та же картина, что у [[chroma-context-rot]] и [[minja-memory-injection-attack]]. В отличие от тех двух случаев, раньше здесь не проверялось, есть ли у автора открытый репозиторий с кодом — он есть, Apache 2.0, и README напрямую излагает архитектуру и числа статьи.

Идея работы (User as Code, UaC): модель пользователя у персонализированного агента — не бэг фактов для similarity search, а типизированный Python-проект. Запись идёт в два этапа — append-only лог фактов, затем периодическая ограниченная структуризация в типизированный код (`domains/`, dataclass-схемы, исполняемые constraints, тесты). Типизированный вид не заменяет retrieval, а дополняет его: README прямо говорит, что система «adds an executable typed-Python view over the user's records while retaining fact and raw-archive retrieval».

## Ключевые факты (подтверждено README репозитория напрямую)

**Лицензия.** Дословно: «Code and documentation are released under the Apache License 2.0» (см. также `NOTICE`).

**Архитектура.** Два этапа записи: «an append-only fact log followed by periodic bounded structuring» — факт сначала просто дописывается в лог, никогда не теряется, и только потом (периодически, ограниченным проходом) превращается в типизированный Python. У каждого пользователя-примера — свой «проект»: dataclass-схемы и состояние под `domains/`, исполняемые constraints, тесты; рабочий прототип в репозитории называется `jessica_thompson`. Типизированный слой даёт то, чего не даёт retrieval — обычный Python может прогнать по нему аналитический запрос (агрегация, подсчёт, перечисление), а не только похожесть по эмбеддингу.

**Чем это отличается от памяти на похожести.** README формулирует ровно слабое место, которое эта вики уже знает по бенчмарку Zep ([[agent-memory-five-questions]], вопрос 4, «⅓ против ~95%»): память, работающая через similarity search, «recalls individual records well but struggles to enumerate every relevant record for an aggregate query» — находит один нужный факт, но не умеет гарантированно перечислить все релевантные записи для агрегирующего вопроса («сколько раз», «все случаи когда»). Типизированный код считает такие вопросы точно, потому что это обычная программа, а не поиск.

**Заявленные числа (бенчмарк Full LOCOMO, 1 986 вопросов, два бэкенда — GPT-5.6 Luna и Gemini 3 Flash Preview):**
- Фактическая память, 1 540 вопросов с ответом в истории: 39,4% / 46,9% token F1, 78,8% / 80,6% judge accuracy.
- Отказ от ответа на провокационный вопрос (446 adversarial-вопросов): 64,3% / 95,7% точность отказа.
- Аналитические (агрегирующие) запросы, 100 детерминированно оцениваемых случаев: **100% точность** у обоих бэкендов.

Популярность репозитория на дату чтения: 20 звёзд, 3 форка, 1 watcher — совсем молодой проект, не признак широкого внедрения.

## Что не подтверждено / требует дальнейшей проверки

- **Сравнение с конкретными конкурентами (MemMachine, Mem0) с цифрами 99%/43%/6%.** Независимый пересказ (агрегатор chatpaper.com через поисковую выдачу) приводит такую тройку чисел на тех же 100 аналитических случаях, но README репозитория эти два названия и эти цифры не упоминает вовсе — только общую формулировку про retrieval-based память и собственный результат 100%. Как факт первого порядка в вики не переносится, цифры 39,4–100% выше — то, что подтверждено самим README.
- **Полный текст статьи** (методология эксперимента, детали двух бэкендов, лимиты подхода) — `arxiv.org` недоступен из этого окружения (`ENOTFOUND`, DNS-уровень), один заход, повторно не пробовать.
- **Насколько типизированная схема нуждается в ручной разметке domain-модели под новую предметную область** — README не раскрывает процесс создания схемы для пользователя, отличного от демонстрационного `jessica_thompson`.

## Оценка источника

Официальный репозиторий автора статьи (имя организации `19PINE-AI` совпадает с институциональной принадлежностью автора «Pine AI», указанной в метаданных препринта) — не сторонний форк и не пересказ. Архитектура и числа взяты из README, которое само описывает систему и репортит бенчмарк, а не из вторичного изложения. Сам текст статьи остаётся непрочитанным (домен заблокирован), поэтому возможные нюансы методологии (составы бэкендов, точный протокол LOCOMO) не проверены из первых рук.

## Проверка безопасности источника

Прочитан текстовый README официального GitHub-репозитория. Обычный исследовательский материал (описание архитектуры, таблица результатов, инструкция запуска прототипа), инструкций, адресованных агенту, не обнаружено.
