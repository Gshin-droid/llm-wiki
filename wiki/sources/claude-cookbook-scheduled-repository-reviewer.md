## Саммари

Recipe строит read-only агента-ревьюера репозитория на [[claude-agent-sdk]], запускаемого по расписанию (cron) без человека рядом — «unattended job you control». Найден не по прямой наводке, а поисковым прогоном рутины практик по темам вики после того, как очередь `raw/` оказалась пуста: искали новый практический материал за неделю 08-31…09-07 по официальным источникам Anthropic, независимые блоги за это окно проверить не удалось (прокси блокирует большинство доменов кроме `github.com` и `platform.claude.com`/`code.claude.com`).

Материал попадает прямо в мандат рутины: это не анонс, а полный воспроизводимый паттерн автономного планового прогона — то есть буквально то, чем эта вики уже пользуется сама (три рутины на Cloud Routines, `git`-коммиты как чекпоинты), только применённый к другой задаче (ревью кода) и с другим примитивом непрерывности (`resume_session_id` вместо файла-хендоффа).

## Три стратегии продолжения между прогонами (дословно из ноутбука)

Таблица «When to resume and when to start fresh»:
1. **Fresh session на каждый прогон** — когда каждое решение независимо (например, проверка отдельных pull request'ов).
2. **Fresh session + прошлые находки в промпте** — нужен только последний результат (трекер TODO-долга).
3. **Resumed session** — нужно сравнение с полным контекстом предыдущего прохода (зависимости, изменения между циклами) — выбор этого recipe.

## Механика read-only агента

- **Разрешённые инструменты** — только `Read`, `Glob`, `Grep`; ни shell, ни сети. Дословно: «content the reviewer reads has nowhere to go but the reply itself» — явное обоснование выбора инструментов через отсутствие канала эксфильтрации, а не только через «меньше прав вообще».
- **`permission_mode="dontAsk"`** + декларативный allowlist (`Read(/{repo}/**)`) вместо диалоговых подтверждений на каждый вызов — нужно для полностью автономного прогона.
- **`PreToolUse`-хук `deny_reads_outside_repo`** — второй, императивный слой поверх allowlist: резолвит путь (включая symlink) и отклоняет всё, что выходит за пределы репозитория; отдельно отклоняет abs-пути, brace-expansion (`{...}`) и `..` в паттернах `Glob`.
- **`disallowed_tools` на служебную директорию** — независимый третий слой: скрипт сам себе запрещает читать директорию, где лежит `.env` и файл сессии, даже если первые два слоя почему-то не сработают. Явно названо «independent second layer» относительно хука.
- **Изоляция MCP/settings** — machine- и account-level MCP-серверы и настройки в прогон не подмешиваются, чтобы поведение на ноутбуке разработчика и на cron-машине было одинаковым.

## Непрерывность через `resume_session_id`, не через файл

Состояние — JSON рядом со скриптом (`session_id`, `review_id`, `finding_ids`), запись атомарна (write-to-tmp + `rename`, защита от обрыва процесса посередине записи). Cold run (файла нет или он повреждён/чужой репозиторий) — полный обход с бюджетом `max_turns=40`/`max_budget_usd=2.00` и схемой без continuity-полей. Follow-up — `resume` с `session_id` из файла, бюджет уже`20`/`$0.50`(дешевле, потому что модель не сканирует репозиторий заново — просто просматривает изменения из уже загруженного контекста), схема добавляет `previous_review_id`/`previous_finding_ids`/`resolved`. После ответа скрипт сам проверяет, что continuity не сломалась (совпадение `previous_review_id`, пересечение находок) и метит `RESUME-LINK-BROKEN`, если нет — то есть **не доверяет собственному успешному вызову**, а перепроверяет заявленную память моделью fact-check'ом по файлу.

Это третий, отличный от двух уже разобранных механизм той же задачи «пережить обрыв контекста между прогонами»: [[long-running-agent-harness]] — `PROGRESS.md` + git; [[planning-with-files]] — три файла + lifecycle hooks; здесь — родная функция SDK `resume`, session_id как единственный носитель памяти, файл нужен только чтобы найти сам session_id.

## Эксплуатационная дисциплина

- Три уровня exit code: 0 — успех, 1 — ошибка агента (budget/turns exceeded — файл сессии **не удаляется**), 2 — usage error (репозиторий не найден, служебная директория внутри репозитория и наоборот — обе стороны изоляции проверяются явно).
- Grep-удобные маркеры в stdout под cron-логи: `REVIEW-RUN-COMPLETE`, `REVIEW-RUN-INCOMPLETE stage=usage reason=...`, `SESSION-FILE-CLEARED`, `RESUME-LINK-BROKEN`.
- Явное предупреждение: «review.log gets the same handling as the repository it reviews» — лог с находками ревью (потенциально содержащий секреты, на которые наткнулся ревьюер) требует той же защиты, что сам репозиторий, а не считается служебным мусором.
- Рекомендация по ротации: периодически удалять файл сессии по расписанию — деградацию распознаёт падение доли «вспомненных» находок в follow-up-ответах.
