## Саммари

**Закрывает старый, явно зафиксированный пробел.** При ingest'е [[claude-code-routines-docs]] (03.08.2026) эта же статья была проверена и отмечена «403 во всех проверенных путях (прямой фетч, `r.jina.ai`, вторичные пересказы dev.to/thenewstack)» — осознанно не реконструирована по пересказам, оставлена как лид. Сегодня `WebFetch` того же `claude.com/blog/getting-started-with-loops` прошёл без отказа. Расхождение со старой записью — не ошибка таблицы маршрутов, а изменение доступности домена во времени (та же нестабильность, что уже отмечена в `source-evaluation.md` для `claude.com/blog`/`claude.dev`).

**Что за материал.** Официальная методология «loop engineering» — четыре вида цикла, различающихся по триггеру, условию остановки, примитиву и типу задачи: **turn-based** (по промпту пользователя, останавливается на суждении Claude), **goal-based** (`/goal`, останавливается на проверке критерия отдельной моделью-оценщиком), **time-based** (`/loop`/`/schedule`, останавливается по отмене или завершению работы), **proactive** (событие/расписание без участия человека в реальном времени, каждая задача завершается по своей цели, но сама рутина работает, пока её не выключат). Статья явно советует начинать с простейшего варианта и наращивать сложность только по необходимости — не выбирать proactive loop по умолчанию.

**Прямое совпадение с этой вики.** Собственные три автономные рутины («новости», «практики», «хвосты») — буквальный пример **proactive loop** из таксономии статьи: триггер — расписание без участия человека, задача завершается по своей цели («страница разобрана, записи в индексе/логе на месте»), а сама рутина продолжает работать до отмены. Разбор следующего уровня глубины «сохраняем" — именно потому, что это описание устройства собственной практики, а не абстрактного примера.

## Что взято в вики

**1. Таблица четырёх видов цикла.**

| Вид | Что вы отдаёте | Когда применять | Инструмент |
|---|---|---|---|
| Turn-based | проверку | исследование/решение | скиллы проверки |
| Goal-based | условие остановки | исход чётко формализуем | `/goal` |
| Time-based | триггер | работа идёт по расписанию вне текущей сессии | `/loop`, `/schedule` |
| Proactive | сам промпт | работа регулярна и хорошо определена | все предыдущие + Dynamic Workflows |

**2. Turn-based — улучшается через `SKILL.md` с критерием самопроверки.** Пример из статьи — скилл для фронтенд-правок: запустить dev-сервер и взаимодействовать с изменённым элементом, скриншоты до/после, ноль новых ошибок/предупреждений консоли браузера, перформанс-трейс и Core Web Vitals через Chrome DevTools MCP; при провале — исправить и повторить с первого шага, не возвращать частично проверенную работу. Общий совет: чем более количественная проверка, тем легче самопроверке Claude сработать надёжно.

**3. `/goal` — конкретный синтаксис и границы применимости.** `/goal get the homepage Lighthouse score to 90 or above, stop after 5 tries` — детерминированный критерий (счётчик тестов, числовой порог) работает лучше размытого; явный потолок попыток рекомендован всегда; `/goal` без аргументов показывает число ходов и токенов, уже потраченных текущей целью.

**4. Proactive loop — состав, а не один инструмент.** Пример статьи — четыре компонента вместе: `/schedule` проверяет канал фидбэка раз в час, `/goal` со скиллами задаёт и проверяет критерий завершения, Dynamic Workflows оркеструет агентов триажа/исправления/ревью, auto mode убирает permission-промпты, чтобы рутина не зависала без человека. Внутри — каждый баг исследуется параллельно в нескольких worktree, затем агент-судья выбирает решение.

**5. Маршрутизация моделей внутри рутины — явный совет, не было в вики ни на одной странице о [[dynamic-workflows]].** Для рутинной работы — маленькие быстрые модели; для содержательных решений — самая способная модель. Прямое дополнение к уже известному чеклисту [[claude-api-cost-optimization]] на уровне не отдельного вызова, а состава ролей внутри одной proactive-рутины.

**6. Управление расходом токенов — пять приёмов, которых не было собранными в одном месте:**
- примитив и модель — под размер задачи, маленькая задача не нуждается в нескольких агентах/циклах;
- точный критерий успеха и остановки — чтобы Claude не останавливался ни слишком рано, ни слишком поздно;
- пилотный прогон перед масштабным — Dynamic Workflows может поднять сотни агентов разом;
- детерминированные шаги — в скрипт, не в рассуждение модели каждый раз (дешевле);
- частота опроса — не чаще, чем меняется наблюдаемая система;
- видимость расхода — `/usage` (по скиллу/субагенту/MCP), `/goal` (без аргументов), `/workflows` (токены по агенту, с возможностью остановить);
- модель и уровень `effort` — названы «одними из главных рычагов стоимости» прямым текстом статьи.

**7. Поддержание качества кода в длинной автономной работе — три приёма:**
- стандарты качества кодируются в скиллах, чтобь Claude мог сам себя проверить, а не только следовать существующим паттернам репозитория;
- второй агент со свежим контекстом для ревью (`/code-review` или GitHub Code Review) — менее подвержен искажению от хода рассуждений первого агента, который писал код;
- результат не дотягивает до стандарта → чинить систему (обновить скилл), а не только конкретную находку — иначе выигрыш разовый, а не на будущие итерации.

**8. Итоговая рамка выбора.** Автор предлагает взять одну задачу, где пользователь — узкое место, и спросить по очереди: можно ли написать проверку самому? чётко ли определён критерий «готово»? приходит ли работа по расписанию? — затем запустить цикл, понаблюдать, где он застревает или перебирает, и итерировать.

## Берём инструмент или логику

**Инструмент.** `/goal` — не пробовался в этой автономной сессии (команда интерактивная, предполагает присутствие человека для первого запуска и контроль порога попыток) — кандидат для собственной интерактивной работы пользователя на задачах с численным критерием (производительность, покрытие тестами), не для трёх автономных рутин вики: у них уже есть собственный критерий завершения (CI-сторожа + `ingest.py check`), который жёстче модель-оценщика `/goal`.

**Логика — три переносимых урока:**
1. **Таксономия цикла — готовая рамка для классификации любой будущей автоматизации вики или проекта пользователя** (какой триггер, какое условие остановки, какой примитив) — до этой статьи такой явной классификации в вики не было, автоматизации описывались по способу запуска (Cloud/Desktop/`/loop`), не по этим четырём осям.
2. **«Система, а не находка»** — прямое совпадение с действующим правилом этой же вики («Ни механический проход, ни сверка не чинят найденное сами... находит одна работа, закрывает другая» в CLAUDE.md, «Рутина 3 — хвосты»): официальная статья формулирует тот же принцип для кодовой автоматизации — находка в одном прогоне должна менять скилл/систему, а не чиниться разово.
3. **Второй агент со свежим контекстом как менее искажённый ревьюер** — та же логика, что уже используется воскресной сверкой с сырьём этой вики (тот же агент, что правил страницу месяц назад, не годится ей судьёй) — независимое официальное подтверждение уже действующей практики, не новый приём.
