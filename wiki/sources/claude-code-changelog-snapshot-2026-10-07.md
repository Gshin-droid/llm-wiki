## Находка 1: восемь permission-bypass фиксов в 2.1.292 — от Windows-варианта `rm`-обхода до TOCTOU в чтении файлов

Все цитаты — дословно по `CHANGELOG.md` (запись помечена вендором как Security там, где это явно сказано):

1. *«Fixed `rm -rf` on the 8.3 short name or another alternate Windows spelling of the home folder or a drive not being treated as removing it»* — **прямое продолжение** находки прошлого снапшота ([[claude-code-changelog-snapshot-2026-10-04]]): там защиту «всегда переспросить» перед опасным `rm` на критическом пути обходила shell-обёртка `bash -c`/`sh -c`; здесь — тот же критический путь (домашняя папка, диск), но обойдённый через альтернативную Windows-форму записи того же пути (короткое имя 8.3, например `C:\Users\USERN~1` вместо `C:\Users\Username`). Анализатор сравнивал путь по буквальной форме записи, а не по тому, на что путь физически указывает — ровно тот же класс слепого пятна, второй раз за две версии подряд, но на другой платформе.
2. *«Security: Fixed PreToolUse hook approvals and auto mode bypassing the permission prompt for file reads from network (UNC) paths»* — отдельная, явно помеченная вендором находка: чтение файла по сетевому Windows-пути (UNC, вида `\\server\share\файл`) не требовало подтверждения ни при проверке через `PreToolUse`-хуки, ни в auto mode — тот же обход «форма пути не распознана защитой», что и находка 1, но для чтения, а не для `rm`, и для другого класса путей.
3. *«Fixed a notebook or PDF read on macOS and Windows being able to return a file outside what was approved, through a link swapped in mid-read»* — TOCTOU (time-of-check-to-time-of-use, состояние гонки «проверили одно, прочитали другое»): между моментом, когда харнес проверил, что путь разрешён, и моментом, когда он фактически читает файл по этому пути, символическая ссылка успевала поменяться на другую цель — прочитанным оказывался не тот файл, что прошёл проверку. Платформонезависимый (macOS и Windows вместе) и концептуально отличается от находок 1-2: там путь маскировался формой записи, здесь — временным окном между проверкой и действием.
4. *«Fixed a tampered on-disk cache of server-managed settings being able to switch off or unseat the built-in policy plugin while the settings fetch failed»* — если синхронизация управляемых организацией настроек с сервером не удавалась, а локальный кэш этих настроек на диске был подменён, встроенный policy-плагин (несущий сами ограничения) можно было отключить или заменить. Отличается от находок 1-3: это не обход конкретного правила, а способ временно снять весь механизм правил целиком, через цепочку «сбой сети + модификация файла на диске».
5. *«Fixed a managed sandbox read-deny path (and user ones beside it) that appears or re-points mid-session not dropping project grants inside it or ending credential injection from files it covers»* — если путь, закрытый управляемым или пользовательским deny-правилом для `Read`, появлялся или менял цель посреди сессии (не был известен харнесу с самого начала), ранее выданные для него project-grants и внедрение credential'ов из покрываемых им файлов не отключались — защита, добавленная «задним числом» при появлении пути, не ретроактивно отзывала уже действующие разрешения.
6. *«Fixed sandboxed commands being able to read the staged file copies of `/ultrareview` uploads under `~/.claude/seed-admin»* — команды внутри песочницы могли прочитать временные копии файлов, загруженных через `/ultrareview`, хотя сама песочница должна была их не видеть.

Находка 2.1.289 (на три дня раньше, первый сигнал той же волны): *«Fixed `Read` deny rules not applying to files @-mentioned, changed, or selected in the IDE through a symlink»* — запрещающее правило для `Read` не применялось, если путь к файлу был символической ссылкой, независимо от того, упомянут ли файл через `@`, изменён или выбран в IDE.

Рядом, тоже 2.1.289, но не про `Read`/файлы — *«Fixed a deny or ask rule on a nested part of a compound shell command not holding over user-installed mod approvals on managed machines»*: вложенная часть составной shell-команды могла не наследовать deny/ask-правило, если на машине (managed) уже было одобрение пользовательского мода. Прямая связь с риском Claude Mods, названным в прошлом снапшоте ([[claude-code-changelog-snapshot-2026-10-04]], находка 2): мод, уже одобренный пользователем, мог «накрыть» своим одобрением composite shell-команду, часть которой должна была пройти отдельную deny/ask-проверку.

**Что это значит практически.** Семь из восьми находок 2.1.292 плюс находки 2.1.289 — не одна уязвимость, а параллельная серия похожих, но технически разных обходов: форма записи пути (1, 2), гонка времени проверки/использования (3), отказ сети + подмена диска (4), ретроактивность правила при появлении нового пути (5), утечка из специфичного временного хранилища (6), наследование одобрения мода на вложенную команду (2.1.289). Для автономных рутин этой вики (Linux-инфраструктура Cloud Routines) прямо применимы находки про симлинки и TOCTOU (3, и находка 2.1.289 про `Read` deny) — Windows-специфичные (1, 2) не применимы напрямую к среде исполнения, но показывают тот же класс мышления атакующего: искать форму пути, которую анализатор не распознал.

## Малое

- **`effort`-параметр у Agent tool** — настраиваемый уровень усилий субагента (ярус исполнения), отдельно от уже описанного в [[claude-code]] уровня усилий основной модели.
- **`--marketplace <source>` у `claude plugin install`** — явное указание источника маркетплейса при установке плагина, без привязки к одному настроенному по умолчанию.
- **`claude attach <name>` / `claude logs <name>`** с частичным совпадением имени сессии (2.1.290).
- **`ceiling` у вопроса/вердикта проверки** (2.1.290) — управляемый организацией потолок уровня одобрения.
- Регрессии 2.1.291 — две: сброс ответов на permission-запросы в облачных сессиях (регрессия 2.1.290) и потеря последних сообщений сессии при выходе (регрессия 2.1.288) — обе исправлены в течение суток после появления.
- Остальные пункты четырёх версий — UI/MCP/Remote Control/плагинные фиксы без веса для практики, полный список — в raw-снапшоте.
