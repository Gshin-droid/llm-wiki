# Memora — MCP-сервер памяти для агентов (репозиторий)

**Дата загрузки:** 2026-08-10
**Автор:** организация `agentic-box` (профиль пустой: без имени, сайта и контактов, 8 подписчиков, 2 репозитория)
**Опубликовано:** репозиторий создан 19.09.2025, релиз v0.3.0 — 10.08.2026
**Тип:** открытый репозиторий (Python, MIT, 619★, 69 форков)
**Ссылка:** https://github.com/agentic-box/memora
**Raw:** повод — `raw/inbox-assistant/2026-08-08-ии-агентам-прикрутили-почти-вечную-память-—-разрабы-собрали.md`

## Саммари

Разбор сделан **не по посту из инбокса, а по репозиторию.** Пост — подпись к видео из телеграм-канала, рекламная по форме («почти ВЕЧНУЮ память»), без ссылки и без единой проверяемой детали; по порогу вики он не проходит. Но он назвал проверяемый артефакт, а открытый репозиторий по нашей же таблице маршрутов — рабочий первоисточник.

Memora — MCP-сервер, дающий агенту память между сессиями: 22 инструмента, хранение в SQLite (или Cloudflare D1 / S3-R2), поиск по смыслу, типизированные связи между записями, TODO и баги, граф и RAG-чат поверх памяти.

Ценность для этой вики — **не инструмент, а чужие решения тех же задач**, которые мы разбирали у [[berezhnitsky-agent-memory-lies]]. Ставить не планируется (вика сама и есть слой памяти, читаемый человеком); брались применимые приёмы и один разбор аварии.

## Что взято — самое ценное первым

### 1. Авария 0.3.0: тихая деградация, которая «отчитывалась здоровой»

Релизные заметки v0.3.0 открываются признанием: систему можно было настроить **по её же README и её же установщику** в состояние, где **эмбеддинги не вычислялись вообще и никто об этом не сообщал**. Дословно:

> «Memora could be configured — following its own README and its own installer — into a state where **no embedding was ever computed and nothing said so**. Every semantic search silently became a keyword search, and the store filled with keyword bags while reporting healthy.»
>
> *Memora можно было настроить — следуя её же README и её же установщику — так, что ни один эмбеддинг никогда не вычислялся, и ничто об этом не говорило. Каждый семантический поиск молча превращался в поиск по ключевым словам, а хранилище наполнялось мешками слов, отчитываясь при этом здоровым.*

Цепочка: установщик прописывал внешний базовый адрес → вызовы эмбеддингов возвращали 404 → одно предупреждение в stderr сервера → откат на TF-IDF → работа продолжалась. **В найденном хранилище 756 записей были мешками слов месяцами.**

Это ровно то, что вика знает как «fail-fast конфиг + функциональная проверка guard'а» ([[claude-code-practices]], п. 5) — там прецедентом был мёртвый guard, потому что docker-compose не выставлял ENV. Разница только в том, что тут отказал не guard, а деградация была *успешной*: система не падала, а выдавала ответы худшего качества под видом обычных. Подробнее применение — в п. 5 практик.

Их лечение и есть тот флаг, который я видел в коде до чтения заметок: `MEMORA_EMBEDDING_STRICT=1` — падать сразу вместо тихого отката. Плюс отпечаток модели в хранилище стал включать backend, id модели, хост эндпоинта и представление, так что несовпадение обнаруживается и вызывает пересборку.

**Противоречие по причине аварии — см. раздел ниже.**

### 2. Принципы из `SOUL.md` — два прямо про нашу болезнь

> «Prefer deterministic aggregation over hidden narrative generation.»
> *Предпочитать детерминированную агрегацию скрытой генерации повествования.*

> «Preserve raw source memory ids so callers can verify summaries or digests.»
> *Сохранять идентификаторы исходных записей, чтобы вызывающий мог проверить сводки и выжимки.*

Второе — это «якорь к источнику» из нашего `CLAUDE.md`, сформулированное как требование к инструменту, а не как правило для агента. Первое — прямая профилактика петли пересказа ([[agent-memory-five-questions]], вопрос 4): сводка собирается детерминированно из записей, а не досочиняется моделью.

### 3. Цепочки замещения: append-only, доведённый до практики

Запись не удаляется и не переписывается — новая версия **замещает** старую типизированной связью `supersedes`, и история обходится запросом. У чтения есть режимы: `active` (по умолчанию — замещённое исключено), `latest` (устаревший id разрешается в текущую версию), `full_history`, `all`. Плюс типы связей `contradicts`, `implements`, `extends`, `references`, `related_to`.

Это то, чего у [[mem0]] не хватало после перехода на append-only (обе версии хранятся, но какая верна сейчас — не сказано), и то же, что делает [[zep-graphiti]] закрытием записи датой, только через граф связей.

### 4. `memory_absorb` — механизм, от которого Mem0 отказался

Основной способ записи. При сохранении факт автоматически проверяется на дубликаты, замещает устаревшее, связывается с похожим, а несколько новых фактов **сливаются в одну более богатую запись синтезом модели**. Исходы перечислены явно: дубликат — пропуск, обновление — новая запись плюс `supersedes`, противоречие — новая запись плюс `contradicts`, и так далее. Есть `dry_run=True` — посмотреть, что произойдёт, не записывая.

Это тот самый механизм, который [[mem0]] пробовал и бросил как ненадёжный на сотнях фактов. Memora страхуется тем, что ничего не теряется (замещённое лежит рядом и достаётся), но текущий вид памяти всё равно производится синтезом поверх записей — то есть петля пересказа не исключена, а сделана обратимой.

### 5. «Одна система памяти, а не две»

Весь `CLAUDE.md` проекта — 248 байт и одно правило:

> «Memora is the sole memory system for this project. Do NOT use Claude Code's built-in auto memory (MEMORY.md).»
>
> *Memora — единственная система памяти этого проекта. НЕ использовать встроенную auto-memory Claude Code.*

Тот же принцип, по которому в нашем `CLAUDE.md` записано не заводить параллельный список к `gaps-backlog.md`, и по которому 10.08 отклонён вариант с делами в хабе: два хранилища одного знания хуже одного.

## Что не взято

- **Установка и использование.** Решение 10.08: не ставить. Вика сама и есть слой памяти — в markdown, в git, читаемый человеком; Memora решает задачу для агентов, чья память непрозрачна, и добавила бы контекстный налог 22 инструментов на каждую сессию.
- **Устройство графа, RAG-чат, форматы экспорта** — ниже порога применимости, читались только по верхам.
- **Полный аудит кода не делался.** Прочитаны метаданные, README, `pyproject.toml`, `embeddings.py`, `backends.py`, `cloud_sync.py`, `skills/memora/SKILL.md`, `CLAUDE.md`, `SOUL.md`, релизные заметки — из тринадцати модулей три. «Закладок нет» не утверждается.

## Противоречия

**Причина аварии 0.3.0 названа неверно либо устарела.** Релизные заметки (10.08.2026) утверждают:

> «**OpenRouter serves no embeddings endpoint** — its catalogue lists 400 models and zero with an embedding task.»
> *OpenRouter не предоставляет эндпоинт эмбеддингов — в его каталоге 400 моделей и ни одной с задачей эмбеддинга.*

Проверка по официальной документации OpenRouter в тот же день, 10.08.2026: эндпоинт **есть** — `POST https://openrouter.ai/api/v1/embeddings`, «Generate vector embeddings from text and images», плюс отдельный `/embeddings/models` для списка доступных моделей, разделы в TypeScript/Python/Go SDK и кулинарная книга по RAG. См. [[openrouter]].

**Датировка закрыта 2026-08-11** ([[memora-openrouter-embeddings-dating]] — см. [[openrouter]]): официальный репозиторий `github.com/OpenRouterTeam/ai-sdk-provider` (прочитан напрямую) датирует появление поддержки эмбеддингов **2025-12-06**, минимум за 8 месяцев до релизных заметок Memora. **Механизм аварии от этого не страдает** — тихий откат на TF-IDF описан ими из первых рук и является главной ценностью материала. Но названная причина неверна не только «на сегодня», а на всём известном по источникам интервале: эндпоинт существовал ещё до того, как их хранилище начало ломаться «месяцами». Правдоподобнее — не проверили сам эндпоинт (например, обращались не туда или не тем способом), а не «эндпоинта нет».

## Оценка источника

Первоисточник высокого порядка: код и документация авторов, прочитанные напрямую, а не пересказ. Репозиторий живой — 366 коммитов, последний в день разбора, релиз v0.3.0 опубликован в тот же день.

Качество инженерной культуры выше среднего: код отказывается смешивать ключ одного провайдера с адресом другого («это отправило бы секрет одного сервиса на хост другого»), есть переключатель строгого режима вместо тихой деградации, релизные заметки честно открываются признанием собственной ошибки вместо списка новых возможностей.

Слабые места, названные прямо: **у организации-владельца пустой профиль** — ни имени, ни контактов, 2 репозитория, а сама организация создана 11.12.2025, позже репозитория, то есть репозиторий в неё перенесли. **CI отсутствует полностью** — папки `.github` нет, тесты в `tests/` есть, но никто автоматически не проверяет, что они проходят, ни на одной ОС. И один фактический промах уже найден (см. «Противоречия»).

## Проверка безопасности источника

Прочитанные файлы просмотрены на предмет инструкций, адресованных агенту. В `skills/memora/SKILL.md` — обычные указания по использованию инструментов (когда вызывать, какие режимы поиска), ничего похожего на попытку переопределить правила читающего агента. В `CLAUDE.md` и `SOUL.md` — правила для их собственного проекта, не для чужого.

Отдельно отмечу, потому что это меняет класс риска: репозиторий несёт **не только сервер, но и скилл, плагин Claude Code с `marketplace.json` и `install.sh`**. Это расширение агента, а не библиотека, — категория, по которой у вики есть цифра: prompt injection в 36% из 3 984 просканированных скиллов ([[ai-security-by-design]]). `install.sh` исполняется до того, как его успели прочитать; при установке (не планируется) конфиг прописывать руками.

Ещё: README рекомендует Cloudflare D1 и в примере вписывает `CLOUDFLARE_API_TOKEN` прямо в `.mcp.json` — файл, который обычно лежит в репозитории проекта. Прямое нарушение правила «секреты только в env, никогда в git».

По внешним ссылкам из репозитория ходил один раз — в документацию OpenRouter, чтобы проверить утверждение из релизных заметок.
