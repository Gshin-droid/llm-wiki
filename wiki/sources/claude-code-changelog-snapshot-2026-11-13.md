## Саммари

Ярус 2 рутины 1 (новости), следом за сводкой [[novosti-2026-11-16]]. Единственная новая версия с прошлого снапшота [[claude-code-changelog-snapshot-2026-11-12]] (v2.1.323) — v2.1.325 (14 добавлений, большой блок Changed, 88 багфиксов). Главное в этом релизе — не вектор атаки и не снятый лимит, а **изменение правил, по которым харнес сам разрешает себе действовать без присмотра**: автоматизация (scheduled tasks, `/loop`) и скиллы с объявленными правами теперь по умолчанию требуют явного разрешения, а не выполняются молча. Разбор доведён до прямой проверки на собственной конфигурации этой вики — редкий случай, когда новость из чужого changelog напрямую касается того, может ли сама эта вики продолжать вестись автономно.

## Что взято в вики

1. **Скилл с `allowed-tools`/хуками в шапке теперь спрашивает разрешение перед запуском в scheduled tasks/`/loop`, если его явно не внести в `permissions.allow`.** Цитата из раздела Changed: *«Scheduled tasks and `/loop` ask before running a skill that declares `allowed-tools` or hooks. Add `Skill(name)` to `permissions.allow` to run it unattended»*. До этой версии харнес запускал объявленный скилл в автоматическом прогоне так же, как и в интерактивной сессии — без отдельного вопроса сверх обычных правил на сами инструменты внутри скилла. Теперь факт объявления `allowed-tools`/хуков в самой шапке скилла — отдельный повод спросить разрешение именно в автоматизации, и ответить на этот вопрос может только присутствующий пользователь.

   **Прямая проверка на собственной конфигурации, не только пересказ формулировки.** Оба скилла этой вики объявляют `allowed-tools` во фронтматтере: `.claude/skills/wiki-ingest/SKILL.md` (Read/Write/Edit/Grep/Glob/WebFetch/WebSearch/AskUserQuestion/ограниченный Bash на `ingest.py`) и `.claude/skills/wiki-lint/SKILL.md` (тот же набор плюс `RemoteTrigger`, Bash на `lint_wiki.py`). Файл `.claude/settings.json` этого репозитория на момент разбора содержит в `permissions.allow` отдельные правила Read/Glob/Grep/конкретных Bash-команд (включая прямые вызовы `ingest.py`/`lint_wiki.py` через Bash) и несколько WebFetch/MCP-правил — записи вида `"Skill(wiki-ingest)"` или `"Skill(wiki-lint)"` там нет. Все три автономные рутины CLAUDE.md («новости», «практики», «хвосты») по описанию своей же работы вызывают эти скиллы инструментом Skill (а не только их скрипты напрямую через Bash) в рамках Cloud Routines — то есть scheduled tasks. Если версия харнеса, исполняющая Cloud Routines, уже это поведение или получит его при следующем автообновлении, у любой из трёх рутин есть шанс дойти до вызова `Skill(wiki-ingest)`/`Skill(wiki-lint)` и упереться в вопрос разрешения, на который в автономном прогоне ответить некому — то есть шаг рутины зависнет или будет пропущен без объяснения в её собственном логе (отличается от штатного «тихо, ничего не прошло порог»: это не решение рутины, а не доведённый до конца шаг).

   Решение, зачем это не исправлено прямо в этом же прогоне: правка `.claude/settings.json` — изменение операционной конфигурации репозитория, а не вики-факт, и не относится к роли рутины новостей («находит одна работа, закрывает другая» — тот же принцип, что для сверки с сырьём в CLAUDE.md, хоть и в другом контексте). Пункт действия — отдельная строка в `wiki/gaps-backlog.md`, с конкретной правкой (`"Skill(wiki-ingest)"`/`"Skill(wiki-lint)"` в массив `permissions.allow`) и условием проверки (следующий автономный прогон не должен упираться в вопрос разрешения).
2. **Bash-песочница по умолчанию перестала автоматически одобрять команды внутри песочницы.** *«Sandboxed Bash commands follow the normal permission flow by default. Set `sandbox.autoAllowBashIfSandboxed: true` to skip prompts»* — обратное прежнему поведению, где факт запуска внутри песочницы сам по себе снимал вопрос разрешения; теперь это отдельная настройка, которую нужно включить явно (в т.ч. managed-источником для организации). Рядом — *«Read-only git commands ask first in repositories that aren't the project's or one you trusted. Name the repository with `--add-dir`... to run them without prompts»*: раньше git-команды только на чтение в доверенных директориях не спрашивали вовсе, теперь спрашивают, если репозиторий не распознан как «свой». Оба изменения — не фикс конкретного обхода (не нумеруются узлом серии permission-bypass), а осознанное сужение дефолта того же общего направления, что разбирает [[ai-security-by-design]] весь последний квартал: автоматическое одобрение по категории («это же только чтение», «это же в песочнице») само по себе менее надёжно, чем явный список разрешённого.
3. **Малое, перенесено одной строкой без отдельного разбора:** security-фикс декодирования zstd-сжатых ответов (конкретный механизм не раскрыт changelog — упомянут в разделе Fixed без деталей); `EnterWorktree` отказывает в пути `WorktreeCreate`-хука, идущем через символическую ссылку внутри проекта (тот же класс путаницы «куда на самом деле идёт запись», что у symlink-grant из прошлого снапшота); сэндбокс отказывает в sandboxed-записи в `.claude`-настройки/скиллы/агенты/хуки даже в добавленных директориях; `claude plugin validate` теперь находит и репортит небезопасные пути/ссылки при загрузке плагина.

## Берём инструмент или логику

Инструмент (сам Claude Code) уже стоит — вопрос «ставить или нет» не возникает. Логика: это прямой кейс, когда новость из changelog требует не просто записи на страницу продукта, а проверки собственной работоспособности — сделано пунктом 1 выше, с конкретным незакрытым разрывом (отсутствие `Skill(...)` в `permissions.allow`), вынесенным в `wiki/gaps-backlog.md`, а не оставленным как факт на странице источника. Более общий урок для [[zabor-i-stena-prava-agenta]]: список `permissions.allow` — забор, который вендор дополняет новыми категориями правил без предупреждения конкретного владельца конфигурации; единственный способ не отстать — читать changelog на предмет новых форм правил (`Skill(name)` — новая форма рядом с `Bash(...)`/`Read(...)`), а не предполагать, что старый список останется достаточным.
