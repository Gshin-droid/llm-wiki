## Саммари

PAIR (Personal AI Router) — бесплатная программа NVIDIA, которая находит в локальной сети машины с RTX, DGX Spark и свежими Mac, и раздаёт между ними запросы к локальным моделям. Приложение обращается к одному адресу, PAIR решает, на какой машине запрос выполнить.

**Главное уточнение, без которого материал понимается неправильно: это маршрутизатор, а не кластер.** Каждый запрос целиком исполняется на **одном** выбранном узле. PAIR не разрезает запрос между видеокартами и **не складывает их видеопамять**. Модель, которая не влезает в один узел, не станет запускаться оттого, что рядом стоит вторая машина. Выигрыш — в параллельности задач, а не в размере модели: пока один агент занял домашнюю машину, второй уходит на свободную.

Сам вывод PAIR не делает — модели по-прежнему исполняют **Ollama или LM Studio**. PAIR только обнаруживает узлы, следит за их готовностью, ставит задачи в очередь и возвращает ответы.

## Как выбирается узел

Планировщик фильтрует спаренные системы по четырём признакам: готовность и доступность узла; наличие на нём движка вывода (Ollama или LM Studio); **наличие запрошенной модели именно на этом узле**; текущая загрузка и утилизация GPU.

Третий пункт практически важен: одинаковый набор моделей на всех машинах не требуется, но запрос уйдёт только туда, где нужная модель уже скачана. То есть «один адрес на весь дом» работает ровно в той мере, в какой модели заранее разложены по машинам.

## Совместимость и установка

- Узлы: Windows-машины с GeForce RTX (серия 20 и новее), DGX Spark/GB10, Mac M4 и новее, Linux с RTX.
- Требования: Windows 11 / DGX OS / Ubuntu / macOS Tahoe; от 8 ГБ ОЗУ, рекомендуется 20+ ГБ на диске. Интернет нужен только чтобы скачать модели, сама работа идёт без него.
- Приложение настраивать не надо — PAIR выдаёт **Ollama-совместимую и LM Studio-совместимую** точку входа. В программе меняется только базовый URL, нового API нет.
- Статус: публичная бета, версия на 09-22 бралась из вторичной выдачи как **v0.1.1**; допроверка 09-24 по CHANGELOG.md репозитория нашла **0.1.5** — подписанные установщики под все три ОС, графический и терминальный интерфейс.
- **Исходный код открыт, лицензия Apache 2.0**, репозиторий `NVIDIA/Personal-AI-Router`. Сама страница продукта про лицензию молчит — установлено по репозиторию и техническому блогу, подтверждено дословно допроверкой 09-24.

## Безопасность

Обнаружение узлов — mDNS в локальной сети. Спаривание подтверждается человеком и образует доверенный набор узлов. Трафик между узлами шифруется **mTLS** с генерируемыми сертификатами и остаётся внутри локальной сети.

Отсюда и цена приватности: PAIR имеет смысл ровно там, где локальная модель уже выбрана ради того, чтобы данные не уходили наружу. Для облачных моделей он бесполезен.

## Когда бесполезен — по признанию авторов

- Задачи **строго последовательные** или состоящие из одного длинного запроса: распределять нечего, выигрыш минимален.
- Бета «специфична к конфигурации» — набор проверенных сочетаний железа и ОС ограничен.
- Не увеличивает доступную видеопамять (см. выше).
- **Требует, чтобы машины были в одной локальной сети.** Машины в разных сетях PAIR не объединит: обнаружение идёт по mDNS.

## Что взято в вики

1. Новая сущность [[nvidia-pair]] — что это, как выбирает узел, границы применимости.
2. **Различение «маршрутизатор ≠ кластер»** → [[delegirovanie-deshevym-modelyam]], ступень 1 (локальная модель): объединение машин не поднимает потолок размера модели, потолок задаёт самая мощная одиночная видеокарта.
3. Ollama-совместимая точка входа как **фактический стандарт локального вывода** — туда же: приложение, умеющее обращаться к Ollama, автоматически умеет обращаться и к PAIR.

## Допроверка 2026-09-24: README и docs/ прочитаны напрямую

Ежедневный процесс закрытия пробелов. Прямое чтение `README.md`, `CHANGELOG.md` и `docs/architecture.mdx` репозитория `NVIDIA/Personal-AI-Router` (`raw.githubusercontent.com`, ветка **`develop`** — не `main`, дефолтная ветка репозитория) закрывает три вопроса пункта бэклога.

**Конфигурация узлов — не файл, а интерфейс.** README не описывает файл конфигурации вообще: спаривание идёт через приложение, `Settings → Cluster`, по **шестизначному PIN** («the inviting machine shows a six-digit pairing PIN, and you enter that PIN on the machine you invited»), отдельные параметры узла — через `Engine settings`. Три ОС названы прямо совместимыми друг с другом («Windows, Linux, and macOS nodes... can all be paired with each other»).

**Лимита на одновременные задачи в README нет, но есть локальный механизм от перегрузки.** Дословная цитата `docs/architecture.mdx`: *«each proxy adds the requests it has just dispatched itself to its own estimate and reserves its choice before forwarding, so a burst spreads without waiting for those reports»* — каждый прокси резервирует свой выбор узла ещё до отправки запроса, поэтому всплеск запросов расходится по узлам сам, не дожидаясь обратной связи о загрузке. Жёсткого числового лимита на узел не названо.

**Что происходит при отпадании узла — не посреди запроса, а до его начала.** *«One request goes to one node and the proxy never splits it»* — если узел уже начал отвечать, разделения или переноса нет вовсе, что подтверждает уже известное «маршрутизатор, не кластер» с новой стороны. Но **выбор узла заранее устойчив к отказу**: PAIR формирует **упорядоченный список failover**, а не одного победителя — сначала узел, закреплённый вручную через терминальный интерфейс, затем по приоритету планировщика (нагрузка GPU переводится в давление 0–3 по порогам 40/70/85%, сортировка «сначала по очереди, затем по давлению, затем по ID узла»), затем остальные по стабильному ID. Отказ различается по типу: *«if that owner answers inference with `404`, the proxy treats it as retryable and moves to the next advertised owner»* — повтор на следующий узел списка; *«genuine client errors such as `400` or `422` are not retried, because they would fail identically everywhere»* — не повторяются вовсе; протухший узел из инвентаря отвечает локальным `502` без обращения к движку.

**Побочная находка, не входившая в вопрос пункта.** README называет три режима совместимости, а не два: *«presents local proxy endpoints for Ollama-compatible, OpenAI-compatible, and Anthropic Messages API requests»* — помимо Ollama/LM Studio (уже известных), PAIR отдаёт и точку входа, совместимую с Anthropic Messages API. Не проверено предметно (какие заголовки/поля поддержаны, есть ли ограничения) — самостоятельный лид, не критичный, отдельным пунктом бэклога не заводится ввиду низкой практической значимости (узлы всё равно исполняют локальные модели через Ollama/LM Studio, а не Claude).

**Не взято, остаётся открытым.** Замеров производительности (сколько задач в параллель реально выдерживает связка) ни README, ни `docs/architecture.mdx`, ни технический блог не приводят числом — цифр в вики по-прежнему нет намеренно.

## Оценка источника

Пост-наводка передал суть верно и дал ссылку на официальную страницу. Две неточности, обе в сторону преувеличения: «превратить в личный ИИ-кластер» и «распределять инференс между несколькими видеокартами» — читается как объединение видеопамяти, которого нет. Формулировка технического блога прямо противоположна: *«PAIR does not split requests across multiple GPUs or merge VRAM»*. Это та же системная черта канала, что и в [[nvidia-sol-pi-harness]]: цифры и ссылки верные, ограничение опущено.

## Проверка безопасности источника

Пост инбокса прочитан целиком. Инструкций, адресованных агенту, не обнаружено, промо-нагрузки нет. По ссылкам ходил: страница продукта на `nvidia.com`, технический блог `developer.nvidia.com`, поисковая выдача по репозиторию `NVIDIA/Personal-AI-Router`. Ничего не устанавливалось: PAIR — программа, слушающая сеть и принимающая задачи от других машин, решение о её установке за пользователем.
