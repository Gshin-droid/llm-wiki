## Что это

Открытый протокол (Apache-2.0, ★4,7 тыс. на 18.11) связи **клиента** (редактор, пульт, свой скрипт) с **агентом для кода**. Устройство по `docs/get-started/architecture.mdx`:

- клиент запускает агента дочерним процессом, обмен — JSON-RPC через stdin/stdout;
- одно соединение держит несколько сессий одновременно;
- агент шлёт клиенту поток обновлений (уведомления) и **сам запрашивает у клиента разрешение на вызов инструмента** — решение принимает клиент;
- MCP-серверы клиента передаются агенту конфигурацией; свои инструменты клиент может отдать как MCP через маленький посредник;
- типы данных по возможности взяты из MCP.

Совместимость определяется версией протокола, согласованной при `initialize`, а не версией библиотеки. Официальные библиотеки — Python, TypeScript, Rust, Kotlin, Java.

Принцип «Trusted» из той же страницы: протокол рассчитан на модель, которой доверяют, — *«the code editor gives the agent access to local files and MCP servers»* (редактор даёт агенту доступ к локальным файлам и MCP-серверам). **Изоляции агента протокол не даёт.**

По ACP говорят, среди прочих: [[opencode]], [[pi-coding-agent]] и его форк OMP, [[deepseek-harness]] (`--profile acp`), MiniMax Code, T3 Code (пульт, см. [[obolochki-agentov-chto-berem]]).

## Адаптер для Claude

`claude-agent-acp` (Apache-2.0, ★2,8 тыс.) делает Claude Code агентом ACP через официальный Claude Agent SDK: разрешения на инструменты, вложенные журналы субагентов, терминалы, слэш-команды, MCP клиента. Две детали из README, важные на практике:

- если указать свой бинарник `claude` через `CLAUDE_CODE_EXECUTABLE`, MCP-серверы сессии вместе с `env` и `headers` уходят в командную строку — **их видят другие пользователи машины**; встроенный в архив бинарник получает их через stdin;
- работа идёт через Agent SDK, а по открытому багу из [[claude-code]] (раздел «Тарифы», #97074) Agent SDK расходует пятичасовое окно подписки примерно в 1,8 раза быстрее интерактивной сессии. Какую метку точки входа ставит адаптер — не проверено.

## Берём инструмент или логику

**Инструмент — пока нет, сначала проба.** Ставить нечего «вообще»: ACP — протокол, его берут вместе с задачей. Задача у нас есть — «коробка» для недоверенного агента на локальной модели. Проба: скрипт на Python-библиотеке ACP запускает [[opencode]] с моделью из Ollama и получает от него хотя бы один запрос разрешения на инструмент. Удалась — ACP становится пультом коробки: задача туда, отчёт и запросы разрешений обратно, решение по белому списку принимает наш код.

**Логика, которая переносится:** разрешение решает клиент, а не агент. Это «стена» из [[zabor-i-stena-prava-agenta]] — но только для вызовов, которые агент сам отправил через протокол. Команды в обход протокола клиент не видит, поэтому песочница (WSL, контейнер) остаётся обязательной отдельно.

**Не берём:** схему «управлять харнессом через экран» из наводки — хрупко и лишнее при живом протоколе.

## Проба (2026-11-18)

Своя проба по плану из раздела выше. **Ответ — да:** скрипт на Python-библиотеке ACP (`agent-client-protocol` 1.0.0) запустил [[opencode]] 1.19.5 дочерним процессом в песочнице WSL, модель — qwen3:8b из Ollama с окном 16 тыс. токенов. В конфиге OpenCode правка файлов и команды стояли в режиме `ask`; задача — «создай файл hello.txt, потом выполни `ls`».

- Агент прислал два запроса `session/request_permission`: на правку (`kind: "edit"`) и на команду (`kind: "execute"`). В каждом — три варианта ответа: `allow_once`, `allow_always`, `reject_once`.
- **Клиент видит, что именно будет сделано, до решения:** в запросе на правку — полный diff нового содержимого, в запросе на команду — сама команда. Белый список можно строить не только по виду инструмента, но и по пути и тексту команды.
- Скрипт оба раза ответил отказом. Агент пометил вызовы как `failed` с текстом «The user rejected permission…», в обход не пошёл, других инструментов не вызывал, закончил ход (`end_turn`). Файла не появилось.
- Сырой поток JSON-RPC клиент пишет наблюдателем: `spawn_agent_process(..., observers=[cb])`.

Что выяснилось попутно:

- **Слабое место — маленькая модель, а не протокол.** qwen3:4b с тем же конфигом не вызвала ни одного инструмента: в рассуждении видно, что инструменты она заметила, но запуталась в правилах системного промпта OpenCode (около 6,3 тыс. токенов) и ответила текстом. Промпт не обрезан — проверено по журналу Ollama. qwen3:8b справилась с первого раза.
- **Запросы приходят только для инструментов в режиме `ask`.** Инструмент, разрешённый в конфиге без вопроса, клиент не увидит вовсе. Какие инструменты OpenCode разрешает по умолчанию (вероятно, чтение) — не сверено ни с документацией, ни прогоном; для «коробки» надёжнее выставить `ask` на всё.
- **OpenCode сам ходит в сеть:** при первом запуске скачал каталог моделей models.dev. Для «коробки» сеть закрывается отдельно — ACP этого не даёт, как и сказано в принципе «Trusted».
- **Ловушка среды:** Ollama на Windows по умолчанию слушает только петлю (127.0.0.1), а WSL в сетевом режиме NAT — отдельная сеть, поэтому из песочницы модель не видна. Решили пробросом порта на адрес хоста во внутренней сети WSL с правилом брандмауэра только для этого интерфейса; отброшены `OLLAMA_HOST=0.0.0.0` (модель открывается всей локальной сети) и зеркальный сетевой режим WSL (песочница видит все порты хоста).
- Ветку «разрешить» прогоном не проверяли: вызовов чтения агент не делал.

Вывод для «коробки»: ACP годится пультом — задача туда, запросы разрешений обратно, решает наш код. Песочница и закрытая сеть остаются обязательными отдельно.
