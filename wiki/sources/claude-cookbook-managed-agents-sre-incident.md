## Саммари

Третий и последний из трёх applied-примеров пункта бэклога «Managed Agents cookbooks» (заведён 2026-08-17, гайдовая часть 16/16 закрыта 2026-09-01, первый и второй applied — [[claude-cookbook-managed-agents-data-analyst]] и [[claude-cookbook-managed-agents-slack-bot]]). Этим нотбуком **пункт бэклога закрыт полностью — 16/16 гайдовых + 3/3 applied**. Сценарий: продакшн-алерт будит агента ночью — тот читает логи, находит рантбук, исправляет Kubernetes-манифест, открывает PR и ждёт одобрения человека перед мёржем. В отличие от первых двух applied-примеров (сборка вокруг уже известных примитивов), здесь впервые в одном сценарии сведены три механизма, которые раньше вики видела порознь: Skills API как загружаемый (не репозиторный) скилл, кастомные тулы для рабочего процесса (open PR → approve → merge) и polling-цикл вокруг `requires_action` как альтернатива стримингу событий.

## Что взято в вики

- **PagerDuty/GitHub/Datadog — заглушки на локальных фикстурах, не реальные интеграции.** Сам нотбук прямо об этом говорит: `"PagerDuty, GitHub, and Datadog are mocked with local fixtures so you can focus on the Managed Agents pieces"`. Обработчик вебхука вызывается напрямую с JSON-фикстурой вместо реального HTTP-запроса от PagerDuty — payload вебхука становится первым `user`-сообщением агенту. Это не платформенный примитив, а честно названное ограничение демонстрации: показывает форму интеграции, не реальное соединение.
- **Skill через Skills API upload, а не через смонтированный репозиторий.** Отличается от механизма на [[claude-cookbook-managed-agents-skills-geo]] (харнес сканирует `.claude/skills/` подключённого `github_repository`) — здесь скилл создаётся программно и передаётся агенту при создании: `skills=[{"type": "custom", "skill_id": skill.id, "version": skill.latest_version}]`. Содержит конвенции команды по рантбукам — куда смотреть и что проверять перед инфраструктурными изменениями. Первый на странице источника пример реального использования Skills API upload (эндпоинт упоминался как факт спецификации на [[claude-skills]], но не был показан в работающем коде managed-agents).
- **Три кастомных тула вместо готового примитива под рабочий процесс PR.** `open_pull_request` (title/body/diff), `request_approval` (summary) и `merge_pull_request` (pr_number) — отдельные тулы, а не единый `escalate()`/`decide()` из [[claude-cookbook-managed-agents-hitl-multiagent]]. Показывает, что человеко-контролируемый рабочий процесс собирается из нескольких простых кастомных тулов под конкретную задачу, а не обязан использовать многоцелевой примитив.
- **Polling вместо стриминга как альтернативный паттерн ожидания approval.** `run_until_approval_or_end()` циклически опрашивает событийный лог сессии, пока не встретит вызов `request_approval` (возвращает его `event_id`, чтобы вызывающий код мог на него ответить) или пока сессия не завершит ход. Ответ человека отправляется как `user.custom_tool_result` с решением в JSON. Нотбук отдельно поясняет, что тот же контракт применим и к продакшену: `"In the Slack version this send happens in your button-click handler — the payload is identical"` — polling здесь учебное упрощение конкретно этого нотбука, механизм подстановки ответа тот же, что был бы у стриминга.
- **`limited`-networking cloud environment.** Явно названная причина: `"A limited-networking cloud environment is enough because the agent only needs its own filesystem"` — три ресурса (логи checkout-сервиса, Kubernetes-манифест деплоя, OOM-рантбук) монтируются через Files API как `resources` по фиксированным путям, внешние репозитории не клонируются вообще. Первый явный пример, где сетевой доступ агента сознательно сужен до нуля через выбор типа environment, а не через `allowed_domains`/`blocked_domains` (тот механизм — из [[claude-code-changelog-snapshot-2026-08-22]]/раздел «Домен-фильтр» на [[claude-managed-agents]]).
- **Модель нотбука — `claude-opus-4-6`.** Не входит в семейство Opus/Sonnet 5, которое видно в большинстве кусков пункта бэклога, и отличается от `claude-sonnet-4-6` первого applied-примера — зафиксировано как факт конкретного примера, не общая рекомендация.
- **Финал: PR реально смёржен.** `"Status: MERGED (PR #1)"` — агент увеличил memory limit контейнера с 128Mi до 512Mi. Итоговая ячейка называет три интеграции, нужные для реального продакшена поверх этой демонстрации: кнопки одобрения в Slack, доступ к GitHub через MCP-сервер, живой фетч логов из Datadog — то есть сам нотбук маркирует границу между демо и продакшн-версией явно, не оставляя её подразумеваемой.

## Что не взято / лиды

Нотбук не даёт количественных метрик (стоимость, число шагов, сравнение с ручной работой инженера) — раздел «Оценка источника» пункта бэклога про экономику координатора ([[claude-cookbook-managed-agents-mongodb-planbig]]) этим нотбуком не пополняется. Не разобран отдельно код настройки трёх Slack-кнопок одобрения (approve/deny/details) — упомянут в финальном разделе одной строкой, без кода; при возврате к теме кандидат на отдельную допроверку. Пункт бэклога «Managed Agents cookbooks» закрыт этим нотбуком полностью — новых applied-примеров или гайдовых нотбуков в директории `managed_agents/` не осталось (подтверждено предыдущей полной сверкой листинга директории 08-20).
