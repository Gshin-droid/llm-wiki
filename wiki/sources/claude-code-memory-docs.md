## Саммари

Закрывает пробел из `wiki/gaps-backlog.md`: механика **auto-memory**, оставленная нераскрытой в [[anthropic-context-engineering-claude-5]] (та статья ограничилась фразой «Claude automatically saves memories that are relevant to the work and to you»). Официальная страница даёт полную картину: формат хранения, область видимости, поведение при конфликте с `CLAUDE.md`, и — что важно — **не упоминает** memory tool из Claude API вообще, то есть это независимые механизмы, не одна фича под двумя именами.

## Ключевые факты

**Формат и место хранения.** `~/.claude/projects/<project>/memory/` — директория с файлом-индексом `MEMORY.md` (грузится в каждую сессию) и опциональными тематическими файлами (`debugging.md`, `api-conventions.md` и т.п., грузятся по требованию через обычные файловые инструменты, не при старте). `<project>` определяется по git-репозиторию — все worktree и поддиректории одного репо делят одну директорию памяти; вне git — используется корень проекта. Путь настраивается через `autoMemoryDirectory` в settings.json.

**Область видимости.** Machine-local и per-repository — **не** per-project/user/global в смысле трёх раздельных уровней, как у `CLAUDE.md` (managed/user/project/local). Один уровень: репозиторий на конкретной машине. Между машинами и облачными окружениями файлы памяти не синхронизируются.

**Лимит на что грузится.** Только `MEMORY.md`, и только первые 200 строк или 25KB (что раньше). Превышение лимита не блокирует запись, но Claude Code возвращает ошибку с требованием переписать индекс компактнее — то, что за пределами лимита, на следующей загрузке просто отбрасывается. `CLAUDE.md`-файлы в этот лимит не попадают — грузятся целиком независимо от размера.

**Область памяти субагентов.** Auto-memory главного диалога **не** передаётся субагентам (кроме `/fork`, который наследует родительский диалог целиком). У субагента может быть своя, отдельная директория auto-memory через поле `memory` в его конфигурации.

**Включение/выключение.** По умолчанию включено. Тумблер — `/memory` в сессии (пишет `autoMemoryEnabled` в `~/.claude/settings.json` или в `.claude/settings.json` проекта) или переменная `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1`.

**Конфликт с `CLAUDE.md` — прямого правила нет.** Страница не описывает отдельную процедуру разрешения конфликта auto-memory vs `CLAUDE.md`. Общий принцип, данный для конфликта *между несколькими `CLAUDE.md`-файлами*, по формулировке страницы распространяется и на память: «Both are loaded as context, not enforced configuration» — то есть оба источника равно необязательны к исполнению, конфликтующие инструкции Claude может разрешить произвольно. Единственный способ гарантированно исполнить правило независимо от решения модели — hook (`PreToolUse` и т.п.), а не память любого типа.

**Отношение к memory tool в Claude API ([[claude-memory-tool]]).** Страница про auto-memory **не ссылается** на memory tool и не упоминает его вообще — они не описаны как варианты одного механизма. Структурная параллель (индекс-файл + тематические файлы, just-in-time подгрузка по требованию) есть, но это архитектурное сходство двух независимых реализаций одной идеи, а не общий код: memory tool — API-примитив, который разработчик подключает к своему агенту и сам решает, где и как хранить данные (Anthropic данные не видит); auto-memory — встроенное в сам продукт Claude Code поведение, хранилище фиксировано (`~/.claude/projects/...`), управляется настройками CLI, а не кодом приложения. Этот вывод — синтез при чтении обеих страниц, не цитата ни с одной из них.
