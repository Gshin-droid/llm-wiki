## Что взято в вики

**`CMA_with_mongodb_atlas.ipynb` (fraud review agent):**
- Три способа подключить внешнюю БД к managed-агенту, раньше на странице не различавшихся: **Path A — host-side custom tool** (рекомендуемый; секрет БД никогда не попадает в сэндбокс, `custom`-тул останавливает сессию через `requires_action`, хост-процесс сам выполняет запрос `pymongo` и шлёт `user.custom_tool_result`); **Path B — `pymongo` внутри self-hosted sandbox** (клиент БД живёт прямо в сэндбоксе, если инфраструктура своя); **Path C — self-hosted MongoDB MCP-сервер за HTTPS**, зарегистрированный как `mcp_toolset`. Тот же выбор («секрет у приложения» vs «секрет в сэндбоксе» vs «через MCP») применим к любой внешней системе, не только MongoDB — общий паттерн для интеграций.
- Одна БД вместо трёх-четырёх систем: `$vectorSearch` (семантика), `$search` (BM25 full-text), `$rankFusion` (гибрид через reciprocal rank fusion, **требует MongoDB 8.0+**; каждый текущий Atlas-кластер, включая бесплатный M0, уже на 8.0+), `$graphLookup` (граф-обход цепочки sender→recipient для колец мошенничества).
- **Новый протокол, не встречавшийся в вики: AP2 (Agent Payments Protocol)** — открытый протокол для платежей, инициируемых агентом (`github.com/google-agentic-commerce/AP2`). Tamper-evident подписанные объекты (Checkout Mandate + Payment Mandate); агент обязан вызвать `verify_mandates` **первым шагом**, до любого поведенческого анализа, и при `valid=false`/`constraints_satisfied=false`/`double_spend_detected=true` отклонить транзакцию немедленно, не проверяя остальное. Жёсткий гейт, а не рекомендация — так прописано в системном промпте демонстрационного агента.
- Human-in-the-loop здесь — не абстрактный пример, а конкретное бизнес-правило в системном промпте: обязательный `escalate()` при сумме $4,900–$4,999 (structuring — сумма чуть ниже порога отчётности), сумме ≥$50,000, срабатывании `detect_fraud_ring`, или средней уверенности агента (75–85%) — количественные пороги эскалации, которых не было ни в одном прошлом куске.
- `transactions` (операционная запись, статус меняется pending→approved/rejected), `transaction_decisions` (неизменяемые вердикты) и `audit_events` (append-only трейл) — три отдельные коллекции одного кластера как система записи; тот же принцип, что у memory stores ([[claude-cookbook-managed-agents-production-memory]]), только для аудита решений, а не для памяти о пользователе.

**`CMA_plan_big_execute_small.ipynb`:**
- Первое прямое измерение экономики мультиагентной координации на этой странице: команда «дорогой координатор + дешёвые воркеры» вышла **примерно в 2.5 раза дешевле и в 3 раза быстрее** сольного прогона той же задачи одной дорогой моделью, при этом **84–98% входных токенов команды посчитаны по цене воркера**, не координатора — раньше на странице было известно только *что* toolset можно урезать по роли, не *насколько* это дешевле.
- Конкретная связка моделей: координатор — `claude-fable-5`, воркеры — `claude-sonnet-5`. Координатор в этом ноутбуке **не имеет собственных тулов вообще** (ни `web_search`, ни `web_fetch`) — только поле `multiagent`; это и есть, по тексту источника, определяющее свойство роли координатора: «The coordinator has no tools of its own — only a `multiagent` roster naming the worker. That one field is what makes it a coordinator.»
- **Новый параметр сессии, не встречавшийся раньше: `budget`.** `client.beta.sessions.create(..., budget={"type": "limit", "max_list_cost": {"currency": "USD", "amount": "1000"}})` — жёсткий потолок на суммарную стоимость (по публичным list-ценам) всей команды, всех потоков сразу, задаётся на уровне сессии при её создании, а не только замеряется постфактум.
- **Новая единица метрики: `usage.list_cost`.** И у сессии (`sessions.retrieve(...).usage`), и у каждого потока (`sessions.threads.list(...)`) — накопленная стоимость по публичным ценам листинга, отдельно от количества токенов. Раньше на странице был известен только сам объект `usage` без этого поля.
- Новый тип события: `agent.thread_message_sent` (координатор → воркер) — рядом с уже известным `agent.thread_message_received` (воркер → координатор, добавлен 08-20). Пара событий делает делегирование видимым в обе стороны в стриме, не только ответ.
- Системный промпт координатора называет два инструмента координатора по имени, которых раньше на странице не было — `create_agent` (спавн воркера) и `send_to_agent` (дослать воркеру уточнение), плюс обязательный `wait_for_agents` перед выводом: «ALWAYS call wait_for_agents after spawning before drawing any conclusion» — синхронизация параллельных воркеров явно вменена промптом, не гарантирована платформой автоматически.
- **Не подтверждено первоисточником отдельно, стоит проверить:** конфигурация окружения использует `config={"type": "anthropic_cloud", ...}` — во всех прошлых кусках (включая практический пример на самой странице [[claude-managed-agents]]) тип облачного environment везде записан как `"cloud"`, не `"anthropic_cloud"`. Может быть опечаткой/устаревшим значением конкретного ноутбука, а не переименованием типа платформой — release notes про переименование не проверялись в этот заход, отдельно не подтверждено.
