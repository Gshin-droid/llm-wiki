## Саммари

Команда прогоняет плагин или скилл по набору тестовых случаев и ставит оценку; по умолчанию каждый случай идёт дважды — с плагином и без, разница показывает, что плагин дал на самом деле. Разобран вместе с пользователем и сразу опробован на собственном скилле. Для вики главное: это **второй уровень проверок** из [[verification-three-levels]] — замер на эталонных задачах, — до сих пор не применявшийся к своим скиллам, теперь встроенный в инструмент.

## Как устроено (по документации)

- **Случай** — папка в `evals/`: `prompt.md` (просьба пользователя, в шапке — лимит ходов, инструменты, модель) и `graders/` — по файлу на проверяющего.
- **Проверяющие:** `regex` (по ответу, журналу или файлу), `tool_used` (вызван ли инструмент или скилл, сколько раз), `tool_order`, `file_exists`, `llm` (вердикт модели-судьи, 2 голоса из 3), `baseline` (не хуже эталонного журнала). Первые четыре бесплатны и стабильны; судья стоит денег и колеблется — документация советует его только для коротких ответов. Своего кода в проверяющих нет.
- **Сравнение «с плагином / без»** (Δ). Высокая оценка сама по себе ничего не доказывает: Claude мог справиться и без плагина. Проверяющие, которые без плагина пройти не могут («вызван ли скилл»), из счёта обоих плеч исключаются, чтобы не завышать Δ; `--ablation none` оставляет одно плечо и вдвое удешевляет.
- **Изоляция прогона:** временные домашняя и рабочая папки, отдельные настройки; не грузятся пользовательские настройки, хуки, `CLAUDE.md`, память, другие плагины и скиллы. Инструменты по умолчанию — только чтение; Bash, Write, сеть — только явной выдачей, Bash тогда в песочнице; прогоны не спрашивают разрешений. Хуки и MCP-серверы самого плагина выполняются вне песочницы — поэтому чужие плагины оценивать только в контейнере.
- **Цена:** настоящие вызовы модели из лимита подписки или счёта API; случаи × прогоны (по умолчанию 3) × 2 плеча + по 3 вызова судьи. Ограничители: `--runs`, `--ablation none`, `--max-cost-usd`.
- Для CI: `--json`, `--threshold`, закреплённые модели, коды выхода (0 — прошло, 1 — ниже порога, 2 — упёрлись в потолок цены).

## Проверка на практике (2026-10-19)

**Задача:** срабатывает ли собственный скилл-конвейер проектов сам, когда пользователь говорит о новом деле своими словами — известная боль: подсказчик ловит слова, но на непривычной формулировке молчит.

**Набор:** 5 случаев — 3 положительных (прямая фраза из описания скилла; «отчёт руками каждую пятницу — нельзя ли автоматизировать»; мимоходом посреди другой работы) и 2 отрицательных (ошибка Python, справочный вопрос). Проверяющий один, бесплатный: `tool_used: Skill` с именем скилла; у отрицательных — `min: 0, max: 0`. Скилл — в копии, упакованной учебным плагином; настоящий не менялся. По 1 прогону, одно плечо.

| Прогон | Итог | Цена по ценам API |
|---|---|---|
| Скилл один | 5/5 — три срабатывания, два молчания | $0,46, 74 с |
| **Проверка проверки:** описание скилла нарочно заменено на «только для CSV» | 0/3 положительных — проверяющий настоящий | $0,18, 41 с |
| Скилл + рядом настоящий superpowers (его вступление требует сначала вызывать `brainstorming`) | 5/5 — выбран конвейер, а не конкурент; присутствие superpowers подтверждено по журналу прогона | $0,49, 75 с |

**Вывод:** описание скилла справляется и с непривычной формулировкой, и с прямым конкурентом; ложных срабатываний нет. Ограничения: по одному прогону на случай (разброс не измерен), 5 случаев, модель по умолчанию, в прогоне нет пользовательского `CLAUDE.md` и других скиллов машины. Набор сохранён локально для перезапуска после правок описания.

**Два препятствия по ходу:** подгружать второй плагин можно только изнутри проверяемой папки (защита «containment root») — конкурента пришлось скопировать внутрь; удаление временных папок с путём в переменной оболочки защита Claude Code не пропускает — копировали в новые папки вместо пересоздания.

## Берём инструмент или логику

- **Инструмент — да, встроен, ставить нечего.** Цена — лимит: пробный прогон набора из 5 коротких случаев ≈$0,5 по ценам API. Обратимо полностью: набор — папка с markdown-файлами.
- **Логика:** перед правкой описания скилла — набор «должен сработать / не должен», после правки — тот же набор. Это правило спуска в действии: проверка срабатывания скилла переезжает с глаз пользователя на замер.

## Что не взято / лиды

- Судья-модель (`llm`) и сравнение с эталонным журналом не опробованы — для проверки срабатывания не нужны.
- Встроенная проверка скилла `skill-creator` устроена похоже, но формат случаев другой, наборы друг друга не читают — не сравнивалась.
- Работает ли на Windows песочница для Bash в прогонах — не проверено (набор обошёлся только чтением).
