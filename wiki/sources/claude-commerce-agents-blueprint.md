## Саммари

Пункт бэклога, заведённый 2026-09-07 при поисковом прогоне рутины практик (замечен в одной связке со [[claude-cookbook-scheduled-repository-reviewer]], но не разобран содержательно в тот день). Репозиторий — не туториал и не cookbook-ноутбук, а полноценный эталонный проект: два агента (шоппинг для покупателя, мерчант для персонала магазина), каждый определён один раз (промпт, скиллы, контракты тулов, гейты) и исполняется на трёх разных рантаймах — Messages API, [[claude-agent-sdk|Claude Agent SDK]] и [[claude-managed-agents|Managed Agents]] — через общий слой `commerce-common/`. Четыре вертикали (retail, travel, telecom, entertainment) показывают одну и ту же пару агентов на разных доменах, не четыре разных продукта.

Дословный дисклеймер репозитория: «Every company, brand, product, and person here is fictional; the only company is ACME. Nothing places an order, charges a card, or changes a live listing: `checkout` renders the cart for the host to complete, and every merchant write is staged until a person approves it.» Официально не поддерживается и не принимает контрибьюций — учебный/референсный статус, не продакшн-сервис Anthropic.

## Что взято в вики

**Один агент, три рантайма — не абстракция, а буквально общий код.** README называет разделение явно: `commerce-common/` (конфиг, fencing, память, скиллы, grounding, presentation, executor) — общий пакет, `shopping-agent/core/` и `merchant-agent/core/` — типы и интерфейсы бэкенда (`StorefrontBackend`/`MerchantBackend`), а `runtime-messages-api/`, `runtime-agent-sdk/`, `managed-agents/` — три тонких адаптера поверх одного и того же `core`. Практический вывод для собственной инженерии агентов: граница «что делает агент» и «на чём он исполняется» может быть проведена так, что вторая меняется, а первая — нет; сейчас на [[claude-managed-agents]] описан путь «прототип на Agent SDK → продакшн на Managed Agents» как последовательная миграция, здесь показана альтернатива — держать оба рантайма одновременно на одном ядре.

**Safety-гейты живут в исполнителе тула, а не в промпте или рантайме — и поэтому работают одинаково на всех трёх путях.** Дословно из `docs/safety.md`: «A rule enforced inside a tool call holds on all three paths, because the Messages API runtime, the SDK toolset, and the MCP server execute tools through the same executor (`commerce_common/execution.py` and each role's `executor.py`). A rule enforced on the turn lives in a runtime; its row names the paths.» Это отвечает на вопрос, который в вики раньше не был сформулирован явно: гейт, зависящий от рантайма (бюджет анализа, grounding, memory extraction), можно обойти сменой рантайма; гейт, зашитый в общий вызов тула, — нельзя, потому что рантайм не участвует в его выполнении.

Четыре гейта, зафиксированных в коде (не в системном промпте):
- **Fencing** — сторонний текст санитизируется, оборачивается в фиксированную метку-фенс, обрезается по `max_fenced_chars` до того, как модель его увидит; санитизация убирает невидимые/управляющие символы, подделанные маркеры хода диалога, теги транскрипта/tool-call и копии самой метки фенса.
- **Cart provenance (сторона покупателя)** — запись в корзину принимает только id товара, который в этой же сессии вернул инструмент каталога или заказа, либо уже лежащую в корзине строку; неоднозначный запрос («добавь товар с опциями») не додумывается моделью, а придерживается и направляется на явный выбор варианта.
- **Staging provenance (сторона мерчанта)** — то же правило происхождения id для листингов/кампаний; `apply_change`/`discard_change` принимают только id изменения, которое сама же сессия получила от staging или `get_pending_changes` — то есть модель не может «одобрить» изменение, о котором не докладывала.
- **Host approval gate** — при `require_host_approval=True` (дефолт) `apply_change` проходит только для id, которые **хост** (человек через портал или SDK-консоль) явно пометил approved; ни превью-карточка, ни «одобряю» в чате разрешения не дают — approval это отдельный канал, не текст диалога. На Managed Agents тот же контракт реализован платформенным `always_ask`-промптом на `apply_change`.

**Прямая параллель с уже задокументированным принципом read-only через отсутствие канала эксфильтрации** ([[claude-cookbook-scheduled-repository-reviewer]], 09-07): там read-only агент лишён канала *наружу* в принципе; здесь агент, у которого есть канал записи (мерчант меняет цены и остатки), лишён способности **исполнить** запись без прохождения через originating-id-проверку и человеческое одобрение — тот же принцип «канал есть, но заперт независимой проверкой», применённый к write-агенту вместо read-only.

**Четыре вертикали — одна пара агентов, а не четыре демо.** Retail (ACME), Travel (ACME Travel, date-bound inventory), Telecom (ACME Mobile, plan matrix + server-authored fee disclosures — регулируемые платежи защищены отдельно от произвольной ценовой правки), Entertainment (ACME Tickets, timed holds/waitlists/venue map) — расширяются через `PresentationExtension` (семь реализаций), не форк кода. `enable_*`-переключатели убирают тулы, строки промпта и правило grounding целиком, если у бизнеса нет соответствующей системы (например, нет корзины на реферальной поверхности) — тот же принцип «отсутствующая возможность — это выключенный тумблер, а не недописанный код», что уже встречался у Managed Agents конфигураций.

**Claude Code plugin для скаффолдинга** — `commerce-builder`, четыре команды (`/scaffold-commerce-agent`, `/add-commerce-flow`, `/author-commerce-evals`, `/review-commerce-agent`). Официальный пример того, как Anthropic сама распространяет паттерн: не отдельный сервис, а плагин, генерирующий код по этому же блюпринту в чужом репозитории.

## Что не взято / лиды

- **Дата публикации репозитория не подтверждена официально.** GitHub releases пусты («There aren't any releases here»), тегов не найдено; беглая проверка истории коммитов через WebFetch дала только один видимый коммит (31.08.2026, автор `alishazal`, «building commerce agents using claude») — недостаточно, чтобы установить дату первого публичного релиза, а не просто дату последнего коммита в выдаче. Дата «~03.09.2026» из записи лога 09-07 остаётся неподтверждённой точной датой, а не опровергнутой — не выдаётся зафиксированной, если не появится более надёжный источник (официальный анонс в блоге/changelog).
- **Backend-реализации (`StorefrontBackend`/`MerchantBackend`) не разобраны построчно** — README описывает интерфейсы (catalog/cart/order/policy, analytics/inventory/pricing/campaigns) на уровне контракта, сам код бэкендов не прочитан. Не критично: суть блюпринта в контрактах и гейтах, не в демо-реализации фейкового магазина.
- **Не проверено на практике** — как и Scheduled Repository Reviewer, разбор по чтению документации и README, без клонирования и запуска `run_demo.py`.
- **Grounding/analysis budgets** (раздел `docs/safety.md`, «grounding, the analysis budgets, and memory extraction are runtime features») — упомянуты как рантайм-специфичные (в отличие от гейтов, зашитых в исполнитель), но точный механизм не изучен отдельно — за пределами прочитанного README/safety.md.

## Оценка источника

Официальный репозиторий Anthropic (`github.com/anthropics/commerce-agents`), README и `docs/safety.md` прочитаны напрямую через WebFetch без блокировки прокси — не пересказ. Материал по мандату рутины (архитектурный паттерн агентской инженерии, переносимый за пределы retail-домена, ради которого он написан) полностью подтвердился: домен-специфика (розница/тревел/телеком/развлечения) — витрина, а не суть; суть — «один агент, три рантайма, гейты в исполнителе тула» переносится на любую пару «читающий + пишущий» агент.

## Проверка безопасности источника

README и `docs/safety.md` прочитаны целиком через WebFetch. Инструкций, адресованных агенту-читателю этой вики, не обнаружено — обычная техническая документация. Репозиторий сам явно декларирует отсутствие реальных побочных эффектов (не проводит платежей, не меняет живые листинги) — не источник риска для собственной вики, факт зафиксирован как есть.
