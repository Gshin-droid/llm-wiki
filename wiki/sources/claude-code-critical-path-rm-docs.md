# Claude Code: защита критических путей от `rm` и переменная, которая её снимает

**Автор:** [[claude-code]] (документация Anthropic)
**Опубликовано:** переменная — с версии 2.1.311 (конец октября 2026); раздел документации сверен 2026-11-02
**Тип:** официальная документация (раздел страницы о режимах прав)
**Ссылка:** https://code.claude.com/docs/en/permission-modes
**Raw:** `raw/inbox-assistant/2026-10-29-новая-переменная-в-claude-code-снимает-последнюю-защиту-прав.md` (`ai-assistant #187`, наводка из сводки обсуждений; первоисточник — документация по ссылке выше, не сохранялась в `raw/`)

## Саммари

Наводка из чата практиков: «новая переменная `CLAUDE_CODE_EVEN_MORE_DANGEROUSLY_SKIP_PERMISSIONS=1` снимает последнюю защиту прав». Факт подтверждён официальной документацией, но наводка опускает половину смысла — где переменная **не действует**. Главное, что берётся в вики, не сама переменная, а слова производителя о собственной проверке: она «может пропустить некоторые команды и не заменяет защиту уровня системы, например песочницу».

## Что взято в вики

**Критические пути** (раздел «Which paths are critical»): корень файловой системы; его прямые дети (`/usr`, `/etc`); домашняя папка, на Windows и её короткое имя 8.3; корни дисков Windows и их папки верхнего уровня (`C:\`, `C:\Windows`, включая написания `\\?\C:\`); рабочая папка и все папки над ней; дополнительные рабочие папки — только при удалении по маске внутри них (`rm -rf <dir>/*`).

**Что с такими `rm`/`rmdir` делает каждый режим.** Ни одно разрешающее правило и ни один хук `PreToolUse`, ответивший `allow`, их не одобряют. `default`/`acceptEdits` — спрашивают; `dontAsk` — отказ; `auto` — в терминале спрашивают с отсчётом, вне терминала отказ; `bypassPermissions` — в терминале спрашивают с отсчётом 2 минуты, в чате плагина VS Code и в Desktop — отказ, если не разрешил хук `PermissionRequest`. После трёх вопросов без ответа за сессию — сразу отказ.

**Переменная `CLAUDE_CODE_EVEN_MORE_DANGEROUSLY_SKIP_PERMISSIONS=1`** (с 2.1.311) снимает этот вопрос в `bypassPermissions`: `rm -rf ~` выполнится без спроса, включая команды, которые Claude Code не смог разобрать. Документация: ставить только в изолированной среде, которую не жалко потерять.

**Где переменная не действует** («Why the critical-path removal prompt stays on»):

- в чате плагина VS Code и в приложении Desktop — только `claude` в терминале;
- есть хоть одно правило `deny` или `ask` на Bash, Edit или Read — даже прочитанное посреди сессии и потом убранное;
- стоит хук `PermissionRequest` (любой matcher) или мод на это событие; хук `PreToolUse` отвечает `ask`;
- включено `permissions.blockReadsOutsideWorkingDirectories`;
- `claude` запущен изнутри другой сессии — но документация прямо говорит не считать это границей безопасности;
- фоновые сессии, участники agent team, сессии Remote Control — стартуют без переменной;
- не прочитаны управляемые настройки или реестр Windows (на неанглийской Windows и в WSL без interop запрос к реестру может не проходить всю сессию — тогда переменная бездействует).

**Читается только из окружения запуска**, блок `env` в любом файле настроек её игнорирует. При запуске печатается строка о состоянии переменной (`is set, so dangerous rm commands can run without a prompt` / `has no effect in this session`) — заданную переменную видно.

**Попутно — PowerShell** (раздел «Remove-Item in PowerShell»): `Remove-Item` на системный путь или с маской `*` отклоняется во всех режимах без вопроса, `cmd /c rd|del` на системный путь — тоже (с 2.1.283, отключается `CLAUDE_CODE_DISABLE_POWERSHELL_CMD_RM_DENY=1`). Отказ «Remove-Item on system path» поэтому бывает встроенной проверкой Claude Code, а не своим сторожем.

## Берём инструмент или логику

**Инструмент — не берём.** Режим `bypassPermissions` не используется; основная среда — чат плагина VS Code, где переменная не действует; версия на рабочей машине на 2026-11-02 — 2.1.306, ниже 2.1.311. Проверено: переменная не задана ни в окружении сессии, ни в переменных пользователя и машины Windows.

**Логика — да:**

1. **Производитель сам называет свою проверку забором.** Цитата: *"The check can miss some commands, so it doesn't replace an operating-system control such as sandboxing"* — «проверка может пропустить некоторые команды, поэтому не заменяет защиту уровня операционной системы, например песочницу». И ещё: проверка касается только `rm` и `rmdir`, «другие одобренные команды тоже могут удалить критические пути». Подтверждение линии [[zabor-i-stena-prava-agenta]]: встроенный запрет на `rm` — забор, стена — песочница или отсутствие инструмента.
2. **Опасный переключатель недоступен из файла настроек.** Переменная читается только из окружения запуска, `env` в настройках её игнорирует. Агент, который может править `settings.json`, не включит её себе сам. Тот же принцип — у своего сторожа адреса API в настройках ([[forever-downloads-agents-md-attack]]): опасное не должно включаться тем каналом, к которому у агента есть доступ.
3. **Заданный опасный режим объявляет себя при запуске.** Строка о состоянии переменной — пример правила «опасное состояние видно, а не тихо» ([[ai-security-by-design]]).

## Что не взято / лиды

- Проверка обходчиком «переменная не задана в окружении пользователя и машины» — предложена как вариант, пользователь выбрал без неё (2026-11-02). Вернуться, если появится сценарий с `bypassPermissions` в терминале.
- Полная таблица запроса на смонтированные диски (`/Volumes`, `/mnt/c`, переменная `CLAUDE_CODE_DISABLE_MOUNTED_DRIVE_RM_PROMPT`) — к нам не относится (Windows без WSL-сценариев с `rm` на `/mnt/c`), только упоминание.
