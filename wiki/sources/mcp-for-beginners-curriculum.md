## Что взято в вики

**1. Минимальный паттерн первого сервера (модуль 03.1).** Декоратор превращает функцию в тул, SDK берёт протокол на себя:

```python
from mcp.server.fastmcp import FastMCP

mcp = FastMCP("Calculator")

@mcp.tool()
def add(a: int, b: int) -> int:
    """Add two numbers"""
    return a + b

if __name__ == "__main__":
    mcp.run()
```

Отдельно назван инструмент разработки — `mcp dev server.py` запускает MCP Inspector автоматически. Тот же паттерн (декоратор + автогенерация протокольной обвязки) повторяется across языков курикулума, не только в Python.

**2. Best practices проектирования тулов (модуль 08), дословно значимое:**
- Единственная ответственность на тул вместо монолитных многофункциональных.
- Схема параметров с ограничениями (`minimum`/`maximum`, `enum` для закрытых множеств) и дефолтами — не просто типы.
- **Retry-политика различает эффектные и read-only операции**: «Generic retry loops are unsafe for tools that create tickets, payments, messages, deployments, or other real-world effects. A response can be lost after the effect commits» — для операций с побочным эффектом нужны стабильные ключи идемпотентности и сверка авторитетного состояния перед повтором, не голый backoff. Read-only — можно обычный exponential backoff.
- MCP `2026-07-28` stateless на уровне протокола — состояние между вызовами держит либо явный «handle» в параметрах тула, либо внешнее хранилище приложения, не сам протокол (совпадает с тем, что уже знает [[mcp-model-context-protocol]] про ревизию, но здесь — практическое следствие для дизайна, не только архитектурный факт).
- Логирование: нативный log-механизм MCP депрекирован спецификацией — писать в `stderr` для stdio-диагностики и использовать OpenTelemetry для метрик/трейсов, не полагаться на протокольный логгинг.

**3. Security-модуль (модуль 02) — шесть угроз, которых на [[ai-security-by-design]] раньше не было поимённо:**
- **Tool poisoning / «rug pull»** — атакующий меняет метаданные/описание тула у удалённого сервера уже после того, как пользователь его одобрил; нужен мониторинг изменений тул-дескрипторов, а не только проверка при первом подключении.
- **Token passthrough** — сервер принимает клиентский токен и пересылает его downstream API без валидации: рвётся аудит (кто именно вызвал), обходятся рейт-лимиты и мониторинг апстрима, сервер превращается в прокси для несанкционированного доступа. Формулировка спецификации дословно: «MCP servers MUST NOT accept tokens not explicitly issued for the MCP server» — валидировать `audience`-claim токена против идентичности самого сервера.
- **Confused deputy** — сервер как OAuth-прокси между клиентом и третьей стороной, атакующий эксплуатирует уже существующий cookie согласия, чтобы обойти экран авторизации; митигация — явное согласие на каждый динамически зарегистрированный клиент, OAuth 2.1 + PKCE, строгая валидация redirect URI.
- **Session hijacking** — требование «MUST verify ALL inbound requests and MUST NOT rely on sessions for authentication» — сессия не может быть единственным фактором.
- **Избыточные права** — минимальные права под конкретную функциональность, ролевая модель, периодический аудит против «privilege creep».
- **Supply chain** — проверка происхождения/лицензии/целостности каждого AI-компонента (модели, эмбеддинги, контекст-провайдеры) до интеграции, не только кода сервера.

Первые три (tool poisoning, token passthrough, confused deputy) — конкретизация уже известного вики класса «MCP-сервер как канал стороннего контента» (кейс ContextCrush на [[context7]]/[[mcp-model-context-protocol]]) под механизм авторизации, а не под контент. Кейс ContextCrush был про доверие к чужому *содержимому*; эта тройка — про доверие к чужой *аутентификации*, отдельный слой той же проблемы.

Перенесено в [[mcp-model-context-protocol]] (новый раздел «Практическая сторона: проектирование и защита сервера») и [[ai-security-by-design]] (новый раздел про три угрозы авторизации MCP).
